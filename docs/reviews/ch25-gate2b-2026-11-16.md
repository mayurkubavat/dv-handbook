## Blocking findings

### B1. The formal tool does not "model every reset at the clock"; it applies reset once and holds `rst_n` inactive afterwards (wrong mechanism)

`chapters/ch25-mutation-testing.qmd:245`: "rIC3 proves the miter, because
the formal tool models every reset at the clock, so the two designs are the
same machine to it." Also `examples/ch25-mutation-testing/equiv-reset/
reset.py:7-9` ("The formal tool models an asynchronous reset as one seen at
the clock"). Measured on a scratch script (`design` of `ch19.tcl` on
`fifo_fixed.sv`, the same `reset -expression {!rst_n}` every miter uses):
`cover {!rst_n}` is **unreachable** and `assert {rst_n}` is **proven** by
`informal-ic3`; with `informal-bmc` 10 s the cover is undetermined while
`cover {full}` is hit at depth 17. So after the reset phase the tool holds
`rst_n` high on every trace: no trace contains a second reset at all,
synchronous or asynchronous. That is why `m05` is proved equivalent: the
two designs differ only in how they respond to a reset that falls between
edges, and the tool never drives one. "Models every reset at the clock"
describes a different (and untested) semantics, and a reader who writes a
property about a mid-run reset will be misled by it. The class name
("equivalent only under the tool's reset model") and the example's result
stand.

Fix: "rIC3 proves the miter, because the formal tool applies the reset
only at the start of every trace and holds `rst_n` inactive afterwards (a
cover of `!rst_n` after reset is unreachable), so the one input on which
the designs differ, a reset that arrives between clock edges, never
occurs." Same correction in `reset.py:7-9`. Optionally add that cover to
`equiv-reset/` so the run shows the mechanism instead of asserting it.

### B2. "Identical code coverage" and "99% or more of the toggles" are contradicted by the opening table (text contradicted by spliced output)

`chapters/ch25-mutation-testing.qmd:30`: "Three of them reach every
expression point and 99% or more of the toggles." `:32`: "The random test
has the same code coverage as the coverage testbench ... Two testbenches
with identical code coverage sit at opposite ends of the kill axis";
`:541` (Summary): "the random test with the same coverage kills 35".
`opening/run.out:18-24` prints toggle 329/330 for the random test and
326/330 = 98.8% for the coverage testbench (the spliced lines 14-20 show
"100%" against "99%", and the figure's alt text itself says 98.8). The
coverage is equal on line, branch and expression points and differs by
three toggle points; it is not identical, and 98.8 is not "99% or more".
The argument does not depend on the difference, which is exactly why the
sentence should not overstate it.

Fix: ":30" "and 98.8% or more of the toggles"; ":32" "has the same line,
branch and expression coverage as the coverage testbench and three more
toggle points, and kills 35. Two testbenches with code coverage equal to
within three toggle points sit at opposite ends"; ":541" "with the same
line, branch and expression coverage".

### N3. The depth 31 of mutation 7759 is rIC3's trace length, not the shortest difference

`netlist-formal/measure.out:85` records `row 7759 - differs@31`, from
rIC3 after 10 s of bounded search found nothing. IC3 counterexamples are
not minimal: `informal-bmc` with a 200 s limit on the same miter finds a
counterexample at **depth 29** for 7759 (and at 31 for 8394, 18 for 7648,
16 for 8096, matching the file). I replayed both traces in an independent
Verilator testbench driving the two netlists (E3): they differ at step 29
and 31 respectively. The chapter's range "depth 16 to 31" (qmd:459) still
holds, but "The two at depth 31 were found by rIC3" (qmd:464) and
`nformal.py:24-26` ("the two deepest differences found again at the same
depth (31 ...)") present 31 as a property of the mutation. Fix: one
clause, "rIC3's traces are not the shortest; bounded search given 200 s
finds 7759 at depth 29".

### N4. The coverage experiment prints 0.945 for a conservative 95% interval without saying why

`netlist-population/run.out:56` (directed, n = 100): coverage 0.945; qmd:436:
"at least 94.5% ... and more often for most, as a conservative interval
should". A reader who has just been told the interval is conservative sees
a coverage below 95%. My exact computation, Clopper-Pearson coverage under
hypergeometric draws of 100 from the population (2,725 kills in 9,281), is
**0.9538**; the printed 0.945 is 1.8 Monte Carlo standard errors
(sqrt(0.05 x 0.95 / 2000) = 0.0049) below it, i.e. noise. Same for the one
high cell, directed at n = 30: exact 0.9752, printed 0.983 (+2.2 se).
Fix: print the Monte Carlo standard error beside the table, or say in the
prose "every value is within two Monte Carlo standard errors (0.005) of at
least 0.95".

### N6. "On the memory" is approximate in both directions

`netlist-list/run.out:49-50` counts lines 29, 36, 42, 43 and 57 as the
memory: line 36 is the `always_ff` header, so its 734 `$procdff`
mutations include the pointer and count flops; line 42 (`if (do_write)`)

which the chapter attributes to memory mapping (qmd:354), are left out.
"Three quarters" (qmd:376) is a fair round figure, but the run line's
label "on the memory" is not exact. Fix: "on the memory and its
write-enable and register cells (lines ...)", or count by cell name.

### N7. The figure generator's pins are `assert` statements

`figures/gen_ch25_figures.py:79` and every value check (`:149-230`) use
`assert`, which `python3 -O` strips, after which a changed `run.out` would
silently redraw. Not run that way by any script here. Fix: `raise
SystemExit(...)` in `data()`.

### E4. Statistics

shared code) reproduces all 56 intervals printed in the chapter's
