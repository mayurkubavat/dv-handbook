### B4. "A simulation can neither refute nor confirm a liveness property" is too strong (L77, L80, L487)
- L77 (Definition box), repeated at L487 ("can say nothing about liveness").
  L80 calls it "a theorem about monitoring".
- By the chapter's own (Alpern-Schneider) definition, **F** p is a liveness
  property, and the three-valued monitor the chapter cites returns *true* for
  it on any prefix that contains p. What holds for every liveness property is
  only that no finite prefix refutes it. The "inconclusive forever" result is
  for non-monitorable formulas such as **G F** p, which is what the cited
  sentence is about.
- Also "confirm" conflates two things: a run can confirm that *this trace*
  met an eventuality; no run confirms a property of the design (safety
  included, as L487 says).
- Fix (L77): "A simulation is a finite prefix, so it can refute a safety
  property and can never refute a liveness property. The most it can do for
  one is witness that this run fulfilled an eventuality (**F** p); for a
  recurrence such as **G F** p it can conclude nothing in either direction."
  Adjust L80's first sentence and L487 to match.

### B5. Until is defined with a strict future (L60)
- "p **U** q ... holds where q holds at some later position and p holds at
  every position before it." In LTL (and SVA `s_until`) q may hold at the
  current position; the chapter's own **G** and **F** are given the
  reflexive reading ("from here on").
- Fix: "holds where q holds at this position or a later one, and p holds at
  every position from here up to it."

### B6. Wrong clause for the sampled-value functions (L133)

- Could not open the standard from this environment; the numbering is from
  memory of 1800-2017 and 1800-2023 and should be confirmed against the PDF
  before the fix is committed.
- Fix: "[@ieee1800-2023, clause 16.9.3]".

### B8. The `_C` suffix is not in the cited source (L234)

### B10. The `First` covers are over-read (L454, L466)
- L454: the rule "says that a run with READY held low must still reach
  VALID, which is a statement that a certain trace *exists* ... It is a
  cover." L466: "Each is a trace ... in which a channel's VALID is high and
  its READY has never been: the master does not wait."
- A reached cover shows that the master *can* raise VALID before any READY
  in at least one scenario. The AXI rule forbids the dependence in every
  scenario; a master that waits for READY only in one mode, or only on
  transfers after the first, reaches all three covers. (The sticky bit also
  means only the first offer on each channel is ever examined, as L454
  admits for simulation; the same holds in the proof.)
- The unreachable result on the mutant (L468) is sound and is the valuable
  half. The reachable result is necessary evidence, not a proof of the rule.
- Fix: L466 "the master is able to offer first; the cover does not show that
  it always does". L454: say the rule is of the form "for every offer there
  is a run ..." and that the cover is its witness for the first offer. If a
  stronger statement is wanted, add a run with `assume {!ARREADY}` (and the
  other two) and show `ArWait_C` still covered, or leave it to the exercises.

## Non-blocking findings

N1. L135, "a tick no specification describes, and each tool fills it in for
itself". IEEE 1800 does define `$past` before the first clock tick (the
default value of the expression's type, so X for 4-state; 16.9.3). A 2-state
simulator returning 0 is a consequence of that, not a free choice. Suggest:
"a tick the design's specification does not describe; the standard gives it
the type's default value, and the two tools here differ".

N2. L133: `$rose`/`$fell` are described as tests of "a one-bit signal". On a
vector they test bit 0 only, and the probe row is "on one bit and on a
vector". One clause would save a reader from `$rose(bus)`. Also `$rose` is
true for X-to-1, not only 0-to-1.

N3. L131 and L158: nowhere does the prose say that the `disable iff`
condition is *not* sampled (it acts on current values, between edges too),
though a probe row and L295 depend on that fact. One sentence at L131.

N4. L225: the fourth vacuity run's `Req_C` "covered at depth 0" is a
finite-prefix artifact: no infinite trace satisfies the two assumptions, so
under the standard's semantics the cover has no witness at all. Worth one
sentence, since other tools report such dead ends differently.

N5. L495 (Summary) "the formal tool's is zero always" contradicts L354
("only an error in the script itself changes the status").

N6. L331: "The two lines before it" (engine and time limit) are not before
`prove -all` in the script shown (`response.tcl` sets them inside `load`).
`clear -all` in the same listing is not explained.

N7. L299: "It refuses the operators it does not implement by name" does not
cover the `checker ... endchecker` row ("no build — SystemVerilog errors").
L295: the build message quoted for `b[=2] ##1 c` is about cycle delays and
default clocking, not about the operator; "refused with a message, which is
the honest outcome" reads more into it than the cell shows.

N8. The InFormal README (fetched, commit 5114330) says constructs it cannot
model "are rejected with a message, never guessed", and lists liveness under
"Not there yet". The chapter measures silent drops of immediate assertions
and a liveness row that *runs*. Both are fair as dated measurements; say in
one sentence that the first departs from the tool's stated intent (and
whether it was reported upstream), so the reader sees a defect of a
pre-release and not a design decision. Same suggestion for the ten Verilator
verdicts: say whether they were reported.

N9. Wording: "the more honest of the two" (L121), "the honest outcome"
(L295). Measured and not disparaging, but "explicit" is the neutral word.

N10. Terms used before definition: *depth* (L25, L27; defined L333);
`expect`, `finish`, `trace` in the first listing (explained L331, L351);
`informal-kind` in the first output (k-induction named L365, L408). A
half-sentence at L25 ("depth, the index of the cycle, counting from the
reset cycle") would do.

N11. L11: the "specification's sentence" is in quotation marks with
"sixteen"; the specification text in `ch01-what-is-dv/rtl/fifo.sv` says "all
DEPTH entries". Drop the quotation marks or quote it as written.

N12. L346 and L52 type whole statements of code into prose
(`always @(posedge clk) if (rst_n) Name_A: assert (expr);`). Identifiers and
operators inline are the book's practice; a full statement is close to the
"no code typed into prose" rule. The L346 form already exists as a probe and
could be spliced.

N13. Listing width: every included *source* file is within 80 columns. Eight
`run.out` files have lines over 80 (one verdict line each; three in
`fifo-proof`; fifteen in `fifo-cocotb/run.out`, up to about 170 columns and
with local install paths). The rule names source files, so this is not a
breach, but the cocotb block will not fit a 7-inch page; splice only the
result lines or filter the log in the runner.

N14. "the first chapter" (L11, L27) is an ordinal in words where the label
`@sec-ch01-example` is already in the sentence at L11. `check-structure.sh`
