## Serious (not blocking)

**S1 — `:99` attributes to OpenTitan's base test an idiom the file does
not contain.**

`:99`: "A factory that creates by type creates the specialization the
environment names, and the test that wants a different one must
`$cast` the result, which is the idiom in OpenTitan's base test
[@opentitan-dv-base-test]."

The cited file (`src/dv_base_test.sv`, fetched today by the previous
round; `:48–:70`):

```
    if (!uvm_config_db#(uvm_object_wrapper)::get(this, "env", "cfg_type", cfg_type)) begin
      cfg_type = CFG_T::get_type();
    end
    ...
      base_cfg = cfg_type.create_object("cfg");
      ...
      // At this point, we will normally have just created an object of type CFG_T, but have a
      // handle to it with a weaker type. But we might have got an instance of some extension class
      // if one is passed as cfg_type. Either way, we should be able to cast the result to a CFG_T.
      if (!$cast(cfg, base_cfg)) begin
        `uvm_fatal(`gfn, ...
```

Three things differ from the sentence. The type is named by the *test's*
parameter `CFG_T` (or by a wrapper the testbench puts in the config
database), not by the environment. The `$cast` is unconditional: the
base test performs it on every path, because `create_object` returns a
`uvm_object` handle — "a handle to it with a weaker type" — and it
casts *to `CFG_T`*, the type it declared. And the party that wants a
different type (the testbench that passes `cfg_type`) does no cast at
all. So "the test that wants a different one must `$cast` the result"
is not the file's idiom; a first-year reader takes away that a caller
casts in order to *get* a different specialization, when the file shows
the receiver casting *down to the one it asked for* and checking the
answer. This was M2 of the previous round; the rewrite changed the
sentence without adopting the fix, and the new wording is further from
the source than the old.

Why serious rather than blocking: the file does contain a factory
create followed by a checked `$cast`, so the citation supports the
general point (typed creation returns a base handle that must be cast
down); what is wrong is who casts and why. It is a claim about a named
project's code, so it should be right before the tag.

Fix: "A factory that creates by type hands back a base handle, and the
receiver `$cast`s it down to the specialization it declared and checks
the answer — the idiom in OpenTitan's base test, which creates its
configuration object through a type wrapper and fatals if the cast
fails [@opentitan-dv-base-test]."

**S2 — `:168` "The tool-layer appendix develops both" — it develops
neither.**

`:168`, closing the Future Directions box: "An agent that derives a
transaction class can be asked, mechanically, whether the derived class
still randomizes to a legal transaction and whether its overrides still
call `super` … And the *wrong* cells in the table above are a
specification: for a flow that runs on that tool, they are the
constructs an agent must refuse to emit … The tool-layer appendix
develops both."

`appendices/appI-agent-tool-layer.qmd` (346 lines, sections
`sec-appI-substrate` … `sec-appI-building`) contains no occurrence of
"substitut", "Liskov", "refuse", "legal", "constraint", "super" (other
than "superseded"), "Icarus", "virtual", "derived class" or any
reference to `@tbl-ch06-support` or `@sec-ch06`. Its tool catalog
(`:139–:212`) lists `rtl.compile_check`, `rtl.lint`, coverage and log
tools; nothing checks an override for a `super` call or a derived
constraint set for legality, and nothing consumes a support table as a
list of constructs to refuse. The sentence sends the reader to material
that is not there.

Fix, either of: (a) drop the sentence and let the box end on "report
success for tests it did not run"; or (b) replace it with what is true
— "A parser that elaborates the whole language is the front end the
tool-layer appendix starts from; the two checks are not in its catalog
yet" — and cross-reference by label (`@sec-appI-catalog`). (a) is the
smaller change.
