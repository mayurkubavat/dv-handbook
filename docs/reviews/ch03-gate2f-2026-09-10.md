## 1. Blocking

### 1.1 A blended clock, and a gate-built clock multiplexer, pass the build gate on an eight-bit asynchronous crossing

`tools/dvh/clocks.py:47-84` decides, at a gate feeding a clock pin, which input
is the clock. Strong evidence is that the net already drives some register's
clock pin *directly*; weak evidence is that it is merely an input port
(`clock_candidates`, `clocks.py:65-76`). `_walk_to_sources` (`clocks.py:155-168`)
keeps only the inputs of the best available tier and records the rest as
`gated by ...`. A second clock that drives no register's clock pin directly is
therefore weak, loses to the strong one, and is recorded as an enable — with
`clock_ambiguous` left **false**, so nothing says the choice was made.

`crossings` (`clocks.py:481-487`) then compares `root_bits`, and both registers
report the same single root bit, so `same_clock_source` is true and the crossing
is dropped from `unrecognized` (`clocks.py:508-509`).

@sec-ch03-clocks — `chapters/ch03-digital-design-for-verifiers.qmd:61` — names
this operation in the chapter's own words, quoting Plassan: "*blending*,
combining two clocks to generate a new one".

```systemverilog
// blend.sv -- Plassan's "blending": two clocks combined to make a third.
// clk2 is an independent asynchronous clock, not an enable.  It drives no
// register's clock pin directly, so the walk has no strong evidence for it.
module blend (input logic clk1, clk2, input logic [7:0] d,
              output logic [7:0] q);
  logic gclk;
  logic [7:0] a, b;
  assign gclk = clk1 & clk2;
  always_ff @(posedge clk1) a <= d;      // clk1 domain
  always_ff @(posedge gclk) b <= a;      // blended domain, 8 bits, no sync
  assign q = b;
endmodule
```

```
$ PYTHONPATH=tools python -m dvh.cli read blend blend.sv
clock domains: 2
  clk1#2: 1 registers
  clk1#20: 1 registers
registers without reset: 2
  a  [blend.sv:9]
  b  [blend.sv:10]
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (clk1#2) -> b (clk1#20), 8 bits, no synchronizer shape  [blend.sv:10]
instances: 0, connections: 0
$ echo $?
0
```

`dvh crossings blend blend.sv --validate` names the mechanism exactly:

```json
{"to": "b", "to_domain": "clk1#20", "from": "a", "from_domain": "clk1#2",
 "width": 8, "direct": true, "second_stage": [], "shape_recognized": false,
 "same_clock_source": true, "note": "no synchronizer shape"}
```

and `"unrecognized": []`. `dvh clock-tree` shows the demotion and shows that it
was never flagged:

```json
"b": {"clock_sources": ["clk1"], "gated_or_muxed": true,
      "through": ["$and", "gated by clk2"],
      "clock_ambiguous": false, "root_bits": ["2"], "domain": "clk1#20"}
```

**The multiplexer case is worse, because the chapter promises it explicitly.**
Nobody writes a clock multiplexer as a ternary; a glitch-free clock mux is
written as gates, and Yosys leaves it as gates, so `_walk_to_sources`'s
`MUX_TYPES` branch (`clocks.py:150-154`) — the branch added in the previous
round precisely so that selection never demotes — never runs:

```systemverilog
// glitchmux.sv -- a glitch-free clock multiplexer built from gates rather
// than from a ternary, which is how one is actually written.
module glitchmux (input logic clk1, clk2, sel, input logic [7:0] d,
                  output logic [7:0] q);
  logic cout;
  logic [7:0] a, b;
  assign cout = (clk1 & ~sel) | (clk2 & sel);
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge cout) b <= a;
  assign q = b;
endmodule
```

```
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (clk1#2) -> b (clk1#24), 8 bits, no synchronizer shape  [glitchmux.sv:9]
```

**Exit 0.**

**This falsifies a printed sentence.**
`chapters/ch03-digital-design-for-verifiers.qmd:296`:

> "Where the two nets trace back to a single shared clock *net*, as a gated
> clock does, the tool says so and the path does not fail the gate. Where they
> do not, as with a divider or a multiplexer between two clocks, it does fail"

On `glitchmux.sv` there *is* a multiplexer between two clocks and it does not
fail. The two nets do not trace back to a single shared clock net either: they
trace back to one *chosen* net, and the other clock was discarded as an enable.
The line printed about both designs — "1 of them one clock gated differently" —
is false of a design whose two clocks are unrelated.

`:242` is falsified by the same designs:

> "What the tool does with that is the part worth copying. It reports the
> crossing and says the clock could not be told from the enable, rather than
> suppressing it."

Here the tool does not say the clock could not be told from the enable. It
decided, silently (`clock_ambiguous: false`), and the crossing is suppressed
from the gate. `:240`'s claim — "Where the evidence ties, the walk says so
rather than choosing" — is true only when the evidence ties. The defect is in
the case where it does *not* tie because one clock happens to have a register
on it and the other does not, which is the ordinary shape of a gated or
multiplexed clock domain: the registers are behind the gate, not in front of it.

**Fix.** Two are available and they are complementary.

1. Strong evidence of "this is a clock" must not be read as evidence that the
   *other* input is not one. `clock_candidates` already computes a `weak` set;
   an input that is a top-level port, a register output, or an unknown driver is
   a clock *candidate*, and where a gate has two candidates the walk should
   either follow both (giving two root bits, so `same_clock_source` is false) or
   set `clock_ambiguous`. Demoting to `gated by ...` should be reserved for an
   input with no candidacy at all — one driven by combinational logic over
   non-clock registers, which is what an enable is.
2. Independently, `same_clock_source` should require that neither register's
   clock walk demoted anything: a crossing whose two clock cones differ in their
   `through` list has not been shown to be one net. That is a two-line change
   and it closes the exit-0 hole even if (1) is judged too aggressive.

Fixtures: `blend.sv` and `glitchmux.sv`.

### 1.2 `(* keep_hierarchy *)` makes the whole design disappear: 0 domains, 0 crossings, exit 0

`design.py:112-117` builds the Yosys script and `load_flat` (`design.py:251-253`)
returns `_parse(...)[top]` — the top module alone. Yosys's `flatten` honors the
`keep_hierarchy` attribute, so a submodule carrying it is left as an instance
and every register inside it is in a module the tool never looks at.

```systemverilog
// keephier.sv -- a submodule marked keep_hierarchy holds the crossing.
(* keep_hierarchy *)
module lane (input logic aclk, bclk, input logic [7:0] d,
             output logic [7:0] q);
  logic [7:0] a, b;
  always_ff @(posedge aclk) a <= d;
  always_ff @(posedge bclk) b <= a;      // 8 bits, no synchronizer
  assign q = b;
endmodule

module keephier (input logic aclk, bclk, input logic [7:0] d,
                 output logic [7:0] q);
  lane u_lane (.aclk(aclk), .bclk(bclk), .d(d), .q(q));
endmodule
```

```
$ PYTHONPATH=tools python -m dvh.cli read keephier keephier.sv
clock domains: 0
registers without reset: 0
crossings: 0, shape not recognized: 0
instances: 1, connections: 4
$ echo $?
0
```

The design contains two clocks, two registers and an eight-bit unsynchronized
crossing between them. The report says the design has no clocks and no
registers, and the build passes. Confirmed directly against Yosys, with the
tool's own script:

```
$ yosys -p "read_verilog -sv keephier.sv; hierarchy -check -top keephier; \
    proc; opt_dff; memory_collect; memory_map; flatten; opt_clean; stat"
=== keephier ===
        4 wires ... 1 submodules
        1   lane
=== lane ===
        2 cells
        2   $dff
```

`keep_hierarchy` is not an exotic attribute. It is the standard way to stop a
synthesis flow dissolving a block, and it is applied most often to exactly the
blocks a CDC analysis cares about — clock-domain-crossing wrappers, hard
macros, and anything with a physical-implementation constraint.

The report is internally inconsistent about it, which is what makes this cheap
to detect: the same run prints `instances: 1, connections: 4`, from the
*hierarchical* load, on the same line as `clock domains: 0` from the flattened
one. The tool already has both numbers in hand.

Note this is not the black-box case. A black box has no contents to analyze and
the tool is right to be silent about it; `keep_hierarchy` means the contents
exist and were skipped.

**Fix.** In `_run_yosys`, when `flatten=True`, strip the attribute first —
`setattr -mod -unset keep_hierarchy` before `flatten` — and, as a
belt-and-braces check that does not depend on knowing every attribute Yosys
honors, have `load_flat` raise `DesignError` when the returned top module still
contains a cell whose type names another module in the same JSON. That turns a
silent exit 0 into exit 2, "the tool could not answer", which is what
`cli.main`'s three-way contract at `cli.py:100-107` exists for. Fixture:
`keephier.sv`.

### 1.3 `shape_recognized: true` on parallel one-bit chains carrying one value, when the sending flops sit behind two clock gates

`_flag_parallel_synchronizers` (`clocks.py:316-391`) has two rules. The second,
the blunt one, groups by `(c["from_domain"], c["to_domain"])`
(`clocks.py:378-380`). A domain key is `label#clkbit` (`_domain_key`,
`clocks.py:206`), so *one* clock gated two ways is two domain keys, and two
chains off it are two groups of one. Neither rule fires.

```systemverilog
// perbitgate.sv -- a two-bit value crossing on two one-bit synchronizers,
// with the two sending flops behind two different clock gates off one clock.
// Each chain is a correct two-flop synchronizer; together they are the loss
// of data @sec-ch03-cdc describes.  `keep` gives aclk strong evidence, which
// is what stops the walk calling the gate ambiguous.
module perbitgate (input logic aclk, bclk, en0, en1,
                   input logic d0, d1, output logic [1:0] q,
                   output logic k);
  logic g0, g1, keep, a0, a1, p0, p1, r0, r1;
  assign g0 = aclk & en0;
  assign g1 = aclk & en1;
  always_ff @(posedge aclk) keep <= d0;   // strong evidence for aclk
  always_ff @(posedge g0)   a0 <= d0;
  always_ff @(posedge g1)   a1 <= d1;
  always_ff @(posedge bclk) p0 <= a0;     // first stages
  always_ff @(posedge bclk) p1 <= a1;
  always_ff @(posedge bclk) r0 <= p0;     // second stages
  always_ff @(posedge bclk) r1 <= p1;
  assign q = {r1, r0};
  assign k = keep;
endmodule
```

```
$ PYTHONPATH=tools python -m dvh.cli read perbitgate perbitgate.sv
clock domains: 4
  aclk#11: 1 registers
  aclk#12: 1 registers
  aclk#2: 1 registers
  bclk: 4 registers
...
crossings: 2, shape not recognized: 0
  known a0 (aclk#11) -> p0 (bclk), 1 bit, two-flop synchronizer  [perbitgate.sv:15]
  known a1 (aclk#12) -> p1 (bclk), 1 bit, two-flop synchronizer  [perbitgate.sv:16]
instances: 0, connections: 0
$ echo $?
0
```

Two bits of one value, synchronized bit by bit across one physical clock
boundary, reported as two recognized two-flop synchronizers, exit 0. Remove the
clock gates — put `a0` and `a1` on raw `aclk` — and both are demoted and the
run exits 1, so the gates are the whole of it.

The tool has the information it needs and does not use it: `clock-tree` reports
`"root_bits": ["2"]` for `a0`, for `a1` and for `keep`, which is how
`same_clock_source` already knows in `crossings` (`clocks.py:481-487`) that
`aclk#11` and `aclk#12` are one clock.

**Relation to the printed text.** `:255` is careful and is not falsified — it
says "the same pair of domains". But `:314`, the summary bullet, says "per-bit
synchronizers are a loss of data rather than a partial fix", and exercise 6 at
`:327` opens "The tool rejects parallel one-bit synchronizers across a clock
boundary, because someone anticipated that anti-pattern — twice". `perbitgate.sv`
is parallel one-bit synchronizers across a clock boundary and the tool accepts
them. This is the third distinct route past that check and the second review in
a row to find one, which is the pattern `gate2e`'s closing section named.

**Fix.** Group by the clock *roots*, not by the domain key: key rule 2 on
`(frozenset(root_bits of from), frozenset(root_bits of to))` taken from
`tree["registers"]`, which `crossings` already has in hand. One clock gated
several ways is then one boundary, which is what it physically is. Fixture:
`perbitgate.sv`.

## 2. Serious (not blocking, but they belong in the next patch)

### 2.1 A deep combinational cone ends the run with `RecursionError`

`_walk_to_sources` (`clocks.py:87`) recurses once per net bit, so the cone depth
is the Python stack depth. A 1500-level chain — an XOR chain, which cannot be
collapsed — ends the run:

```
$ PYTHONPATH=tools python -m dvh.cli read deepchain deepchain.sv
dvh: RecursionError: maximum recursion depth exceeded
dvh: this is a defect in the tool, not a finding about the design
$ echo $?
2
```

The three-way exit contract works exactly as `:300` says it should: this is
reported as "could not answer", not as a finding, and a gate would stop. So it
is not blocking. It is listed because the fix is two lines — make
`_walk_to_sources` iterative over an explicit stack, which it can be since it
only unions the sources it reaches — and because the failure mode is invisible
in the tests, whose deepest design is a few levels.

### 2.2 The run time is superlinear in array size, and the chapter proposes this as a per-commit gate

`_flag_parallel_synchronizers` (`clocks.py:351`) builds `feeds` by calling
`_data_cone_registers` once per register, and each of those walks a cone that a
lowered array makes wide. Measured on a plain dual-clock RAM (`ram<N>.sv`,
`N x 32`, one write clock and one read clock):

| entries | registers | `dvh read` |
|---|---|---|
| 16 | ~512 | 4.0 s |
| 32 | ~1024 | 10.0 s |
| 64 | ~2048 | 31.1 s |
| 128 | ~4096 | 158.9 s |
| 1024 | ~32768 | did not finish in 25 minutes |

That is roughly N^2.3. `:294`'s Future Directions callout proposes deriving "the
domain map, the crossing inventory, the reset-release order and the connection
graph on every commit"; a single 1 KB x 32 memory puts that out of reach. Worth
either a stated limit in the callout or a cheap fix: `feeds` recomputes the same
cones many times, and memoizing `_walk_to_sources` per (bit, any_comb) would
collapse most of it.

### 2.6 `ancestors`'s memo can cache an incomplete answer

`_flag_parallel_synchronizers` (`clocks.py:352-366`) memoizes into `reach` while
sharing one `seen` set down the recursion:

```python
    def ancestors(name, seen=None):
        seen = seen if seen is not None else set()
        if name in reach:
            return reach[name]
        out = set()
        for p in feeds.get(name, ()):
            if p in seen:
                continue
            seen.add(p)
            out.add(p)
            out |= ancestors(p, seen)
        reach[name] = out
        return out
```

A nested call runs with a `seen` that already holds nodes, prunes them, and then
writes the pruned result into `reach` as if it were complete. Running the
function verbatim over `memo.sv`'s own register graph (below) and permuting only
the visit order shows the algorithm is order-dependent by construction; the
iteration order it actually gets is `_data_cone_registers`'s return value, a
Python **set**, whose order varies with the interpreter's string hash seed
(verified: `PYTHONHASHSEED` 0-9 gives both `['aa','bb']` and `['bb','aa']`).

I could not make it change a printed report: on `memo.sv` the note comes out
identical under `PYTHONHASHSEED` 0-7, and rule 2 (§1.3) catches the cases rule 1
misses whenever the chains share a domain pair. So this is a latent defect, not
a demonstrated one — but it is latent in the one rule `:253` and `:255` describe
at length, and the consequence when it does bite is the wrong register named in
"read together by X", which `:255` calls "the specific thing a reviewer wants to
be told". Fix: give each top-level call its own `seen` and drop the memo, or
memoize properly with an SCC-aware traversal.

```systemverilog
// memo.sv -- two one-bit synchronizer chains whose bits are read together
// by a register further downstream, through a diamond in the register graph.
module memo (input logic aclk, bclk, input logic x1, x2, output logic rr);
  logic a1, a2, f1, s1, f2, s2, bb, aa, r;
  always_ff @(posedge aclk) begin a1 <= x1; a2 <= x2; end
  always_ff @(posedge bclk) begin f1 <= a1; s1 <= f1; end
  always_ff @(posedge bclk) begin f2 <= a2; s2 <= f2; end
  always_ff @(posedge bclk) bb <= s1;         // reads chain 1
  always_ff @(posedge bclk) aa <= bb & s2;    // reads bb and chain 2
  always_ff @(posedge bclk) r  <= aa & bb;    // reads aa and bb
  assign rr = r;
endmodule
```
