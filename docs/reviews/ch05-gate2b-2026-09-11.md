## Blocking

**B1 — `:25` says the chapter adopts the 2013 X paper's guideline, then
states a rule the guideline excludes, without saying so.**

`chapters/ch05-testbench-language.qmd:25`:

> That paper's guideline is the one this chapter adopts: variables that
> will or might take randomly generated values are declared two-state,
> and two-state types are used for that and for nothing else in a
> testbench [@sutherland2013x]. […] The testbench rule is then:
> Two-state for what the testbench *computes* — stimulus, counters,
> expected values, scoreboards — because those values are the
> testbench's own and an X among them is a testbench bug.

The paper, §10.1 (`x2013.pdf`, page 18, read in layout):

```
Sutherland HDL recommends using 4-state data types in all places, with
two exceptions:
• The iterator variable in for-loops is declared as an int 2-state
  variable.
• Verification stimulus variables that will (or might) have randomly
  generated values are declared as 2-state types.
[…] 2-state data types should only be used for generating random
stimulus values. Design code should use 4-state types.
```

The first sentence reports the guideline accurately — two-state for
random stimulus and for nothing else. The rule that follows two
sentences later, introduced with "then", puts counters, expected values
and scoreboards in two-state as well, and `:79` extends it further
("Declare a scoreboard's *expected* values two-state, because the
testbench computed them"). The chapter's rule is broader than the
guideline it says it adopts, and the paragraph — which is careful to
declare its departure from the 2007 paper's `logic` advice two clauses
earlier — does not declare this one. A reader who follows the citation
finds the paper recommending four-state for everything the chapter's
rule puts in two-state except the stimulus. This is the residue of the
previous round's B1: the rule is now built on the paper that states the
guideline, but it still claims more of that paper than it gives.

Fix (one sentence): own the extension. For example, after the
`[@sutherland2013x]` sentence: "This chapter goes further than that
guideline, and says so: it puts everything the testbench computes in
two-state, not only the random stimulus, because … ." Then "The
testbench rule is then" becomes "The testbench rule is". `:79` needs no
change once the extension is declared.

**B2 — `:253` still names the 2013 synthesis paper as the source of the
type rule and of the interface reconciliation; the body no longer does,
and the paper gives neither.**

`:253`:

> Sutherland and Mills' SNUG 2013 paper is the source for the type rule
> and for why the two style guides disagree about interfaces
> [@sutherlandmills2013synth].

The paper's whole statement on testbench types is one sentence that
defers elsewhere (`synth2013.raw.txt:215–217`): "Note that verification
code is a little different. In a testbench, randomly generated test
values should be declared as bit (2-state), rather than logic (4-state).
See Sutherland [20] for a detailed exploration of using 2-state and
4-state types in design and verification code." The chapter's own `:25`
now says exactly that ("note in passing … with the reasoning deferred to
Sutherland's paper on X") and attributes the guideline to
`sutherland2013x`. On interfaces, the paper's §8 gives the
related-versus-all-ports distinction and the one-line verification
aside (`:1829–1833`); it does not mention lowRISC or either style guide,
and `:107` now says in so many words that "the reason the exception
holds is this chapter's, not theirs". The further-reading sentence is
the previous round's B1 and S6 surviving in the one paragraph a reader
uses to find the sources — and the X paper, which the body names as the
guideline's source, is not in further reading at all.

Fix: "Sutherland's DVCon 2013 paper on X states the two-state guideline
this chapter starts from [@sutherland2013x]; Sutherland and Mills' SNUG
2013 paper gives the RTL-side rule and the distinction between an
interface that bundles related signals and one that bundles a
testbench's [@sutherlandmills2013synth]."

## Serious (not blocking)

**S1 — `:109` makes "using it before it is set" the single cause of
three failures, one of which happens at the moment it is set.**

`:109`: "using it before it is set is the single cause of every
virtual-interface failure a testbench has: the null dereference at run
time, the compile error when the class's declared parameters do not
match the instance it is given, and the silent nothing when the wrong
instance is given [@sutherland2007gotchas; @rich2012missinglink]."

The parameter mismatch is a type error on the assignment. Measured with
pyslang 11.0.0 on a class holding `virtual itf #(16) vif` assigned an
`itf #(8)` instance:

```
BadAssignment value of type 'interface itf#(W=8)' cannot be assigned to
type 'virtual interface itf#(W=16)'
```

The error is at `m.vif = i8`, which is the handle being set, not used
before it is set. The sources support the parts (2007 §4.2: "a pointer
to an interface is called a virtual interface"; Rich: "any
parameterization of the interface instance needs to be repeated in the
virtual interface declaration", `rich2012.raw.txt:228–230`); neither
supports "single cause". The Pitfall at `:118` has the defensible form
already — "Each is 'it is a variable' seen from a different side". Fix:
use that form at `:109`: "every virtual-interface failure a testbench has
is a variable's failure: …".

**S2 — `:25` attributes to the synthesis paper two reasons it does not
give.**

`:25`: "Sutherland and Mills argue that RTL should avoid two-state types
altogether, because a two-state model cannot show the reset a design
forgot or the input nobody connected". The paper's reasons
(`synth2013.raw.txt:253–258`): "there is a risk of a functional mismatch
between simulation and the synthesized implementation … 2-state
variables begin simulation with a value of 0 … Avoid all 2-state types
in RTL models. These types can hide design problems (see Sutherland
[20]), and can lead to simulation vs. synthesis mismatches." The
forgotten reset and the unconnected input are the 2006 paper's §3.3
(`g2006.raw.txt:783–823`), which `:32` cites correctly. Fix: "because,
as the 2006 catalogue shows, a two-state model cannot show …
[@sutherland2006gotchas; @sutherlandmills2013synth]", or drop the
"because" clause.

**S3 — The table row "queues and arrays of handles" measures a fixed
array; a queue of handles gives a different verdict on Icarus, and the
worked example's scoreboard is a queue of handles.**

`probes/j20a_handle_array_init.sv` declares `item arr[4]` and no queue.
Measured, a queue of handles with the handle pushed from a variable
(`q_handles2.sv`):

```
$ iverilog -g2012 -o build/qh2.vvp q_handles2.sv
q_handles2.sv:2: Sorry: Queue of type `class item{...}` is not yet supported.
q_handles2.sv:3: Error: Class/null r-value not allowed in this context.
$ ./build/qh2/Vtop            # Verilator 5.030
sum=3
```

So the queue half of the label is *no build* on Icarus where the row
says *no run* (the array's `vvp` load failure). The counts are
unaffected (both are "not runs"), but the worked example's `packet
expected [$]` (`tb_packet_fifo.sv:14`) is the construct a reader will
look up, and the cell they find was measured for something else. This
was noted in the previous round's §2 table and not carried into a
numbered finding; the row is unchanged. Fix: split the row as the static
row was split — "fixed array of handles" (no run / runs) and "queue of
handles" (no build / runs) — with a queue probe.

**S4 — `:188` "Each is a documented gap" sources two of the five.**

`:188` lists interfaces as module ports, virtual interfaces,
parameterized classes, clocking blocks and associative arrays, then
cites issues for the first and last only. The other three are documented
— the tracker has, all open: #465 (2021-01-02) "SV: interface - parsing
support for clocking block, modport?", #166 (2017-10-04) "Does icarus
support SV virtual interface?", #291 (2019-12-26) "Parameterized class
not supported" (GitHub search API, titles as returned). Fix: add the
three entries and cite them in the sentence, or say "two of them are
tracked issues".
