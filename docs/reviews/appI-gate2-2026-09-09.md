# Verdict

**Blocking findings remain.** Four.

The second pass did most of what the first review asked, and the parts it did
it did properly. Every named field in all four schemas now carries a
non-empty description, and the test that enforces it really descends into
`$defs`, `items` and `additionalProperties` — I removed a description from each
of those positions in turn and the walk caught all three. The sign-off caveat is
in the top-level `description`. All four JSON-printing commands are covered by
`schema.FOR_COMMAND` and validated by a test; `read`, the only command that
prints no JSON, is correctly excluded. The source locations are real, relative,
and right: `datapath.sv:14.3-22.6` is the `always_ff` that infers `acc` and
`count`, `datapath.sv:24.3-26.6` is the one that infers `last_cfg`, and the
per-bit fixture's eight instances are named `g_sync[0].u` through `g_sync[7].u`
exactly as the appendix says. The manual `I.n` prefixes are gone and the PDF now
numbers the appendix's sections once, B.1 through B.12, with no duplicate. The
four triage verdicts are two and a flag, and no sentence anywhere still promises
four. The pre-commit path was fixed too, so line 340's "checked on every commit"
is now true rather than aspirational.

What blocks is a smaller set, but three of the four are the same class the first
review was written to catch: a claim about this repository's own code that the
repository does not support, and a claim about the world that its own evidence
note forbids.

The most serious is **B-1**: the second pass carried `src` through into the
clock tree, the reset tree and every crossing — which is what `STATUS.md:96`
accurately records — but the appendix says "every report". The `connections`
report carries no source location at all, the `read` report prints none, and the
reset tree's headline finding, the `no_reset` list, is a bare list of names. So
the sentence that ends "a finding names the RTL that produced it" is false for
the one finding Chapter 3 makes its teaching point of. Worse, line 41 of the
same section still says the netlist road "has thrown the source-level tree away"
and lists source locations among the things only a syntax-tree front end
answers — which the second pass made untrue six lines later.

The thing I managed to break is **M-1**, below: I replaced `design._relative`
with a function returning the empty string, so that every cell in every report
lost its source location, and ran the suite. All 18 tests passed and all four
schemas validated. `src` is typed as a bare `"type": "string"`, so `""` and
`"not a location at all"` both conform, and no test asserts otherwise. The
grounding claim at line 47 — the appendix's most-quoted promise about its own
tools, and the thing the second pass changed the code to make true — is
protected by nothing.

Verified and re-run, needing no action: all 32 citation keys resolve against
`refs.bib`; all eleven `@sec-`/`@tbl-` targets exist; no `research/` or
`docs/specs/` path is cited; only four of the six permitted callout kinds appear

# 1. Blocking

## B-1. `appendices/appI-agent-tool-layer.qmd:47` — "into every report" is false, and line 41 contradicts it

> The book's own tools carry the source location Yosys records for each cell
> through into every report, so a finding names the RTL that produced it.

Run, not read:

```
$ python -m dvh crossings   top …/rtl/*.sv   # src on every crossing        ✓
$ python -m dvh clock-tree  top …/rtl/*.sv   # src on every register        ✓
$ python -m dvh reset-tree  top …/rtl/*.sv   # src on every reset register  ✓
                                             # no_reset: ["last_cfg"]       ✗
$ python -m dvh connections top …/rtl/*.sv   # 'src' not in the payload     ✗
$ python -m dvh read        top …/rtl/*.sv   # no location printed at all   ✗
```

`graph.connections` never touches `Cell.src`; `connections.schema.json` has no
`src` property anywhere. `clocks.reset_tree` puts `src` on every entry of
`registers` but `no_reset` is a plain array of strings
(`tools/dvh/schema/reset-tree.schema.json:62-68`), so the register the tool is
telling you about — the one the report exists to surface — is the one entry with
no pointer back to the RTL. `cli._report` prints no location in any of its lines.

Three of four JSON reports carry `src`; "every report" claims four of four plus
the human one. `STATUS.md:96` states the true scope ("in the clock tree, reset
tree and every crossing"); the appendix broadened it.

Second, and in the same section, `appendices/appI-agent-tool-layer.qmd:41`:

> This book's own tools take the cheaper one, an elaborated netlist, which
> answers structural questions and has thrown the source-level tree away. A
> syntax-tree front end answers those same questions and also the ones about
> types, expressions and source locations.

That sentence was written when the tools carried no `src`. It now contradicts
line 47 directly: source locations are on the list of things only the
syntax-tree road gives you, six lines before the claim that the netlist road
delivers them into every report. A reader who notices will not know which half
to believe.

One further precision worth having: a crossing's `src` is the *receiving*
register's location (`tools/dvh/clocks.py:295` uses `cell.src`, where `cell` is
the register at the `to` end). For `cfg_b -> acc` it is `datapath.sv:14.3-22.6`,
`acc`'s `always_ff`, not `cfg_b`'s. A crossing has two ends and the schema's
`"Source location, as file:line.col-line.col."` does not say which one it names.

**Proposed fix.** Either make the sentence exact:

> The book's own tools carry the source location Yosys records for each cell
> through into the clock tree, the reset tree and every crossing, so a finding
> names the `always_ff` block that produced it.

and add "carry `src` through the connection graph and the unreset-register list"
to the sequence at `@sec-appI-building`; or carry `src` through those two paths
and keep the sentence. Either way, correct line 41 so the two agree — the
netlist keeps a per-cell `src` span but not a source-level tree, so the
syntax-tree advantage is types, expressions and *expression-level* locations,
not locations as such. And name the end: `"description": "Source location of the
receiving register, as file:line.col-line.col."`.

## B-3. `appendices/appI-agent-tool-layer.qmd:39` — UVM field macros do not generate `do_compare`

> A text search for `do_compare` finds the implementations written by hand and
> none of the ones a field macro generated, and the generated ones are where a
> comparison silently includes a field nobody meant to compare.

The point is right; the mechanism named does not exist. `uvm_field_*` expand
inside `uvm_object_utils_begin` / `uvm_object_utils_end`, and what they generate
is the field-automation body — `__m_uvm_field_automation` in UVM 1.2, replaced by
`do_execute_op` under IEEE 1800.2-2020. `do_compare` is the *hand-written* hook:
`uvm_object::compare` runs the generated field automation and then calls
`do_compare`. So a grep for `do_compare` finds every occurrence there is, and
misses the generated comparison entirely — which makes the paragraph's argument
*stronger* than the sentence claims, not weaker.

This replaces the `run_phase` error the first review caught (6.2), and it is the
same kind of error: a correct point resting on a mechanism a verification
engineer will know is wrong. `STATUS.md:96` records the belief ("UVM field
macros generate `do_compare` not `run_phase`"), so the correction should land
there too.

**Proposed fix.**

> A text search for `do_compare` finds every hand-written hook and nothing at
> all for the field-by-field comparison the `uvm_field_*` macros generate —
> which lives in a method the macros write for you, is called before your hook
> runs, and is where a comparison silently includes a field nobody meant to
> compare.

# 2. Serious, not blocking

## M-1. The source-location claim is protected by neither a schema constraint nor a test

`src` is declared as a bare string in all three schemas that carry it
(`crossings.schema.json:70-73`, `clock-tree.schema.json:55-58`,
`reset-tree.schema.json:55-58`). Run:

```
empty src accepted:                          True
garbage src accepted:                        True
contradictory synchronized/reason accepted:  True
clock-tree cross-key mismatch accepted:      True
reset-tree contradiction accepted:           True
```

and then, with `design._relative` replaced at run time by `lambda s: ""` so that
every cell in every report loses its location:

```
18 passed in 0.20s
exit code with every source location blanked: 0
```

Nothing fails. A Yosys upgrade that stops emitting `src`, a `read_verilog`
invocation that omits it, or an exception swallowed inside `_relative` would
leave the appendix's grounding claim silently false with a green build. This is
the one place where the second pass changed the code to make a sentence true and
then left the sentence's truth untested.

**Proposed fix.** In each schema, `"src": {"minLength": 1, "pattern":
"^[^:]+:[0-9]+\\.[0-9]+-[0-9]+\\.[0-9]+"}` alongside the type; and one test
asserting that every register and every crossing carries a `src` naming a file
that exists, on the two-clock design. That is four lines and it turns the
appendix's most load-bearing claim about its own tools into something CI holds.

## M-2. `test_every_field_carries_a_description` has four blind spots

The walk (`tools/dvh/tests/test_ch03.py:251-265`) is real, not vacuous. I
mutated the four schemas in memory and re-ran it:

| Description removed from | Caught? |
|---|---|
| a top-level `properties` entry | yes — `crossings/crossings` |
| a `$defs` subschema's property | yes — `crossings/$defs/crossing/synchronized` |
| under `additionalProperties` | yes — `clock-tree/registers/additionalProperties/gated_or_muxed` |
| under `items` | yes — `reset-tree/no_reset/items/name` |
| the schema's own top-level `description` | yes — the separate `assert` at :269 |
| under `allOf` / `anyOf` / `oneOf` | **no** |
| under `patternProperties` | **no** |
| under `prefixItems` | **no** |
| a `description` set to `""` | **no** |

None of the four schemas uses `allOf`, `patternProperties` or `prefixItems`
today, so the test's guarantee holds as of this commit — but the sentence at
line 207 is a promise about the future ("if any field has been added"), and
those are the three keywords a field would plausibly be added under. The
empty-string hole is the cheapest to close and the most likely to be hit, since
`if "description" not in sub` passes on `""`.

**Proposed fix.** `if not sub.get("description")` instead of `if "description"
not in sub`, and extend the recursion list to
`("items", "additionalProperties", "contains", "propertyNames")` plus a loop
over `("allOf", "anyOf", "oneOf", "prefixItems")` and `patternProperties`.
