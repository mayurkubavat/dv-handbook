## 1. Blocking

### 1.1 The latch sentence now says the opposite of what the code does

`chapters/ch03-digital-design-for-verifiers.qmd:247`:

> Both walks stop at a latch, because a latch is a state element and walking
> through one would hide a crossing that lands on it.

The third pass changed the code to do the reverse. `tools/dvh/clocks.py:110`
opens `if cell.type in LATCH_TYPES and any_comb:` and walks the latch's `D`
inputs, prepending the latch cell type to `through`. The data walk does not
stop at a latch. Verified:

```systemverilog
// lat_through.sv -- a crossing through a latch and then through an adder.
module lat_through (input logic bclk, brst_n, cclk, crst_n, hold,
                    input logic [3:0] d_in, output logic [3:0] q_c);
  logic [3:0] src_b, lat;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) src_b <= 4'h0; else src_b <= d_in;
  always_latch if (hold) lat = src_b;
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) q_c <= 4'h0; else q_c <= lat + 4'h1;
endmodule
```

```
crossings: 1 unsync: 1
  src_b(bclk) -> q_c(cclk) w=4 direct=False 2nd=[] sync=False
```

The fix itself is good: the crossing is reported, and `direct=False` keeps it
out of the synchronizer class, which is the right classification. Only the
chapter was left behind. Worse, the chapter contradicts itself inside one
section: `:283` lists among the designs the tools once got wrong "one
through a latch that went unseen after the first fix", which is only true if
the walk no longer stops there.

The same false sentence is **printed twice**, because it is also the comment
above `LATCH_TYPES`, and `clocks.py` is spliced into the chapter at `:242`:

- `tools/dvh/clocks.py:29-30` — "Walking through one would hide a crossing
  that lands on it, so both walks stop here instead."
- `tools/dvh/clocks.py:111-113`, forty lines further down the same printed
  listing — "the crossing behind it is still a crossing, so the walk
  continues rather than stopping here."

A reader sees both. This is the third occurrence of the failure mode the
first two reviews named: the code changed, the sentence about the code did
not.

**Fix.** Replace `:247`'s last sentence with what the code does and what it
still cannot see, for example: "The clock walk stops at a latch, because a
latch is not a clock source. The data walk goes through one, because the
crossing behind it is still a crossing, though the path is no longer direct
and so cannot be a synchronizer. What neither walk sees is a crossing that
*lands* on a latch: latches are not in `registers()`, so they are never a
destination, and that is a blind spot rather than a decision." Then correct
`tools/dvh/clocks.py:29-30` to match `:111-113`.

The landing case is real and currently silent:

```systemverilog
// lat_lands.sv -- the crossing lands on the latch itself.
module lat_lands (input logic bclk, brst_n, cclk, crst_n, hold, d_in,
                  output logic q_lat, output logic q_c);
  logic src_b;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) src_b <= 1'b0; else src_b <= d_in;
  always_latch if (hold) q_lat = src_b;
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) q_c <= 1'b0; else q_c <= 1'b1;
endmodule
```

reports `crossings: 0 unsynchronized: 0`, exit 0.

### 1.2 The shared-clock-root rule silently drops real crossings

This is the most serious thing in this review: the third pass introduced a
rule that turns a reported crossing into no crossing at all, and the chapter
introduces that rule as the thing that makes the ambiguous case safe.

`chapters/ch03-digital-design-for-verifiers.qmd:240`:

> What saves the report in that case is a second rule. Two domains that share
> a clock root are the same clock gated two ways, so a path between them
> raises a timing question rather than a metastability one, and it is not
> reported as a crossing.

`tools/dvh/clocks.py:280` implements it as a set intersection over the
domain *name*:

```python
if set(theirs.split("+")) & set(mine.split("+")):
    continue
```

A domain name is `"+".join(clock_sources)`, and in the ambiguous case
`clocks.py:141-144` deliberately keeps *every* tied input, so the enable is
in the name. The rule therefore treats two genuinely asynchronous clocks as
one clock whenever they share a gating enable. A shared global
power-saving enable is an ordinary design:

```systemverilog
// shared_en_gate.sv -- two asynchronous clocks, one global enable gating
// both. No register runs on a bare clock. There is a real unsynchronized
// one-bit crossing from the bclk side to the cclk side.
module shared_en_gate (input logic bclk, cclk, rst_n, run, d_in,
                       output logic q_c);
  logic gb, gc, d_b;
  assign gb = bclk & run;
  assign gc = cclk & run;
  always_ff @(posedge gb or negedge rst_n)
    if (!rst_n) d_b <= 1'b0; else d_b <= d_in;
  always_ff @(posedge gc or negedge rst_n)
    if (!rst_n) q_c <= 1'b0; else q_c <= d_b;
endmodule
```

`python -m dvh read shared_en_gate shared_en_gate.sv`:

```
clock domains: 2
  bclk+run: 1 registers
  cclk+run: 1 registers
registers without reset: 0
crossings: 0, unsynchronized: 0
```

Exit 0. A build gates green on an unsynchronized asynchronous crossing.

The second case is the one the brief asked for by name, and it fails the
same way. A clock mux between two genuinely asynchronous sources:

```systemverilog
// mux_clk.sv -- a clock mux between two asynchronous sources, with
// registers on each source as well. q_a -> q_m is a real crossing whenever
// the mux points at clkb.
module mux_clk (input logic clka, clkb, rst_n, sel, d_in,
                output logic q_a, q_b, q_m);
  logic mclk;
  assign mclk = sel ? clka : clkb;
  always_ff @(posedge clka or negedge rst_n)
    if (!rst_n) q_a <= 1'b0; else q_a <= d_in;
  always_ff @(posedge clkb or negedge rst_n)
    if (!rst_n) q_b <= 1'b0; else q_b <= d_in;
  always_ff @(posedge mclk or negedge rst_n)
    if (!rst_n) q_m <= 1'b0; else q_m <= q_a;
endmodule
```

```
clock domains: 3
  clka: 1 registers
  clka+clkb: 1 registers
  clkb: 1 registers
crossings: 0, unsynchronized: 0
```

Exit 0. The muxed domain shares the token `clka` with `q_a`'s domain, so the
path is discarded. This contradicts the chapter's own physics twice: `:63`
("A multiplexed clock can hand the same node the timing of either input, so
it may genuinely create a new domain") and Summary bullet `:297` ("A gated
clock keeps its source's domain; a multiplexed clock may not").

Both misses are caused by that one line, not by anything older. Re-running
both designs with `clocks.py:280-281` disabled and nothing else changed:

```
shared_en_gate  WITHOUT shared-root rule -> crossings: 1 unsync: 1
    d_b bclk+run -> q_c cclk+run  synchronized=False
mux_clk         WITHOUT shared-root rule -> crossings: 1 unsync: 1
    q_a clka -> q_m clka+clkb     synchronized=False
```

Both were reported before the third pass and are silent after it. The
fixture `two_clock_gates.sv` is the one shape where the rule is right
(`crossings: 0` there is correct), and it is the only shape it was tested
on.

**Fix, code.** The rule needs a notion of clock root that the enable cannot
enter. Two workable forms:

- Suppress only when the two domains' *clock-carrying* sources are equal,
  keeping ambiguous or muxed sources out of the comparison. Concretely,
  record the followed roots separately from the tied/ambiguous ones and
  compare only the former, and never suppress when either domain is marked
  ambiguous or reached through a `MUX_TYPES` cell.
- Or restrict the suppression to the unambiguous gated case: suppress when
  one domain's source set is a subset of the other's *and* neither carries
  the `ambiguous` marker.

**Fix, text.** `:240` cannot stand as written either way. If the rule is
narrowed, say what it is narrowed to. If it is not, say that the tool cannot
distinguish a shared clock from a shared enable and will drop a crossing on
that account — which, given `:260` ("the tool exits non-zero on them, so a
build can gate on it") and `:286` ("derive ... on every commit"), the reader
has to be told.

### 1.3 The convergence rule is defeated by a three-flop synchronizer

`chapters/ch03-digital-design-for-verifiers.qmd:251`:

> the tool looks for two or more recognized synchronizers that some register
> downstream reads *together*, and rejects the group

`_flag_converging_synchronizers` (`tools/dvh/clocks.py:218-247`) does not do
that. It builds `stages` from `c["second_stage"]` only
(`clocks.py:235-237`), so the register that must do the reading is one that
reads the **immediate second stages**. Any register further downstream reads
nothing the rule can see. One extra flop per bit — a three-flop
synchronizer, which is a recommended structure, not a contrivance — walks
straight past, on the chapter's own anti-pattern with the chapter's own
single declared sending vector:

```systemverilog
// per_bit_3ff.sv (abridged; the eight blocks are identical)
module per_bit_3ff (input logic bclk, brst_n, cclk, crst_n,
                    input logic [7:0] cfg_in, output logic [7:0] acc);
  logic [7:0] cfg_b, m1, m2, m3;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) cfg_b <= 8'h00; else cfg_b <= cfg_in;
  always_ff @(posedge cclk or negedge crst_n)      // x8, one per bit
    if (!crst_n) begin m1[0] <= 1'b0; m2[0] <= 1'b0; m3[0] <= 1'b0; end
    else begin m1[0] <= cfg_b[0]; m2[0] <= m1[0]; m3[0] <= m2[0]; end
  // ... bits 1..7 the same ...
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) acc <= 8'h00; else acc <= acc + m3;
endmodule
```

`python -m dvh read per_bit_3ff per_bit_3ff.sv`:

```
crossings: 8, unsynchronized: 0
  ok   cfg_b (bclk) -> m1[0] (cclk), 1 bit, synchronizer
  ...eight of these...
```

Exit 0. Eight bits of one value cross bit by bit, are reassembled into `m3`
and consumed as one eight-bit value by `acc` — "a complete loss of data" in
the words the chapter quotes at `:93` — and the tool signs it off. `acc` *is*
"some register downstream" that reads all eight "together", so `:251` is a
false claim about the code, not merely an incomplete one.

Note what this is not: it is not the fixture's shape with the sending flops
renamed. It is the fixture's shape with the sending vector left exactly as it
is and one flop added per chain. The committed fixtures
(`per_bit_sync.sv`, `split_source_sync.sv`) both use two-flop chains.

**Fix, code.** Follow the recognized chain forward rather than stopping at
the second stage: mark every register transitively reachable from a
recognized crossing's second stage within the destination domain as carrying
that crossing's value, then look for a register whose data cone reads two or
more distinct crossings' values. A bounded forward closure over
`_feeds_directly` from each second stage is enough to catch the three- and
four-flop forms.

**Fix, text.** Whatever the code ends up doing, `:251` must describe it and
not more than it. If the closure is bounded, say the bound.

## 2. Non-blocking findings against the code

### 2.1 The convergence rule produces false positives on correct designs

The rule does not require the converging crossings to come from the same
sending domain, or from the same value, or to have any coherency
requirement at all. Two ordinary designs are rejected:

```systemverilog
// indep_errs.sv -- two INDEPENDENT one-bit sticky error flags, each
// correctly synchronized, OR-ed into one status flop.
module indep_errs (input logic bclk, brst_n, cclk, crst_n,
                   input logic parity_err, timeout_err,
                   output logic any_err);
  logic p_b, t_b, p_m, p_s, t_m, t_s;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) begin p_b <= 1'b0; t_b <= 1'b0; end
    else begin p_b <= parity_err; t_b <= timeout_err; end
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) begin p_m <= 1'b0; p_s <= 1'b0; end
    else         begin p_m <= p_b;  p_s <= p_m;   end
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) begin t_m <= 1'b0; t_s <= 1'b0; end
    else         begin t_m <= t_b;  t_s <= t_m;   end
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) any_err <= 1'b0; else any_err <= p_s | t_s;
endmodule
```

reports two `BUG` findings, "2 one-bit synchronizers are read together by
any_err", exit 1. `two_src_domains.sv` (same shape, but the two sources are
in two *different* clock domains, so the bits could not be coherent under
any implementation and nothing asks them to be) reports the same two
findings. A status or interrupt aggregation register makes this a common
shape.

The chapter is honest about the direction in general terms at `:266` ("it
will flag a right one whose shape it does not know"), so the prose is not
false. The **printed comment is**: `tools/dvh/clocks.py:227-229` says
grouping by name "would wrongly flag two unrelated controls that happen to
share one declared vector", presenting convergence as the cure. Convergence
cures that exact shape — `indep_bits.sv`, the previous review's §8.3 case,
now correctly reports `crossings: 2 unsync: 0` — and introduces a different
false positive of the same kind.

**Fix.** Require the converging crossings to share a `from_domain` before
demoting, which removes `two_src_domains` outright and narrows `indep_errs`,
and extend the comment at `clocks.py:227-229` to say that a register
aggregating independent synchronized controls is flagged and is not
distinguishable from a bus.

### 2.2 A divided clock still yields a `BUG` on a synchronous path

```systemverilog
// div_clk.sv -- a divide-by-two. q_fast and q_slow are synchronous.
module div_clk (input logic clk, rst_n, d_in, output logic q_fast, q_slow);
  logic clk_div;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) clk_div <= 1'b0; else clk_div <= ~clk_div;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) q_fast <= 1'b0; else q_fast <= d_in;
  always_ff @(posedge clk_div or negedge rst_n)
    if (!rst_n) q_slow <= 1'b0; else q_slow <= q_fast;
endmodule
```

```
  BUG  q_fast (clk) -> q_slow (clk_div), 1 bit, no synchronizer
```

Exit 1. The shared-root rule does not fire because the domain names are
`clk` and `clk_div` and share no token — the same string comparison that is
too loose in §1.2 is too tight here. Raised as §8.2 of the previous review;
the chapter still does not list it, while `:260` and `:286` propose gating a
build and a commit on the exit code.

**Fix.** Either make the root comparison structural (a divided clock's root
is its own clock's root, which `clock_candidates` already knows: `clk_div`
is in `strong` because its `Q` drives a clock pin) or add one sentence to
`:240` or the Future Directions box naming derived clocks — dividers, muxes,
black-box outputs — as producing findings that are not bugs.

### 2.3 `$dffsr` resets are still reported as constants

Unchanged from §5.8 of the previous review. `clocks.py:185` picks
`"ARST" if "ARST" in cell.conns else "CLR"` and never examines `SET`, and
the reset walk skips a multiplexer's select, which is where a `$dffsr`'s
real reset sources sit.

```systemverilog
module dffsr_reset (input logic clk, set0, clr1, input logic [1:0] d,
                    output logic [1:0] q);
  always_ff @(posedge clk or posedge set0 or posedge clr1)
    if (set0)      q <= 2'b01;
    else if (clr1) q <= 2'b10;
    else           q <= d;
endmodule
```

```
rst q: asynchronous active-high sources=['const 0', 'const 1']
       through=['$mux', 'mux']
```

Neither `set0` nor `clr1` appears. A verifier reading that report learns
the register is asynchronously reset by constants, which is false. No
chapter sentence asserts otherwise, which is why this is not blocking, but
`:236` ("the split between them is what lets the reset walk report a kind
and a polarity rather than a guess") sits close to it.

**Fix.** The previous review's suggestion is still the safe one: detect
`$dffsr`/`$dffsre` in `reset_tree` and record the kind as unclassified with
a reason, rather than reporting a source list the walk did not establish.

### 2.4 The ambiguity marker never reaches the printed report

`chapters/ch03-digital-design-for-verifiers.qmd:240` — "Where the evidence
ties, the walk says so rather than choosing." It says so in the JSON, in
each register's `through` list ("ambiguous: clock not distinguishable
here"). `cli._report` (`tools/dvh/cli.py:27-49`) prints domain names and
counts and never prints `through`, so the `read` output the chapter typesets
at `:255` would not show it. On `one_gate_only.sv` (a single fully gated
block, no register on the bare clock) the whole report is:

```
clock domains: 1
  clk+en: 2 registers
registers without reset: 0
crossings: 0, unsynchronized: 0
```

Nothing there tells the reader the tool could not tell the clock from the
enable. **Fix.** Print one line per ambiguous domain in `_report`, e.g.
`  note: clk+en -- clock not distinguishable from enable here`, and pin it in
`test_ch03.py` alongside the existing report text.

### 2.5 A tool crash and a found crossing exit the same way

`design.py:90-91` runs Yosys with `check=True, capture_output=True`, so a
bad top-module name or a missing file raises `CalledProcessError`, prints a
Python traceback, discards Yosys's own diagnostics, and exits 1 — the same
code `read` uses for "unsynchronized crossings found". A build gate of the
kind `:260` and `:286` propose cannot tell the two apart.

**Fix.** Catch `CalledProcessError` in `cli.main`, print the captured stderr,
and exit 2 (which `_emit` already uses for a schema failure).

## 3. What the third pass did fix

Confirmed on designs written for this review, not on the fixtures:

- **Crossings through a latch are reported** (§1.1), and are correctly *not*
  classified as synchronizers: `lat_sync_shape.sv`, a latch sitting in the
  first-stage position of an otherwise perfect two-flop chain, reports
  `direct=False, sync=False`. The one thing the fix leaves invisible is a
  crossing that lands on a latch.
- **A clock out of a black box is a primary clock.** `pll_clk.sv` (an
  analog `(* blackbox *)` PLL feeding registers directly) gives one domain
  per clock and one true crossing; `pll_gated.sv` (the PLL output gated two
  ways, with no register on the bare PLL output) gives **one** domain and no
  false `BUG`. The previous review's §5.1 second case is closed, and the
  code now implements the whole of the chapter's Definition at `:56`.
- **A latch-based glitch-free clock gate** — the structure the chapter
  recommends at `:63` — gives one domain `clk` with
  `through=['$and', 'gated by en_lat']`. No `$dlatch` string leaks into a
  domain name.
- **A single fully gated block** gives one domain and no false `BUG`
  (`one_gate_only.sv`), and two gates on one clock give no crossing. The
  previous review's §5.1 first case is closed — by the rule that §1.2 shows
  is too broad, but closed.
