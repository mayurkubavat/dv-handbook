## 2. The technical corrections: right, or merely different?

### 2.1 The X semantics are now correct — confirmed by construction

The first review's blocking finding was that "an `if` whose condition is unknown
takes neither branch" is true only of a bare `if`. The second pass rewrote both
the prose (149) and the example. Both are now right. Checked with a purpose-built
case under Icarus rather than by reading:

```
bare if            : 111  (111 = kept old value)
if/else            : 238  (238 = else branch ran)
case w/ default    : 99   (99 = default taken)
case w/o default   : 111  (111 = nothing ran)
case w/ 1'bx item  : 77   (77 = x item matched, not default)
arith  x+1         : xxxxxxxx
bitwise x&1        : x
logical x||1       : 1    (1 = NOT propagated)
bitwise x|1        : 1    (1 = NOT propagated)
```

Every clause of line 149 holds. Two things the pass got right that are easy to
get wrong and worth recording so they are not "fixed" later:

- Line 147's hedge, "Arithmetic and bitwise operators **generally** propagate
  it", is doing necessary work: `x | 1` is 1 and `x & 0` is 0. Do not remove
  "generally".
- The example's `out_bare`/`out_else` split (`dut_unreset.sv:26–31`) reproduces
  the distinction with one reader of each kind, exactly as the brief said.

The primary source agrees, in as many words. Sutherland 2013 §3, Example 5:
"should the control condition evaluate to unknown, the else branch is executed."
The chapter is not merely different from the first draft; it is right.

**F-2.1 (non-blocking).** `chapters/ch04-simulation-fundamentals.qmd:149`. The
chapter draws the with-else / without-else distinction carefully for `if`, then
drops it for `case`: "A `case` on an unknown selector takes its `default` for the
same reason." Without a `default` nothing executes and the target keeps its old
value — the exact parallel to the bare `if`, and the cited source states it
(Sutherland 2013 §3.2: a case statement without a default branch "retains its
previous value"). *Fix:* mirror the `if` sentence — "…takes its `default`, or, if
it has none, does nothing, for the same reason."

### 2.2 The Reactive region is now described correctly

Line 46 and the table row at 58 both say the Reactive region set holds `program`
code and assertion action blocks, and that an ordinary module testbench runs in
Active alongside the design. That matches the evidence record exactly
(`research/ch04-simulation-fundamentals.md:332–352`): the Reactive set schedules
"the blocking, `#0` blocking and non-blocking assignments in program code, plus
any task or function called from a program", and Reactive itself executes "the
pass/fail code from concurrent assertions". The note is equally explicit on the
trap the first review caught (`:340–342`): assertion action blocks do **not** run
in Observed — "they schedule a process into Reactive". The correction is right,
not merely different.

This could not be confirmed by running: neither shipped simulator implements the
Reactive region set (Verilator implements Active and NBA only; Icarus's `program`
support does not extend to observable region ordering). It is confirmed against
the primary source only, which is the honest position and is what the chapter's
own line 39 claims for the section.

**B1 (blocking).** `chapters/ch04-simulation-fundamentals.qmd:41`, repeated at
`:229`.

> Three regions do the design's work. **Then assertions sample and evaluate.**
> Then the same three regions repeat for the testbench. Then everything settles.

Sampling does not happen there. Preponed runs **first in the time slot**,
immediately after time advances, before any Active-region work — the chapter's
own table puts Preponed at the top eight lines later, and its own line 137 says
the values an assertion sees are sampled "before anything in the timestep has
run". Only *evaluation* (Observed) sits between the Active set and the Reactive
set. As written, the shape the chapter offers as the memorable version of the
model teaches the wrong order for the one region a verification engineer most
needs to place, and the reader meets the contradiction two lines later.

The Summary repeats it verbatim at `:229`: "three for the design, then assertion
sampling and evaluation, then the same three for the testbench".

*Fix:* split sampling from evaluation in both places. For instance, at 41:
"Sampling happens first, before anything runs. Then three regions do the design's
work. Then assertions are evaluated on the values sampled at the top. Then the
same three regions repeat for the testbench. Then everything settles." And at
229: "…assertions are sampled before it starts and evaluated after the design's
three regions…". Note this is *not* the research note's purpose-grouping
(`:269–275`), which is a grouping by what each region is for and is explicitly
not an ordering; the chapter presents it as an ordering ("Then … Then … Then").

### 2.3 B4: what the regions decide, and what the value set decides

`chapters/ch04-simulation-fundamentals.qmd:72`

> What is stable is everything the regions decide: the non-blocking target still
> reads as **unknown** in Active, and `$strobe` sees it updated.

The sentence exists to separate what is guaranteed from what is arbitrary, and it
puts the wrong item on the guaranteed side. Running the same `tb_regions.sv`
under this book's other simulator:

```
$ verilator --binary --timing --timescale 1ns/1ps --top-module tb_regions tb_regions.sv
one timestep, printed from several places:
  [active]    just assigned a=1 with =
  [active]    just assigned b<=1, b is still 0        <-- 0, not x
  [postponed] $strobe sees b=1, after the update
  [next step] a=1 b=1
```

Two things happen here at once. The Active lines swap, which is what the
paragraph predicts and is a genuine confirmation of it. And `b` reads **0**, not
unknown — because a two-state simulator has no unknown to read. What the region
guarantees is that the read sees the value *from before the update*; that the
before-update value is unknown is decided by the value set, which is the subject
of @sec-ch04-fourstate and not of the regions at all.

This matters more than a wording slip because the chapter is at that moment
teaching the reader how to tell a guarantee from an accident, and it is a
conflation the chapter elsewhere is careful about.

*Fix:* "…the non-blocking target still reads as its pre-update value in Active,
and `$strobe` sees it updated." One clause, and the sentence becomes true under
both simulators. Optionally add that under this book's four-state simulator that
pre-update value happens to be unknown, which is @sec-ch04-fourstate's subject.

### 3.1 The second-hand trap, checked specifically

The brief asks for a paraphrase of standard text at one remove. Two candidates
were examined and both come out clean, but the second is close enough to record.

**The Definition at line 28** is the one the note warns about most directly,
because Cummings and Salz's definition of *simulation time* is itself lifted from
a draft of the standard, while their definition of *timestep* is their own and is
safe (`research/…:63–69, 205–216`). The chapter defines **timestep** — "all the
work a simulator does at one value of simulation time" — and then states the
drain rule. Both track the authors' own exposition (the note: "all activity for a
given simulation time executes until no further activity remains for that
timestep, *without advancing simulation time*"), not the borrowed definition. The
chapter never defines *simulation time* at all. Clear, and deliberately so.

**Line 91** is the closer call. The source sentence is itself a report of the
standard:

> "The Verilog and SystemVerilog standards state that all procedural blocks,
> regardless of their type, become active at time zero, and in any order.
> Verilog initial blocks have no precedence over always blocks…"
> — Sutherland, Mills and Spear 2006, p. 38 (verified in the fetched PDF)

The chapter renders it as "At time zero, `initial` and `always` blocks activate
in any order, with no precedence between them." That is standard content at two
removes, and the phrase "in any order" survives intact. It is **not** a
violation: it is a rule of the language, not clause text; the source presents it
as its own exposition rather than as a block quotation; and the research note
explicitly recommends this content and paraphrases it the same way
(`research/…:605–617`). Recorded so a later pass does not rediscover it as new.

### 3.2 Constraint 11 remains soft (non-blocking, carried from the first review)

`chapters/ch04-simulation-fundamentals.qmd:137`

> A concurrent assertion's expression is sampled in Preponed, before anything in
> the timestep has run…

The word "must" is absent, so the constraint is not broken. But the note's reason
for the constraint is stronger than the word: Preponed and the previous slot's
Postponed are both read-only and carry identical values, so "it is not observable
in which region the simulator actually samples a value" (`research/…:977–980`).
The chapter states it as observed mechanism.

*Fix (optional, one clause):* "…is sampled in Preponed — in the model; a
simulator only has to behave as if it were…". Left non-blocking because the
chapter is explicitly teaching the model, and line 182 already tells the reader
the model is not what a simulator does.

## 5. B2, B3, and everything else

### 5.1 B2 (blocking): the timescale paragraph states a false cause

`chapters/ch04-simulation-fundamentals.qmd:178`

> This chapter's own examples make the point against themselves. None of them
> declares a timescale, so the event-driven simulator reports its finish time in
> seconds while the other runs at nanoseconds, which is visible in the output
> printed earlier in this chapter.

Three problems, one of them fatal to the sentence.

**The cause is wrong.** Every Verilator invocation in this chapter's examples
passes `--timescale 1ns/1ps` explicitly:

- `examples/ch04-simulation/fourstate/run.sh:18` and `:24`
- `examples/ch04-simulation/fourstate/Makefile:7`
- `examples/ch04-simulation/race/run_both.sh:16`
- `examples/ch04-simulation/race/lint_both.sh:13`

The statically scheduled simulator runs at nanoseconds because the build *tells
it to*, not because no source declares a timescale. The sentence's "so" is false.

**The counterfactual is also wrong.** With the flag removed, Verilator does not
fall back to nanoseconds — it defaults to **1ps/1ps**:

```
$ verilator --binary --timing --top-module ts ts.sv    # no --timescale
Time scale of ts is 1ps / 1ps
- Verilator: $finish at 5ps

$ verilator --binary --timing --timescale 1ns/1ps ...
Time scale of ts is 1ns / 1ps
- Verilator: $finish at 5ns
```

The chapter's own evidence record already says this: "defaulting to **1ps/1ps**
to match SystemC" (`research/…:1211–1213`). So the paragraph contradicts the note
it was written from, in the one section whose subject is that a timescale mistake
produces a plausible answer rather than a broken one.

**"Visible in the output printed earlier" is not true of the second half.** The
`(1s)` from Icarus is visible, in the `regions` and `sampling` blocks. But the
`race` example is the only one that runs the statically scheduled simulator, and
its `run.out` is filtered to `^(design|count)=` (`race/run_both.sh:15, 20`), so
it prints no time at all. Nothing anywhere in the chapter shows that simulator's
time units.

*Fix.* Either state the true cause — "None of them declares a timescale in
source, so the event-driven simulator falls back to seconds while the build
supplies `--timescale 1ns/1ps` to the other; two tools, two different answers to
the same missing declaration, which is exactly the failure this section
describes" — or drop the second simulator from the sentence and keep only the
`(1s)` that the printed output actually supports. The first is the better
chapter: it is a *stronger* instance of the section's point, since it shows the
missing declaration being papered over by a build flag nobody reading the source
would see.

### 5.2 B3 (blocking): a borrowed sentence, bolded rather than quoted

`chapters/ch04-simulation-fundamentals.qmd:44`

> The **Reactive region set is the dual of the Active region set**.

This is Cummings and Salz's own sentence. The evidence record is unambiguous
about that: "The structural insight the chapter should lead with is the authors'
own: the **Reactive region set is the testbench dual of the Active region set**
… and the authors state it in exactly those terms" (`research/…:279–286`). The
chapter drops one word and sets the rest in bold as the chapter's organizing
idea, with no quotation marks and no citation on the line.

The house rule is explicit: "Direct quotation is limited to a sentence or two, in
quotation marks, with the citation on the same line." The blanket attribution at
line 39 ("the account here follows Cummings and Salz, whose paper is the source
for everything in this section") covers the *account*; it does not convert a
verbatim sentence into a paraphrase. And the second pass demonstrably knows how
to do this correctly — at line 134 it quotes "surprisingly error-prone" with the
citation on the line. The same treatment is owed here, one section earlier.

*Fix:* `The Reactive region set is, in Cummings and Salz's words, "the testbench
dual of the Active region set" [@cummingssalz2007events].` The bold can stay on
the surrounding claim; it should not be on borrowed words presented as the book's
own formulation.

### 5.6 Clarity for a first-year DV engineer

The chapter is, overall, unusually clear for its subject, and the second pass
improved it. The opening (17–19) is the best motivation in the book so far, and
the "which region is this in?" Pitfall at 115 is the single most useful paragraph
for a new engineer. The findings below are small.

**F-5.6a — the eight guidelines, presented as seven rows.** `:95` promises "the
eight guidelines", the table (97–104) has six rows, and `:106` adds a seventh as
a corollary. The missing one is not missing: row 3 silently merges Cummings' #2
(latches) and #4 (mixed sequential and combinational), which is a legitimate
merge — they share a region and a reason. But a reader who counts finds seven of
eight and cannot tell whether something was dropped. *Fix:* a half-clause on row
3, "(two of the eight, sharing a region and a reason)", or "eight guidelines,
grouped here into seven rows".

**F-5.6b — `safe.sv` is spliced after the output that reports on it.** The order
on the page is `racy.sv` (198) → `run.out` (203), which contains *both* the racy
and the safe results and the "agree on safe" verdict → `safe.sv` (208). The
reader is told what the fixed design does before being shown it. *Fix:* move the
`safe.sv` include above the `run.out` include, or split `run.out` — but the
splice must stay whole-file, so moving the listing is the cheaper fix.

**F-5.6c — "across ten thousand seeds" where there are no seeds.** `:160`:
"Starting every register at zero says nothing at all: both readers give a
plausible answer, and would across ten thousand seeds." With a fixed zero
initialization there is no seed to vary; ten thousand runs are one run repeated.
The sentence means the right thing and says a confusing thing next to a paragraph
whose *other* two models genuinely do vary with a seed. *Fix:* "…and would on
every run, because there is nothing for a seed to change."

**F-5.6d — the third block shows one reader where the text promises two.** `:153`
sets up "an unreset register read two ways … One reader uses a bare `if`; the
other adds an `else`", and `:160` then discusses all three initialization models.
But the randomized block in `run.out` prints only the bare-`if` reader —
`fourstate/run.sh:31` filters with `grep -E '^bare'`. Not a false claim, but the
reader looking for the `if/else` column in the third block will not find it and
has no way to know it was filtered rather than absent. *Fix:* either widen the
filter to `'^(bare|if/else)'` and re-capture, or add a clause: "reported here for
the bare reader only, since under two-state both readers vary the same way."
