**Verdict: blocking findings remain.**

Headline, answering question (1):

* **A clock on a multiplexer's select pin is never examined, declared or
  not.** The clock walk skips `S` at every multiplexer
  (`tools/dvh/clocks.py:245-252`), and under a declaration the selection is
  "undecided only where its inputs depend on different clocks"
  (`clocks.py:264-269`). So `clk2 ? clk1 : ~clk1` -- which is clk1 XNOR
  clk2, the blend `gate2h` §1.1(c) wrote as `~^` -- has two inputs that
  both depend on clk1, is not undecided, resolves to clk1's net, and the
  eight-bit crossing onto it is "one clock gated differently". Exit 0 with
  `--clock clk1 --clock clk2`, a declaration that is complete and correct
  by every check the tool has. The same shape passes with the select a
  black-box (PLL) output, and with the select a register in the other
  clock domain, which the chapter at `:63` calls a crossing in its own
  right. §1.1. Four designs.
* **A register's asynchronous set, clear or load pin is not a clock
  dependency.** `clock_deps` follows a register's `CLK` and nothing else
  (`clocks.py:166-169`), so a flag set asynchronously by clk2's edge and
  cleared by clk1 "depends on clk1", is control at `clk1 & flag`, and the
  register behind the gate lands on clk1's net. Exit 0, both clocks
  declared. §1.2. Two designs (`$adff`, `$aldff`).

Sentences the chapter prints about the tool that are false of the code are
collected in §1.3, with line numbers.

Every design quoted in `gate2h` was re-created and re-run (§2). Its three
blocking findings, all five serious findings and the three minor findings
are fixed, with two qualifications: the deep *clock* cone still ends in
`RecursionError`, exit 2, declared and undeclared, which `gate2h` §3.1
listed as serious and this round keeps as serious (§3.2); and the defense
`gate2h` §3.4 accepted for a hidden clock -- the list of ports read as
gating control -- does not fire when the hidden clock reaches the gate
through a register (§3.1).

## 1. Blocking

### 1.1 A multiplexer's select is never asked which clock it depends on

`_walk_to_sources` at a multiplexer, clock walk (`tools/dvh/clocks.py:245-252`):

```python
# A multiplexer's select is not a clock, so the clock walk skips it.
# A data cone must follow it: a foreign register steering a mux is a
# crossing like any other.
skip_select = not any_comb and cell.type in MUX_TYPES
ins = [(port, b) for port, bits in cell.conns.items()
       if cell.dirs.get(port) == "input"
       and not (skip_select and port == "S")
       for b in bits]
```

Everything after that line -- the undecided test at `:268-269`, the
`direct`/`have` classification at `:280-299` -- runs over `ins`, which has
no `S` in it. The select is never classified as clock, control or unknown;
it simply does not exist to the walk. "A multiplexer's select is not a
clock" is an assumption about the design, and it is the assumption a
blend written as a selection breaks.

**(a) A blend written as a selection.** `clk2 ? clk1 : ~clk1` is
`~(clk1 ^ clk2)`. `gate2h` §1.1(c) wrote the same function as `clk2 ~^ pol`
and it now fails correctly (§2); written as a `$mux` it passes.

```systemverilog
// muxsel.sv -- a blend written as a selection whose *select* is the second
// clock. `clk2 ? clk1 : ~clk1` is clk1 XNOR clk2, a blend of two clocks.
// Both clocks are ports, both drive clock pins directly, both are declared.
module muxsel (input logic clk1, clk2, input logic [7:0] d,
               output logic [7:0] q, output logic t);
  logic mclk, tog;
  logic [7:0] a, b;
  assign mclk = clk2 ? clk1 : ~clk1;       // = ~(clk1 ^ clk2)
  always_ff @(posedge clk1) a <= d;        // clk1 domain
  always_ff @(posedge mclk) b <= a;        // 8 bits, no synchronizer
  always_ff @(posedge clk2) tog <= ~tog;   // clk2 clocks registers too
  assign q = b;
  assign t = tog;
endmodule
```

`through` names `$mux` and `$not` and nothing else: clk2 left no trace.
Undeclared the same design exits 1 (`clk1#2 -> clk1#23`, no excuse
without a declaration), so following the report's advice to declare the
clocks turns a finding into a pass, which is `gate2h` §1.1's shape again
by a different route.

**(b) A bypass multiplexer whose select is the second clock.**
`clk2 ? clk1 : (clk1 & en)` is `clk1 & clk2` whenever `en` is low.

```systemverilog
// muxgate.sv -- a bypass multiplexer whose select is the second clock:
// `clk2 ? clk1 : (clk1 & en)`. With en low this is clk1 & clk2, a blend.
module muxgate (input logic clk1, clk2, en, input logic [7:0] d,
                output logic [7:0] q, output logic t);
  logic gclk, mclk, tog;
  logic [7:0] a, b;
  assign gclk = clk1 & en;
  assign mclk = clk2 ? clk1 : gclk;
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge mclk) b <= a;        // 8 bits, no synchronizer
  always_ff @(posedge clk2) tog <= ~tog;
  assign q = b;
  assign t = tog;
endmodule
```

`b`: `"through": ["$and", "$mux", "gated by en", "mux"]`. The report names

**(c) The select is a black-box clock.** `gate2h` §1.1 established that an
opaque net "is never control" (`clocks.py:277-279`); on a select pin it is
never anything.

```systemverilog
// muxpll.sv -- a bypass multiplexer whose select is a black-box output.
(* blackbox *)
module pll (input logic ref_clk, output logic clk_out);
endmodule
module muxpll (input logic clk1, ref_clk, en, input logic [7:0] d,
               output logic [7:0] q, output logic t);
  logic pclk, gclk, mclk, tog;
  logic [7:0] a, b;
  pll u_pll (.ref_clk(ref_clk), .clk_out(pclk));
  assign gclk = clk1 & en;
  assign mclk = pclk ? clk1 : gclk;
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge mclk) b <= a;
  always_ff @(posedge pclk) tog <= ~tog;
  assign q = b;
  assign t = tog;
endmodule
```

**(d) The select is a register in the other clock domain.** This is the
ordinary bypass multiplexer of `gate2h` §3.3 with its mode bit registered
on the other clock. The chapter at `:63` says "The gating enable is itself a
crossing: gating signals are synchronized precisely to eliminate clock
glitches when a domain switches clocks", and at `:251` that "a foreign
register steering a multiplexer is a control crossing like any other" --
of the *data* walk. On a clock multiplexer nobody follows it.

```systemverilog
// muxreg.sv -- a bypass multiplexer around a clock gate, selected by a
// register in the *other* clock domain. Both clocks declared.
module muxreg (input logic clk1, clk2, en, m, input logic [7:0] d,
               output logic [7:0] q);
  logic gclk, mclk, mode;
  logic [7:0] a, b;
  always_ff @(posedge clk2) mode <= m;     // clk2-domain control
  assign gclk = clk1 & en;
  assign mclk = mode ? clk1 : gclk;        // steered from clk2
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge mclk) b <= a;
  assign q = b;
endmodule
```

```
$ dvh read muxreg muxreg.sv --clock clk1 --clock clk2
clock domains: 3
  clk1#2: 1 registers
  clk1#23: 1 registers
  clk2: 1 registers
ports treated as gating control: en
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (clk1#2) -> b (clk1#23), 8 bits, no synchronizer shape
exit 0
```

`mode (clk2) -> b` appears nowhere in the report: `_data_cone_registers`
walks `b`'s data inputs, and its clock net is not one of them. The same
enable on an AND gate is caught, because there it is an input the
classification sees (`hier.sv`, §5: `clk1+en2`, exit 1). A selection is
the one place a foreign control can steer a clock unreported.

**Two shapes escape by accident, and the accident is worth recording.**
`clk2 ? clk1 : 1'b0` (`muxand.sv`, which is `clk1 & clk2`) is undecided
and exits 1 -- because the constant's dependency set is empty and clk1's is
not, so "different clocks". A `case (clk2)` statement (`pmuxsel.sv`)
lowers to a `$pmux` whose `A` input is the constant `x`, and it is
undecided for the same reason, with `"gated by const x"` in its `through`
list. Neither is the select being examined; both are the constant
happening to differ from the clock.

**This falsifies printed sentences.** `:242`: "the crossing onto a blended
or multiplexed clock still fails, because it is still a crossing" -- four
multiplexed clocks above, exit 0. `:298`: "Where they do not, as with a
divider or a multiplexer between two clocks, it does fail" -- `muxsel.sv`
is a multiplexer between clk1 and its inverse selected by clk2, exit 0.
`clocks.py:137-139` (printed at `:246`): "At a gate feeding a clock pin,
the inputs that reach a declared clock through logic alone are the gate's
clocks. Every other input is compared against them" -- the select is not
compared against anything. The schema's `same_clock_source` description,
"Both clocks resolved to one net, declaration given"
(`tools/dvh/schema/crossings.schema.json`), is false of every design
above: the second clock was skipped, not resolved.

**Fix.** Under a declaration, classify `S` with the other inputs. Compute
`clock_deps` for the select exactly as for `A` and `B`; if it depends on a
declared clock the multiplexer does not otherwise have, or on `UNKNOWN`, or
on a register whose clock is not one the multiplexer has (`muxreg.sv`),
the selection is a blend and the select is carried as a root. If it depends
on nothing, or only on clocks the multiplexer already has, it is control and
is recorded as `gated by`, so that a *port* on a select pin reaches
`ports_treated_as_control`. Undeclared, a select that is itself a clock
candidate (tier 1 or 2) should mark the multiplexer undecided, as a
demoted gate input does at `:313-314`. `S` on a `$pmux` is a vector;
each bit is classified. Fixtures: `muxsel.sv`, `muxgate.sv`, `muxpll.sv`,
`muxreg.sv`; keep `muxand.sv` and `pmuxsel.sv` so the accidental escapes
stay accidental.

### 1.2 A register's asynchronous control pin is not a clock dependency

`clock_deps` at a register (`tools/dvh/clocks.py:166-169`):

```python
if cell.type in DFF_TYPES:
    if through_registers:
        stack += cell.conns.get("CLK", [])
    continue
```

The docstring says what this means (`:128-130`): "A register's output ...
depends on whatever its clock or enable and data depend on". A register
with an asynchronous set, clear or load changes its output on that pin's
edge, not on its clock's, and the pin is not followed. The pulse-generator
idiom -- a flag set asynchronously by one clock's edge and cleared by the
other's -- is the ordinary way an edge of clk2 is turned into one cycle of
clk1, and its output is timed by both.

```systemverilog
// asyncset.sv -- a flag set asynchronously by clk2's rising edge and
// cleared by clk1: the pulse-generator idiom. Its output changes on clk2's
// edge, and it gates clk1. clock_deps follows a register's CLK pin only,
// so the flag "depends on clk1" and is control. Both clocks declared.
module asyncset (input logic clk1, clk2, input logic [7:0] d,
                 output logic [7:0] q, output logic t);
  logic flag, gclk, tog;
  logic [7:0] a, b;
  always_ff @(posedge clk1 or posedge clk2)
    if (clk2) flag <= 1'b1; else flag <= 1'b0;   // rises with clk2
  assign gclk = clk1 & flag;
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge gclk) b <= a;              // 8 bits, no synchronizer
  always_ff @(posedge clk2) tog <= ~tog;
  assign q = b;
  assign t = tog;
endmodule
```

```
$ dvh read asyncset asyncset.sv --clock clk1 --clock clk2
clock domains: 3
  clk1#2: 2 registers
  clk1#22: 1 registers
  clk2: 1 registers
registers without reset: 3
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (clk1#2) -> b (clk1#22), 8 bits, no synchronizer shape
         [asyncset.sv:13]
exit 0
```

```
"flag": {"clock_sources": ["clk1"], "gated_or_muxed": false, "through": [],
         "root_bits": ["2"], "domain": "clk1#2"}
"b":    {"clock_sources": ["clk1"], "gated_or_muxed": true,
         "through": ["$and", "gated by flag"], "clock_ambiguous": false,
         "root_bits": ["2"], "domain": "clk1#22"}
```

`flag` is a `$adff` whose `ARST` is the port `clk2`; the report puts it in
clk1's domain with an empty `through`. When `gclk` rises because `flag`
rose on clk2's edge while clk1 was high, `b` captures `a` -- a clk1-domain
value -- at a clk2-determined instant. Undeclared: `undecided clock of b`,
exit 1. The same with an asynchronous *load* (`aldffclk.sv`, a `$aldff`
whose `ALOAD` is clk2): `clk1#2: 2 registers`, `clk1#23: 1 registers`,
"1 of them one clock gated differently", exit 0.

The flip-flop version of `gate2h` §1.3 (`flopar.sv`) is reported, because
there the clear comes from a *register* and `_data_inputs` finds it as a
data crossing into `flag`. Here the clear is a port, so no crossing is
constructed anywhere, and the only route to the finding was the clock
dependency that ignores the pin.

**Fix.** In `clock_deps`, with `through_registers` true, a register's
output depends on its `CLK` *and* on every asynchronous control pin the
cell carries -- `ARST`, `ALOAD`, `SET`, `CLR` -- since each is an edge that
moves the output. `RESET_PINS` (`clocks.py:420-424`) already lists them;
the synchronous ones (`SRST`, `EN`) stay excluded. With that, `flag`
depends on `{clk1, clk2}`, is not a subset of `{clk1}`, and the gate is a
blend. Fixtures: `asyncset.sv`, `aldffclk.sv`.

## 3. Serious (not blocking, but they belong in the next patch)

### 3.1 The hidden-clock defense does not fire when the clock arrives through a register

`gate2h` §3.4 accepted that a clock which only ever appears gated cannot be
caught by the completeness check, on the strength of the new
`ports_treated_as_control` list (`clocks.py:397-406`, printed at
`cli.py:68-70`) and the chapter's sentence at `:242`: "the report lists
every port it read as gating control, and a reader who finds a clock in
that list has found the declaration's mistake." The list holds *ports*
demoted at a gate. A hidden clock that reaches the gate through a register
clocked by it demotes the register, and the list is empty:

```systemverilog
// hidreg.sv -- a clock that only ever appears gated (so the completeness
// check cannot know it) reaches the gate through a register clocked by it.
// The demoted input is a register, not a port, so the "ports treated as
// gating control" list is empty and the defense the chapter names does not
// fire. `--clock clk1` is accepted as complete.
module hidreg (input logic clk1, hclk, en, input logic [7:0] d,
               output logic [7:0] q);
  logic hg, r, gclk;
  logic [7:0] a, b;
  assign hg = hclk & en;
  always_ff @(posedge hg) r <= ~r;         // register in the hidden domain
  assign gclk = clk1 & r;                  // blend
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge gclk) b <= a;        // 8 bits, no synchronizer
  assign q = b;
endmodule
```

No "ports treated as gating control" line is printed:
`ports_treated_as_control` is `[]`, and `r`'s entry is
`"clock_sources": ["en", "hclk"], "through": ["$and"]` with neither input
demoted (at `hclk & en` no input reaches a declared clock, both have empty
dependencies, and the `else` branch at `:293-295` carries nothing and
demotes nothing). The netlist *does* show a clue -- a domain named
`en+hclk` with two roots -- but the report does not connect it to the
declaration. Not blocking, because the declaration is wrong and the correct
one fails; serious because it is the exact case `gate2h` §3.4 was closed on.

**Fix.** Two independent halves. (1) A register whose own clock walk ended
on an undeclared port -- any register in a domain whose `root_bits` include
a port bit not in the declaration -- is evidence that the declaration is
incomplete, and `clock_ports` can be extended to collect every port a
register's clock walk reaches through `PASS_THROUGH` (the fix `gate2h` §3.4
already proposed); `hclk` would then be refused as undeclared. (2) Failing
that, a demoted input whose dependency set is empty *because it traces to
an undeclared port* (rather than to nothing) should put that port in
`ports_treated_as_control`, so the list means what `:242` says it means.
Fixture: `hidreg.sv`.

### 3.2 The clock walk still recurses; a 1500-gate chain is exit 2

`gate2h` §3.1 stands for `_walk_to_sources` (`clocks.py:199-337`), which
recurses once per cell. The declared path no longer adds a recursion of
its own -- `clock_deps` is iterative and `ripple2.sv` runs (§2) -- but the
walk that calls it is still recursive, so under a declaration a deep clock
cone crashes exactly as it does without one:

```
$ dvh read deepclk deepclk.sv --clock clk1 --clock clk2
dvh: RecursionError: maximum recursion depth exceeded
dvh: this is a defect in the tool, not a finding about the design
exit 2
$ dvh read gchain2 gchain2.sv --clock clk        # 1500 chained clock gates
dvh: RecursionError: maximum recursion depth exceeded
exit 2
```

`gchain.sv`, the same chain at 400 gates, runs in 1.1 s and exits 0 with
`--clock clk`, so the limit is between 400 and 1500 gates. Two more
recursive walks share the cause: `_cone_registers` (`:730-733`), used by
`_latch_crossings`, ends a 1500-level data cone into a latch's `D` with
`RecursionError` (`deeplatch.sv`, exit 2), and the reset walk at `:459` does
the same on a 1500-level reset cone (`deeprst.sv`, exit 2). All three are
the three-way exit contract working, which is why this is not blocking; all
three have the fix already applied to `_data_cone_registers` and
`clock_deps`. Fixtures: `deepclk.sv`, `gchain2.sv`, `deeplatch.sv`,
`deeprst.sv`.

### 3.3 A constant is reported as gating control, and it is what saves two designs

At `clk1 & 1'b1` and at a `$pmux` whose unused input is `x`, the constant
lands in `through` as `"gated by const 1"` / `"gated by const x"`
(`pmuxsel.sv`: `["$pmux", "ambiguous: ...", "gated by const x", "mux"]`).
A constant is not control and should not be listed as demoted; more to the
point, §1.1 shows that `muxand.sv` (`clk2 ? clk1 : 1'b0`) and `pmuxsel.sv`
are undecided only because the constant's empty dependency set differs from
the clock's. Once the select is classified (§1.1's fix), a constant input
should be dropped from `ins` before the comparison rather than counted as
a differing clock, or the "fix" will turn these two from accidental
failures into accidental passes.

## 7. Answers to the questions asked

**1. Can `dvh read` exit 0 on an unsynchronized crossing between two
asynchronous clocks, with a complete and correct declaration? Yes, six

clock dependency (`asyncset.sv`, `aldffclk.sv`, §1.2). **Without a

every `gate2h` design now exits 1 both ways.

fixed. No false `shape_recognized`. No wrong location. Run time is linear
where it was measured.

three minor findings fixed, with the deep clock cone still exit 2 and the
hidden-clock defense not firing in one shape (§2).

at a gate: every AND, OR and XOR blend tried, through buffers, black boxes,
latches, dividers, vector ports and hierarchy, now fails correctly. What

a few lines. The prose fix is the larger one: `:242` and `:298` promise
that a multiplexed clock fails, and the tool's own docstring says a select
is not a clock.
