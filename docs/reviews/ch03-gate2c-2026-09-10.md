# Chapter 3 gate-2 re-review

Scope: the fifth pass. The redesign in `tools/dvh/clocks.py` (domain identity
is the clock net; an unresolved clock gets an identity of its own; nothing
suppressed, but a same-source pair marked and kept out of the build gate; the
convergence rule indexed by crossing; `opt_dff` added to the Yosys script),
then every sentence in @sec-ch03-example that makes a claim about the code,
then the residue listed as non-blocking in
`docs/reviews/ch03-gate2b-2026-09-09.md`, then the research note's seven
constraints and the house rules.

Method. Every claim about the code was tested by running the code on designs
written for this review. `tools/dvh/tests/rtl/` was read but not relied on;
where a design from an earlier review is re-run to settle residue it is marked
as such. Every design below is reproduced in full so it can be re-run. Tools:
Yosys 0.68+post, the `dvbook` conda environment, `PYTHONPATH=tools`.

Baseline, verified before anything else and again after: `pytest
tools/dvh/tests/test_ch03.py` passes, 25 tests; `scripts/check-examples.sh
ch03` reports `pass=3 fail=0`. Both stay green through every failure below.

**Verdict: blocking findings remain.** Five blockers in §1. §1.1 is a crossing
dropped from the report entirely, with exit 0 — the fourth consecutive round in
which that happens, by a fourth mechanism. §1.2 is the build gate silenced on a
real asynchronous crossing outside the boundary the drafter recorded. §1.4 is a
regression the previous review predicted in writing and prescribed the guard
for; half the prescription was taken.

## 1. Blocking

### 1.1 A crossing is dropped from the report entirely: a memory array

This is the failure the re-review was asked to hunt, and it is present.

```systemverilog
// ramcross.sv -- an asynchronous crossing through a small RAM: written on
// aclk, read on bclk, with no synchronizer anywhere.
module ramcross (input logic aclk, arst_n, bclk, brst_n,
                 input logic [3:0] waddr, raddr,
                 input logic [7:0] wdata, input logic we,
                 output logic [7:0] q);
  logic [7:0] mem [0:15];
  logic [7:0] rdata;
  always_ff @(posedge aclk)
    if (we) mem[waddr] <= wdata;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) rdata <= 8'h00; else rdata <= mem[raddr];
  assign q = rdata;
endmodule
```

```
clock domains: 1
  bclk: 1 registers
registers without reset: 0
crossings: 0, shape not recognized: 0
instances: 0, connections: 0
```

Exit 0. `dvh crossings` returns `{"crossings": [], "unrecognized": []}`. A
two-clock design is reported as having one clock domain, and an eight-bit
unsynchronized crossing between two asynchronous clocks is reported as nothing
at all. There is no `CHECK`, no note, no ambiguity marker: the report is silent
in exactly the way §1.1 of the previous review, §1.2 of the one before it and
§1.3 of the one before that were silent.

Three lines cause it, and they are independent of the domain-identity question,
which is why the redesign did not touch them:

* `design.py:89` builds the script `hierarchy; proc; opt_dff; flatten;
  opt_clean` with no memory pass. An array written from a process that carries
  no reset — the ordinary way a RAM is written, and the way an asynchronous
  FIFO writes one — stays a `$memwr_v2`/`$memrd` pair. (An array written from a
  process that *does* carry the reset is bit-blasted, which is why the Chapter 1
  FIFO's sixteen entries appear and this design's sixteen do not. The behaviour
  is a property of the writing style, not of the array.)
* `design.py:159-160` yields registers only for `cell.type in DFF_TYPES`, so
  the write port is not a register, so `aclk` is not a domain and the sender
  does not exist.
* `clocks.py:110-111` excludes `$mem*` from `combinational`, so
  `clocks.py:161` returns the `$memrd` output as an opaque `unknown` source and
  the data cone stops there. `_data_cone_registers` (`clocks.py:244-252`) keeps
  only `kind == "register"`, so nothing survives.

Verified against the textbook structure as well. A Gray-pointer asynchronous
FIFO with two-flop pointer synchronizers and a dual-port RAM (`afifo.sv`,
16×8, reproduced in the working notes) reports:

```
clock domains: 2
  rclk: 4 registers
  wclk: 4 registers
registers without reset: 0
crossings: 2, shape not recognized: 2
  CHECK rgray (rclk) -> wq1_rgray (wclk), 5 bits, no synchronizer shape
  CHECK wgray (wclk) -> rq1_wgray (rclk), 5 bits, no synchronizer shape
```

The two pointer crossings are found. The eight-bit data crossing through the
RAM is absent, and so are the sixteen unreset memory entries. The exit code is
1, so a build gate happens to trip — on the pointers, not on the data. In
`ramcross.sv`, with no pointers, it does not trip at all.

Three printed sentences are falsified.

`chapters/ch03-digital-design-for-verifiers.qmd:285` — "Yosys expands the array
into individual flip-flops and the tool faithfully reports what it finds" — is
stated as what Yosys does with a storage array, and is false for the common RAM
writing style. `:129` — "The tool later in this chapter reports every unreset
register it finds" — is true only in the trivial sense that it finds none;
`afifo.sv` prints `registers without reset: 0` over sixteen unreset entries.
And Exercise 5 at `:318` asks the reader to restore the `cfg` synchronizer
"using each of the four correct structures from @sec-ch03-cdc in turn" and to
say "which does the tool recognize, and which does it report as a bug" — one of
those four is the asynchronous FIFO of `:97`, and the honest answer for its data
path is that the tool does not see it. An exercise whose answer is "the tool is
blind here" is a fine exercise, but the chapter has to know that is the answer.

**Fix.** Add `memory_collect; memory_map;` after `opt_dff;` in `design.py:89`.
Verified: with that one change `ramcross.sv` reports `clock domains: 2`,
`registers without reset: 16` and `crossings: 16`, every one a `CHECK`, and the
exit code becomes 1. If mapping every array is judged too expensive, the
alternative is to make `$mem*` cells first-class: a memory with a write port on
one clock and a read port on another is itself a domain boundary and can be
reported as one. What must not remain is silence. Note also that the same fix
does *not* recover the `afifo.sv` data crossing, because there the read is
combinational and the destination is a port rather than a register — that is
the separate, narrower limit at §2.7 below, and it wants a sentence in the
chapter rather than code.

### 1.2 `same_clock_source` silences a real asynchronous crossing at the build gate, outside the recorded boundary

`clocks.py:382-384` decides that two clocks are one clock when the *sets* of
source names the walks reached are equal:

```python
same_source = (not unsure_pair(tree, name, src)
               and _sources(tree, name) == _sources(tree, src)
               and _sources(tree, name) != set())
```

and `clocks.py:405-406` then keeps such a crossing out of `unrecognized`, which
is what `cli.py:125` exits on. The drafter recorded one failure case: where the
evidence heuristic picks the wrong signal as the clock, two different clocks can
resolve to one source. That case is real and reproduces —

```systemverilog
// muxdom.sv -- two $mux clock multiplexers over clk_a and clk_b on opposite
// selections, plus one register clocked straight from clk_a, which is the
// strong evidence that collapses both multiplexer outputs onto clk_a.
module muxdom (input logic clk_a, clk_b, sel, rst_n, d,
               output logic q, output logic q_a);
  logic ck_x, ck_y, rx, ry, ra;
  assign ck_x = sel ? clk_a : clk_b;
  assign ck_y = sel ? clk_b : clk_a;
  always_ff @(posedge clk_a or negedge rst_n)
    if (!rst_n) ra <= 1'b0; else ra <= d;
  always_ff @(posedge ck_x or negedge rst_n)
    if (!rst_n) rx <= 1'b0; else rx <= d;
  always_ff @(posedge ck_y or negedge rst_n)
    if (!rst_n) ry <= 1'b0; else ry <= rx;
  assign q = ry; assign q_a = ra;
endmodule
```

```
crossings: 1, shape not recognized: 0
  CHECK rx (clk_a#11) -> q (clk_a#9), 1 bit, no synchronizer shape
```

Exit 0 — but the boundary is wider than the record says. The rule does not need
the heuristic to be wrong. It fails just as completely when the walk is
*right*:

```systemverilog
// bothstrong.sv -- the same two clock multiplexers, but clk_a and clk_b each
// also drive a register's clock pin directly. Both are therefore strong
// evidence, the walk correctly resolves each multiplexer output to the set
// {clk_a, clk_b}, and nothing is marked ambiguous.
module bothstrong (input logic clk_a, clk_b, sel, rst_n, d,
                   output logic q, output logic qa, output logic qb);
  logic ck_x, ck_y, rx, ry, ra, rb;
  assign ck_x = sel ? clk_a : clk_b;
  assign ck_y = sel ? clk_b : clk_a;
  always_ff @(posedge clk_a or negedge rst_n)
    if (!rst_n) ra <= 1'b0; else ra <= d;
  always_ff @(posedge clk_b or negedge rst_n)
    if (!rst_n) rb <= 1'b0; else rb <= d;
  always_ff @(posedge ck_x or negedge rst_n)
    if (!rst_n) rx <= 1'b0; else rx <= d;
  always_ff @(posedge ck_y or negedge rst_n)
    if (!rst_n) ry <= 1'b0; else ry <= rx;
  assign q = ry; assign qa = ra; assign qb = rb;
endmodule
```

```
clock domains: 4
  clk_a: 1 registers
  clk_a+clk_b#10: 1 registers
  clk_a+clk_b#12: 1 registers
  clk_b: 1 registers
crossings: 1, shape not recognized: 0
  CHECK rx (clk_a+clk_b#12) -> q (clk_a+clk_b#10), 1 bit, no synchronizer shape
```

Exit 0. The clock walk did everything asked of it: four distinct domains, both
multiplexer networks correctly resolved to both of their sources, no ambiguity
marker anywhere. `same_clock_source` then reads "the same two sources" as "the
same clock, gated or selected differently" and drops the pair from the gate. The
comment at `clocks.py:377-381` states the intended meaning — "Two clock nets that
resolve to the same source are one clock, gated or selected differently. That is
a timing question, not a metastability one" — and equality of a *set* of two
asynchronous sources is not that.

A third shape reaches the same place through the enable path:

```systemverilog
// en_strong.sv -- a strobe used both as the clock of a small block and as the
// enable of two clock gates on two asynchronous clocks.
module en_strong (input logic clk_a, clk_b, en, rst_n, d,
                  output logic q, output logic q_e);
  logic g_a, g_b, re, ra, rb;
  assign g_a = clk_a & en;
  assign g_b = clk_b & en;
  always_ff @(posedge en or negedge rst_n)
    if (!rst_n) re <= 1'b0; else re <= d;
  always_ff @(posedge g_a or negedge rst_n)
    if (!rst_n) ra <= 1'b0; else ra <= d;
  always_ff @(posedge g_b or negedge rst_n)
    if (!rst_n) rb <= 1'b0; else rb <= ra;
  assign q = rb; assign q_e = re;
endmodule
```

`CHECK ra (en#9) -> q (en#10), 1 bit, no synchronizer shape`, exit 0.

`:262` tells the reader "it exits non-zero on those, so a build can gate on it",
and `:264` closes with "A report that a build gate trusts has to be wrong in the
loud direction". For this class the gate is wrong in the quiet direction, and the
chapter has no sentence anywhere describing a category that is printed and not
gated.

**Fix.** Narrow the marking to what its own comment claims. Require a *single*
resolved source at both ends and no multiplexer in either clock net:
`len(_sources(...)) == 1` on both sides, the two equal, and no `mux` in either
register's `through`. A gate is then still a gate and a multiplexer is never one.
`gated_clock.sv` and `two_clock_gates.sv` are unaffected; `muxdom`, `bothstrong`
and `en_strong` all become exit 1. Whatever the rule ends up being, the chapter
needs a paragraph stating that the report has a third category — reported, not
gated — and what a reader should do with it, because a reader who gates a build
on the exit code will otherwise never learn that those lines exist.

### 1.3 The printed report contradicts itself: `shape not recognized: 0` above a `CHECK` line

Every output in §1.2 shows it. `cli.py:66-67` prints the count from
`xings["unrecognized"]`, which `clocks.py:405-406` filters by
`same_clock_source`; `cli.py:71` marks a line `CHECK` whenever
`shape_recognized` is false, which that filter does not affect. So the header
says zero unrecognized shapes and the next line is a shape that was not
recognized.

This is not cosmetic. The report is the chapter's artifact — `:280` says "its
exact text is part of the tool's contract" — and the contradiction lands
precisely on the crossings that pass the gate while looking exactly like the
ones that fail it. A reader has no way to tell, from the printed report, which
`CHECK` lines the build gate acted on.

**Fix.** Either count the printed `CHECK` lines and name the gated subset
separately (`crossings: 1, shape not recognized: 1, gating: 0`), or give a
same-source crossing its own mark, `SAME-CLK`, so the count and the lines agree.
Then pin the new line in `_assert_report_text` (`test_ch03.py:116-131`) and say
in the chapter which mark gates a build.

### 1.4 `shape_recognized: true` for structures that are not two-flop synchronizers

Three, and the first is a regression this pass introduced.

**An enabled first stage.** The previous review's §1.4 prescribed two things
together: add `opt_dff`, *and* require the receiving and second-stage flops to
have no `EN` connection before `shape_recognized` can be true, because `opt_dff`
folds an enable mux into `$dffe` and puts the data straight on `D`. The first
half was taken (`design.py:89`); the second was not.

```systemverilog
// en_first.sv -- the first stage samples only when `sample` is high.
module en_first (input logic aclk, bclk, arst_n, brst_n, d, sample,
                 output logic q);
  logic sa, m1, m2;
  always_ff @(posedge aclk or negedge arst_n)
    if (!arst_n) sa <= 1'b0; else sa <= d;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) m1 <= 1'b0; else if (sample) m1 <= sa;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) m2 <= 1'b0; else m2 <= m1;
  assign q = m2;
endmodule
```

```
crossings: 1, shape not recognized: 0
  known sa (aclk) -> m1 (bclk), 1 bit, two-flop synchronizer
```

Exit 0. Before this pass the same design reported `CHECK`. `en_second.sv`, with
the enable moved to the second stage instead, does the same. `_feeds_directly`
(`clocks.py:323-329`) documents itself as answering whether "`source` reaches
this register's D with no logic in between", and `:251` repeats it as "is this
register fed by the foreign register with nothing in between" — with `$dffe`
there *is* a select in front of the flop in the RTL, and both statements are now
false of what the function computes. The recirculation path this creates, from a
possibly metastable `Q` back through the enable mux to the same flop's `D`, is
the reason the structure is not the thing the chapter defines at `:89`.

**An opposite-edge second stage.** Identity is the net, and a net is one
identity regardless of which edge a flop takes:

```systemverilog
// negsync.sv -- the "second stage" is on the falling edge of the same clock.
module negsync (input logic aclk, bclk, arst_n, brst_n, d, output logic q);
  logic sa, m1, m2;
  always_ff @(posedge aclk or negedge arst_n)
    if (!arst_n) sa <= 1'b0; else sa <= d;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) m1 <= 1'b0; else m1 <= sa;
  always_ff @(negedge bclk or negedge brst_n)
    if (!brst_n) m2 <= 1'b0; else m2 <= m1;
  assign q = m2;
endmodule
```

`known sa (aclk) -> m1 (bclk), 1 bit, two-flop synchronizer`, exit 0. The
chapter defines the structure at `:89` as one that "waits a full clock period
before sampling the first stage into a second"; this one waits half. The
resolution time `S` in the MTBF formula at `:79` is halved, and `:83`'s whole
point is that halving it is not a detail. The tool asserts the shape as a fact,
in the field the redesign created for facts.

**Fix.** In `crossings` (`clocks.py:385-388`), require the receiving cell and
every second-stage cell to have no `EN` in `conns`, and require each second-stage
cell's `CLK_POLARITY` parameter to equal the receiving cell's. Then re-check that
`en_first.sv`, `en_second.sv` and `negsync.sv` all report `CHECK` and that the
book's own `en_b` path still reports `known`.

### 1.5 The chapter still misdescribes the code, in four new sentences

Fifth consecutive review, and each item below is a sentence that was not wrong
last time.

* `:236` — "The register cell types are the ones Yosys emits after `proc` and
  before technology mapping, and the split between them is what lets the reset
  walk report a kind and a polarity rather than a guess." The script is now
  `proc; opt_dff` (`design.py:89`), and `$sdff`, `$sdffe` and `$sdffce` are
  emitted only by `opt_dff` — which is the whole content of the previous
  review's §1.4 and of `test_ch03.py:400-413`. The same claim is in the spliced
  comment at `design.py:23`, "Sequential cell types Yosys produces after `proc`
  (no technology mapping)", so the corrected script and the uncorrected sentence
  are typeset on facing pages. **Fix.** Say "after `proc` and `opt_dff`" in both
  places, and add one clause saying `opt_dff` is what infers the synchronous
  forms — it is the sentence the last round's bug was made of.
* `:231` — "The pipeline matters: `proc` must lower RTLIL processes into cells
  before any register can be found ... and `flatten` produces the single-module
  view". Two of the four passes are named; `opt_dff`, the one the entire reset
  report depends on, is not. **Fix.** Name it.
* `:287` — "The tests gathered under *limits the tools were once wrong about*
  are there for a different reason", followed by a list of designs. That banner
  is at `test_ch03.py:134-137` and its block ends at `:238`, where the schema
  banner at `:240-243` starts. Five of the designs the sentence goes on to list —
  `shared_enable_clocks`, `three_flop_per_bit`, `sync_reset`,
  `mux_selected_clocks` and `shared_second_stage` — are tested at
  `test_ch03.py:374-441`, *after* the schema block, under no banner at all. The
  sentence names a heading and then lists things that are not under it. This is
  the previous review's §2.3 in a new form: the position reference was replaced
  by a name reference and the name is also wrong. Separately, `two_clock_gates.sv`
  is in `tests/rtl/` and is still not in the list. **Fix.** Move the five tests
  under the existing banner so the sentence becomes true, which is the smaller
  edit, and add the two-clock-gates design to the list.
* `:292` — "A derived clock, whether divided, multiplexed or arriving from a
  block the netlist cannot see into, is a different clock net, so a path from its
  source to a register behind it is reported. Those findings are usually not
  bugs, and on a design with a clock divider the gate would fail every run with
  nothing to fix." Verified true for a divider (`div2.sv`: `CHECK fast (clk) ->
  q (div)`, exit 1) and for a black-box clock (`bbclk.sv`: `CHECK ra (pclk
  (driven by pll)) -> q (clk_b)`, exit 1). It is false for the multiplexed and
  gated cases, which are reported and do *not* fail the gate (§1.2). The
  paragraph now describes the opposite of the behaviour for one of the three
  things it names. **Fix.** Split the sentence: dividers and black-box clocks
  fail the gate and want a waiver; multiplexed and gated clocks whose sources
  resolve alike are printed and not gated — which is the paragraph §1.2 asks for,
  and this is the right place for it.

## 2. Non-blocking

### 2.1 The convergence rule's false positives remain

Re-run of the previous review's §2.1 on designs rewritten for this pass.
`indep_errs.sv` — two independent sticky error flags in one domain, each
correctly two-flop synchronized, OR-ed into one status flop — reports:

```
crossings: 2, shape not recognized: 2
  CHECK s1 (aclk) -> m1a (bclk), 1 bit, 2 one-bit synchronizers are read
  together by any_err; their bits can resolve in different cycles
  CHECK s2 (aclk) -> m1b (bclk), 1 bit, ... (same note)
```

Exit 1. `two_src_domains.sv`, the same shape with the two senders in two
*different* domains (`aclk` and `cclk`), reports the same two findings and exits
1. Neither carries one value, so `shape_recognized: false` is a false statement
of the fact as `clocks.py:342-346` defines it, in the direction that fails a
build. The `note` remains honest about what was observed, which is what keeps
this non-blocking. Requiring a shared `from_domain` before demoting would remove
`two_src_domains` outright; that suggestion is now three reviews old and
unimplemented.

### 2.2 `$dffsr` resets are still reported as constants

Unchanged from two reviews ago. `clocks.py:219` picks `"ARST" if "ARST" in
cell.conns else "CLR"` and never looks at `SET`; the reset walk skips a
multiplexer's select, where a `$dffsr`'s real reset sources sit. On the same
`setreset.sv` as before (`posedge clk or negedge rst_n or posedge set`):

```json
"q": { "kind": "asynchronous", "active": "high",
       "sources": ["const 0", "const 1"], "through": ["$mux", "mux"] }
```

Neither `rst_n` nor `set` appears. Still non-blocking on the same grounds — no
chapter sentence asserts otherwise — but `:236` sits close to it and this is a
false statement of fact in a report the chapter presents as facts. **Fix.**
Detect `$dffsr`/`$dffsre` in `reset_tree` and record the kind as unclassified
with a reason.

### 2.3 A tool crash and a finding still exit the same way

`design.py:93-94` runs Yosys with `check=True, capture_output=True`. `dvh read
nosuchtop file.sv` raises `CalledProcessError`, prints a Python traceback,
discards Yosys's own diagnostics, and exits 1 — the same code `read` uses for a
finding. Unchanged. **Fix.** Catch it in `cli.main`, print the captured stderr,
exit 2, which `_emit` already uses.

### 2.4 Runtime is much better, and the limits paragraph could now say so

The previous review's §2.8 measured a 32-entry array at 11.2 s and a 256-entry
one as not finishing in 120 s. Re-measured on a two-clock register file whose
array is bit-blasted and whose contents genuinely cross (`xf<N>.sv`, an N×8
array written on `aclk` and read into a register on `bclk`):

| entries | registers | crossings | `dvh crossings` wall time |
|---|---|---|---|
| 32 | 34 | 66 | 1.2 s |
| 64 | 66 | 130 | 1.6 s |
| 128 | 130 | 258 | 3.4 s |
| 256 | 258 | 514 | 11.1 s |

Still superlinear, no longer an obstacle at the size the previous review used.
Downgraded from "the tool does not finish" to "the cost grows faster than the
design does"; memoizing `_walk_to_sources` per `(bit, mode)` would still be the
fix, and `:292`'s claim that the limits "are structural rather than temporary"
is now defensible without a runtime caveat.

### 2.5 `:198` and its own evidence record disagree about `SYNCASYNCNET`

`:222` is fixed: it now says `SYNCASYNCNET` is "the one warning in the list that
touches reset and clocking style at all" and credits `MULTIDRIVEN` with the

`examples/ch03-digital-design/sv-lint/Makefile:10-13` says the same. The previous

`:198` still says "Two warnings, `MULTIDRIVEN` and `SYNCASYNCNET`, mention
crossings as a possible consequence of a local pattern." The evidence record is
internally inconsistent about this: the quoted description at
`research/ch03-digital-design-for-verifiers.md:346` does not mention clock

mistake" — while the note's own summary sentence at `:411` asserts that both

is right, `:198` should credit only `MULTIDRIVEN`.

### 2.7 A crossing whose destination is not a register is never reported

Registers are the only destinations `crossings` considers, so a value that
crosses into a top-level output port, or into a latch that leaves through a
port, is not reported. `afifo.sv` is the case that matters: `assign rdata =
mem[rbin[AW-1:0]]` is a combinational read, so even with the memory pass of
§1.1 added the data crossing has no receiving register and stays absent. This is
consistent with the criterion as the code states it and is not claimed otherwise
anywhere, so it is not a defect — but it is the second reason the chapter's most
recommended multi-bit structure produces no finding, and `:268`--`:272`, which is
the chapter's honest passage about the tool's ceiling, is the place for one
concrete sentence saying so.

## 5. Verdict

**blocking findings remain**

1. **§1.1** — an eight-bit asynchronous crossing through a memory array is
   dropped from the report entirely: `ramcross.sv` reports `clock domains: 1`,
   `crossings: 0`, exit 0. Cause is `design.py:89` (no memory pass),
   `design.py:159-160` and `clocks.py:110-111`. Falsifies `:285` and `:129`, and
   makes Exercise 5's asynchronous-FIFO case unanswerable as written. Verified
   fix: `memory_collect; memory_map;`.
2. **§1.2** — `clocks.py:382-384` marks two clock-multiplexer networks over the
   *same two asynchronous clocks* as one clock source and keeps the crossing out
   of the build gate: `bothstrong.sv`, `muxdom.sv` and `en_strong.sv` all exit 0
   on a real unsynchronized crossing. `bothstrong.sv` does it with the walk
   entirely correct and nothing marked ambiguous, which is outside the boundary
   the drafter recorded. Contradicts `:262`, `:264` and `:292`.
3. **§1.3** — `cli.py:66-67` and `cli.py:71` disagree, so the report prints
   `shape not recognized: 0` directly above a `CHECK ... no synchronizer shape`
   line, on exactly the crossings that pass the gate.
4. **§1.4** — `shape_recognized: true`, "two-flop synchronizer", is asserted of
   an enabled first stage (`en_first.sv`), an enabled second stage
   (`en_second.sv`) and an opposite-edge second stage (`negsync.sv`), all exit
   0. The first is a regression created by this pass: the previous review
   prescribed `opt_dff` *and* an `EN` guard, and only `opt_dff` was taken.
5. **§1.5** — four sentences describe code that has changed under them: `:236`
   and `design.py:23` on `opt_dff`, `:231` on the pipeline, `:287` on which
   tests sit under which heading, `:292` on which derived clocks fail the gate.

**On the design question the redesign was meant to settle.** Net identity works.
Every case that defeated the last four passes through the domain-name route —
`glitchless`, `falsesync`, `muxdom` as a *domain* question, `two_clock_gates`,
`shared_enable_clocks`, `bus2` — is now reported, and the undecided key is a
better answer than a print statement because it makes an unresolved clock
unequal to everything by construction. The stopping rule in STATUS.md asks
whether "another defect of the same class in `clocks.py`" has appeared. Two of
the five blockers above are the same *symptom* — a real crossing that does not
reach a reader — but neither is the same class: §1.1 is upstream of the domain
map entirely (a sender that is never a register), and §1.2 is a suppression rule
layered on top of a correct domain map, not a failure of it. Both have local
fixes that do not disturb the identity scheme, and §1.3, §1.4 and §1.5 are
ordinary bugs and sentences. My reading is that the design change succeeded and
the sixth pass is a patch rather than a redesign — but the author should be the
one to decide that, because it is the second time a review has said "the cause is
fixed" about this file.

**What is genuinely good.** The undecided-clock key, the crossing-indexed
convergence rule, and the chain-following that now works across module
boundaries are all correct and were tested here on designs they have never seen.
The reframing from verdict to shape at `:264`--`:272` remains the strongest
passage in the chapter and is exactly the right design. It is also, for the fifth
review running, more true of the tool than the sentences around it admit — and
`:287`'s own claim, that "a tool's description of what it does is an assumption
like any other", keeps being demonstrated by the paragraph it sits in.
