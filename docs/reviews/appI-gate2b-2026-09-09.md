# 1. Blocking

## B-1. `appendices/appI-agent-tool-layer.qmd:207` — the sentence about the schema is falsified by the schema printed above it

> And the schema records what the tool *cannot* decide in `description`, the
> keyword a consumer is meant to read, rather than in a note between schema
> authors: this one says in its own summary that no verdict it reports is a
> sign-off.

Two things are wrong, and both are visible on the same spread of the printed
book. `pdftotext -layout _book/Design-Verification.pdf` puts the schema on
pages 161-163 and this paragraph at the foot of 163. The last line of the
listing, immediately above the paragraph, is:

```
"$comment": "Reports a shape, never a verdict about safety."
```

and the top-level `description`, at `tools/dvh/schema/crossings.schema.json:5`, is:

```
"description": "Crossings between clock domains, and their shapes."
```

So:

1. **The caveat is in `$comment`, which is exactly where the sentence says it is
   not.** The `description` says nothing about what the tool cannot decide.
2. **Nothing in the schema says anything about a sign-off.** The word does not
   appear in the file.

`git log -p` on the schema shows when this happened. Before `b6206f5` the
`description` read "Crossings between domains. No verdict is a sign-off." —
which is what the previous gate verified. `b6206f5` moved the substance to
`$comment:96` and left the appendix's sentence standing. The sentence has been
true and is now false, and it is false in the most checkable place in the
appendix: the paragraph immediately under the listing it describes.

There is nothing to catch this. `test_every_field_carries_a_description`
(`tools/dvh/tests/test_ch03.py:290`) asserts only `doc.get("description")` —
that the string is non-empty, not what it contains.

A second site, from the same contract change:
`appendices/appI-agent-tool-layer.qmd:154`

```
| `rtl.crossings` | top | crossings with classification and reason | @sec-ch03-example |
```

The tool this row points at no longer returns a classification or a reason. It
returns `shape_recognized`, "a fact about structure, not a verdict about
correctness" (`tools/dvh/clocks.py:297-298`), and `note`, described in the schema
as "Empty when known; else what was seen." `chapters/ch03-digital-design-for-verifiers.qmd:264`
is explicit that the report "does not say the `cfg_b` crossings are bugs, and it
does not say the `en_b` one is safe". "Classification and reason" is the
vocabulary the tool was redesigned to stop using, in the catalog row that
specifies it, inside the appendix that opens B.4.2 with the shape-versus-verdict
distinction.

**Proposed fix.** Restore the caveat to the keyword the sentence names, and make
the sentence describe what is there. Either put it back in `description`:

```json
"description": "Crossings between clock domains and their shapes. A shape is not a verdict: nothing here is a sign-off."
```

and leave `:207` as it stands — or, if the `description` is to stay a bare
summary, rewrite `:207` to describe the schema that exists:

> And what the tool *cannot* decide is recorded in the schema rather than in the
> code that produced it: this one says in its own summary that it reports a
> shape, and that a shape is never a verdict about safety.

Whichever way, add an assertion that pins it, so the next contract change cannot
silently falsify the page again — one line in
`test_every_schema_is_versioned_by_url` or its own test, asserting that the
crossings schema's `description` contains the caveat.

At `:154`, change the Returns cell to match the contract:
`crossings, with whether each matches a recognized shape and what was seen`.

## B-2. `appendices/appI-agent-tool-layer.qmd:47` — "the netlist gives it no location to pass on" is false, and `:41` says the opposite

> **Grounding.** A tool's answer comes with a provenance a person can check. The
> book's own tools carry the source location the netlist records for each cell
> into the clock tree, the reset tree and every crossing, so each of those
> findings names the file and line of the RTL that produced it. **The connection
> graph does not: it reports which instance joins which, and the netlist gives it
> no location to pass on.**

Run, not read:

```
$ python3 -c '... design.load_hier(TWO_CLOCK, "top")["top"].cells ...'
  u_dp         datapath   src='examples/ch03-digital-design/rtl/top.sv:51.12-59.4'
  u_regs       regblock   src='examples/ch03-digital-design/rtl/top.sv:32.12-40.4'
  u_sync_en    $paramod…  src='examples/ch03-digital-design/rtl/top.sv:43.22-48.4'
```

Every instance in the hierarchical netlist carries a `src`: the instantiation
site. Yosys also attaches one to every net, so an *edge* has a location too
(`acc` → `top.sv:25.22-25.25`). And `design._parse` (`tools/dvh/design.py:118-121`)
already reads the cell attribute into `Cell.src` for these very cells — the field
is populated and sitting there. `graph.connections`
(`tools/dvh/graph.py:12-51`) never reads it, and `connections.schema.json` has no
`src` property. The tool does not carry the location. The netlist did not
withhold it.

The consequence is not only a false fact. It is a contradiction inside one
section, which is the shape the last gate blocked at this same paragraph.
`appendices/appI-agent-tool-layer.qmd:41`:

> It does keep a thread back to the source: the netlist records a file and line
> for each cell, which is enough to say where a finding came from …

An instance *is* a cell. Line 41 says the netlist records a location for each
cell; line 47 says the netlist has none to give for the graph of cells. The last
review moved this contradiction out of the "every report" clause; it has
reappeared in the excuse clause six lines later.

`STATUS.md:97` carries the same wrong belief — "**not** the connection graph,
which the netlist gives no location for" — so the correction lands there as well.

**Proposed fix.** State the limit as a choice, not an impossibility:

> The connection graph does not yet: it reports which instance joins which, and
> the instantiation site each edge could name is not carried through. That is
> step 2 of @sec-appI-building, not a limit of the netlist.

Better, and it is a two-line change since `Cell.src` is already populated: carry
it. Add `"src"` to each instance in `connections["instances"]` (or an
`instances` object of `{module, src}`), add the property to
`connections.schema.json` with the same `pattern`, and extend
`test_every_finding_carries_a_real_source_location` to cover it — after which
`:47` can say "every report" and be right, and the paragraph loses its exception
altogether.

## S-1. `:209` — the previous blocker was reworded, not repaired, and the sentence is now wrong in a new way

> A further test, in the tool layer's own suite rather than in the file below,
> walks the schemas and fails if any field is added without a description, or if
> a reported source location is blank or does not point at a real file:
>
> ```{.python include="tools/dvh/schema.py"}
> ```

The previous gate's B-4 was that the colon introduced `schema.py` as the test
that walks the schemas, and `schema.py` contains only `load` and `validate`. The
pass answered by inserting a disclaimer — "rather than in the file below" — and
leaving the colon pointing at the file below. The reader is now told, in one
sentence, that the thing being described is not in the listing, and is then given
the listing. Nothing introduces `schema.py` as the validator, which is what it
is.

The sentence has also acquired a new inaccuracy. It attributes both checks to one
test that "walks the schemas". There are two, and only one walks a schema:
`test_every_field_carries_a_description` (`test_ch03.py:261`) walks the four
schemas; `test_every_finding_carries_a_real_source_location`
(`test_ch03.py:294`) runs the tools on a design and inspects the reports. A
schema walk cannot find a blank source location, because a schema has none.

One further precision. "or if a reported source location is blank or does not
point at a real file" reads as a property of the check a caller runs. It is a
property of the *tests*, on the two designs they pin. `--validate`, the check the
CLI offers, cannot detect a location that does not resolve. Demonstrated with a
`` `line`` directive, which is what preprocessed or generated RTL looks like from
Yosys:

```
$ python3 -m dvh reset-tree lined /tmp/rtl/lined.sv --validate
{ "registers": {}, "no_reset": [ { "name": "q",
    "src": "build/gen/phantom.sv:7.3-7.35" } ] }
exit=0
```

No such file exists. The schema's `pattern` constrains shape, and shape is all it
can constrain.

**Proposed fix.** Reorder so the colon introduces what is shown, and split the
two claims:

> The check is not advisory. The tools validate on request, and the tests
> validate the output of every command that prints JSON on every run, so an
> output that drifts from its schema fails in continuous integration rather than
> in somebody else's parser. Two further tests, in the suite @sec-ch03-example
> prints, hold the rest: one walks the schemas and fails if a field has been
> added without a description, and one runs the tools and fails if a reported
> source location is missing, absolute, or does not name a file on disk. The
> validator itself is small enough to read:
>
> ```{.python include="tools/dvh/schema.py"}
> ```

# 5. Observations outside this appendix

Recorded because they were found while checking it.

- **`tools/dvh/schema/*.json`: the `src` pattern rejects a legal file path.**
  `^[^:]+:\d+` assumes no colon in the filename. A source file whose path
  contains one makes `--validate` exit 2 and print nothing:
  `no_reset/0/src: '.../od:d.sv:2.3-2.35' does not match '^[^:]+:\\d+'`. A Windows

  false rejection. Narrow, and the appendix prints this schema.
