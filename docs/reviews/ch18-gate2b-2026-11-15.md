## Blocking findings

### B1. The narration of the counterexample to induction names the wrong operation (text contradicted by a run)

`chapters/ch18-formal-property-verification.qmd:141`: "and then a read with
the count somehow at zero and the pointers apart is the bad state."

The path printed in `examples/ch18-formal-property-verification/kind/run.out`
lines 14-17 ends `wr_ptr=1 rd_ptr=1 count=3` -> `wr_ptr=0 rd_ptr=1 count=0`.
The read pointer does not move and the write pointer does: the step is a
**write**, and the count goes from 3 to 0 by overflow of its two bits. No read
takes place. Decoded from the model with the example's own `evaluate`
(inputs in the order rst_n, wr_en, rd_en):

```
from wr_ptr=1 rd_ptr=1 count=3:
  1 0 0 -> wr_ptr=1 rd_ptr=1 count=3      idle
  1 1 0 -> wr_ptr=0 rd_ptr=1 count=0      write only: the bad state
  1 0 1 -> wr_ptr=1 rd_ptr=0 count=2      read only
  1 1 1 -> wr_ptr=0 rd_ptr=0 count=3      both
```

The sentence matters because the paragraph teaches the reader to read such a
path, and the reader who checks it against the listing above it finds it
wrong. Fix: "and then a write alone moves the write pointer and wraps the
count from three to zero: empty, with the pointers apart."

### B2. The engine table reports a property the external engine was never given as "no verdict in 4 s" (table and caption contradicted by a run)

`examples/ch18-formal-property-verification/engine-guide/tbl-engines.md`,
liveness row, column `ric3-ic3`: "no verdict in 4 s". Its caption
(`engine-guide/guide.py:91`): "*No verdict* is a statement about the limit,
not about the engine." Chapter line 444: "the external engine returned
none."

InFormal does not run external engines on liveness properties at all
(the tool's shell document says so, and `examples/mk/informal-engines.toml`
repeats it in a comment). Measured on the row's own design
(`lasso/live_small.sv`, `Grant_A` with `Fair_M`, `informal::set_engines
ric3-ic3`):

```
ric3-ic3 on liveness, limit 4s:  2 ms   Grant_A undetermined
ric3-ic3 on liveness, limit 30s: 2 ms   Grant_A undetermined
informal-bmc, limit 4s:       4017 ms   Grant_A undetermined
```

The same on a design of mine (a two-requester arbiter): 66 ms for five
properties, two of them liveness, both `undetermined`. So for this one cell
"no verdict" is a statement about the tool and not about the limit, the
caption's sentence is false of it, and the table attributes to a named
third-party engine a failure to prove something it was never asked.
Fix: have `guide.py` print "not run (liveness)" in that cell (the row kind
is known to the script), and say in the prose that the tool does not hand
liveness properties to external engines, which is why the row has no fourth
answer. Exercise 12(e) then has an honest row to cite.

### E2. The teaching engines against my own fuzzer (task 2)

builder, writes each system as an `.aag` file (so the book's `Aig` parser is

`ts.explicit`. Constraint semantics as in AIGER 1.9: a transition or a bad
state counts only under an input that satisfies every constraint.

Families: random logic (0 to 3 inputs, 1 to 6 latches, constants in the pool,
0 to 2 constraints); "corner" (constant next-state functions, constant bad
literal, a constraint that is constant false); counters (wrap, saturate,
reset-at-limit, any start value); shift registers with and without a

property needs `a == b`.

Checks on every system:

- IC3: the verdict equals the oracle's; a counterexample is a list of states
  that starts in an initial state, follows real transitions and ends in a
  bad state; an invariant contains every initial state, is closed under
  every allowed transition and holds no bad state, by enumeration over all
  states and inputs; `certify` accepts it; and `certify` is then given
  three perturbed lemma sets (lemmas dropped, a random cube added) and each
  of its three answers must equal the enumeration's.
- k-induction, plain (bound 10) and with unique states (bound
  `min(2^n, 18)`): never `proven` on a false property, never `cex` on a
  true one; a counterexample is a real path of exactly `k` steps and `k` is
  the shortest depth; a returned counterexample to induction is a real
  model of the step case (good edges only, last state bad, pairwise
  different when asked); with the bound at `2^n` the unique-states run must
  decide; and the pair (verdict, k) must equal what I compute without a
  solver: plain induction's step case at `k` is satisfiable iff a walk of
  `k` good edges ends in a bad state, the unique-states one iff a simple
  path of `k` good edges does.
