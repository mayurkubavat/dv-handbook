### B1. Ch.6, `chapters/ch06-oop-testbench-design.qmd:77` — "for six releases" is a number the change log does not support

Sentence: "`new src` is a shallow copy of the object, and for six releases
Verilator copied the object *the handle's declared type said was there* ...

Evidence: `/opt/homebrew/Cellar/verilator/5.052/Changes` line 681, under the

releases nobody measured and releases that predate class copy support.

measured before this one, 5.030, copied the object the handle's declared type

## Serious

### S1. `.github/workflows/book.yml` — the Yosys build step cannot run: v0.68 has no Makefile

The new step runs
`(cd /tmp/yosys && make -s -j"$(nproc)" PREFIX=/opt/dvtools install)`.
The GitHub contents API for `YosysHQ/yosys` at `ref=v0.68` lists
`CMakeLists.txt` and `cmake/` at the root and no `Makefile` (v0.56, for
comparison, still has `Makefile`). Both raw-file fetches of
`v0.68/Makefile` returned 404. The v0.68 README says: "CMake is used for build
configuration ... `cmake -B build . -DCMAKE_BUILD_TYPE=Release`,
`cmake --build build --config Release --parallel $(nproc)`,
`sudo cmake --install build --strip`", and lists CMake >= 3.28, Bison >= 3.8,
Python >= 3.11 and a C++20 compiler as requirements. So on every cache miss
`make` exits with "No targets specified and no makefile found" and the job
fails before the examples run. The tag `v0.68` itself exists
(`git ls-remote --tags` -> `5d64ef30...`). The apt list does not name `cmake`;
the hosted runner image ships one, but pinning it in the list would make the
build reproducible.

Also worth knowing before rewriting this step: nothing under `examples/` or
`scripts/` invokes `yosys` (`grep -rl yosys examples scripts .github` finds
only the workflow). The build is currently paid for a `yosys -V` line.

The Verilator and Icarus builds look right: `v5.052` and `v13_0` exist
upstream (`efa4927b...`, `30a7d1a1...`); Icarus's `autoconf.sh` exists at
`v13_0`; the apt list covers Verilator's documented prerequisites (git,
help2man, perl, python3, make, autoconf, g++, flex, bison, libfl-dev,
zlib1g-dev) and Icarus's (autoconf, gperf, flex, bison, g++,
libreadline-dev, zlib1g-dev).

### The four fixed sources (task 3)

Lint command for each: `verilator --lint-only --timing --timescale 1ns/1ps
-Wall -Wno-DECLFILENAME -Wno-UNUSEDSIGNAL -Wno-PROCASSINIT --top-module <top>
<sources>`.

- `examples/appF-counter/sv/tb_counter.sv`: correct. `rst_n <= 1` and `en <=
  (n > 0)` are non-blocking writes from an `initial`/task at a `posedge clk`,
  so the `always_ff` in `counter.sv` samples the old values at that edge and
  the count starts one edge later, which is what `expected` assumes (the check
  is `@(posedge clk); #1; expected++`). The trailing `en <= 0` lands at
  edge+1 ns, off the edge. `rst_n` only rises, so the asynchronous `negedge
  rst_n` term never fires from it. Lint: clean, exit 0. Without
  `-Wno-PROCASSINIT` the only warning is PROCASSINIT on `logic clk = 0` /
  `always #5 clk <= ~clk`. Note: the file is not spliced into any page (only
  its Makefile and `run.out` are), so the prose describing it is the paragraph
  above, which is accurate.
- `examples/ch05-testbench-language/interface-vif/sink.sv`: correct. The old
  file had `initial taken = 0;` beside an `always_ff` that writes `taken`,
  which 5.052 rejects under the book's flags:
  `%Warning-MULTIDRIVEN: sink.sv:11:11: Variable also written to in always_ff
  (IEEE 1800-2023 9.2.2.4): 'taken'` (5.030 lints the old file clean). The new
  form, an initializer on the variable output port (`output logic [7:0] taken
  = '0`), is the fix Verilator's own PROCASSINIT page prescribes ("Do not use
  a separate initial block for a variable assigned by an always_ff process
  ... Use a declaration initializer"). I checked the port-initializer form on
  both tools with a standalone module: Icarus prints `taken=3`, Verilator
  5.052 prints `taken=3`. Lint of the whole example (`--top-module tb_vif
  bus_if.sv sink.sv tb_vif.sv`): clean, exit 0. (Linting `sink` alone as top
  reports UNDRIVEN on `bus_if.valid`, which is expected with nothing
  connected and not a finding.) The chapter's prose near the listing
  (`ch05-testbench-language.qmd:104-107`) says nothing about the initializer;
  the file's own comment, "The bundle carries no reset, so the count starts
  from an initializer on the port", is accurate.
- `examples/ch06-oop-testbench-design/fifo-env/tb_fifo_env.sv`: the three
  `automatic` keywords are on class-handle variables declared in nested
  `begin` blocks of a static `initial`; the language allows `automatic` on a
  block-local declaration and it stops the variable being a static shared by
  the block's re-entries. Correct. Lint (full source list from the Makefile):
  clean, exit 0. `scripts/check-examples.sh fifo-env`: pass; `run.out` differs
  from before only by a trailing space.
- `examples/ch01-what-is-dv/sv-random/tb_fifo_random.sv`: same change on
  `seed` and `levels` in the `initial`. Correct. Lint: clean, exit 0.

One environment note for anyone re-running probes with an `--Mdir` under the
session scratchpad: the scratchpad root holds a stale `verilated.cpp` from
some earlier run, and Verilator's generated makefile searches `..` first, so a
first-level `--Mdir` there fails in the C++ stage with `m_ifaceRefMutex`
errors. A nested `--Mdir` avoids it. Not a book issue.
