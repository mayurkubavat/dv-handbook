#### C1 detail

The chapter, `:43–47`:

> Cummings and Salz put the organizing idea in one sentence: "the Reactive region
> set is the testbench dual of the Active region set" [@cummingssalz2007events].

Both revisions were fetched and searched (Rev 1.0, 40 pp., and Rev 1.2, 42 pp. —
the revision the entry says the book cites). The quoted sentence occurs in
neither. What the paper actually says:

- Rev 1.2 §10.1, p. 41: Mantis 890 "formally defined the behavior of the Reactive
  set of event regions (see sections 2.2.7 - 2.2.10) that were put in place to be
  the **testbench dual of the RTL Active set of event regions** (see section
  2.2.2)."
- Rev 1.2 §2.2.8: "The Reactive region is the reactive region set dual of the
  corresponding Active region in the same time slot." §2.2.9 and §2.2.10 say the
  same for Re-Inactive/Inactive and Re-NBA/NBA.

The quoted words are the research note's own compression
(`research/ch04-simulation-fundamentals.md:281–282`), which the note then asserts
"the authors state in exactly those terms". They do not. The substance is
genuinely the authors' — that is not in dispute — but the quotation marks are
not earned, and the book is now attributing a formulation to two named people.

*Fix.* Quote what the paper says, or stop quoting:

> The Reactive set of regions was, in Cummings and Salz's words, "put in place to
> be the testbench dual of the RTL Active set of event regions"
> [@cummingssalz2007events]: Reactive mirrors Active, Re-Inactive mirrors
> Inactive, Re-NBA mirrors NBA, and the second set runs after the first.

Drop "put the organizing idea in one sentence" as well — the duality is stated
once in a revision-history section and once per region in §§2.2.8–2.2.10, never
in a single sentence.

This is the **third consecutive round** in which this one sentence is a finding:
unquoted and uncited in the first pass, bolded as the book's own in the second,
quoted from a source that does not contain it in the third. The cause is
upstream, in the evidence record, and a fourth pass will re-derive the same
quotation unless `research/ch04-simulation-fundamentals.md:279–286` is corrected
too — it is the line that claims the authors use those exact terms.

### 1.1 B1 checked against the source's own account, not the note

The brief asks specifically that the region ordering be confirmed against the
source's account. It was, in both revisions:

- Rev 1.0 (8 regions, no Re-NBA): "Preponed events, Active events, Inactive
  events, Nonblocking Assign Update events, Observed events, the two

The chapter uses the nine-region model throughout — `:189` says "two regions of
nine" and the table at `:51–60` lists nine — which is consistent with the
`refs.bib` note declaring Rev 1.2 as the cited revision, and with the
Further-reading caveat at `:252` about the two revisions and the venue predating
the content by two years. All three of those were verified in the fetched Rev 1.2
(page footers read "SNUG Boston 2006 / Rev 1.2"; §10.1 is dated December 5, 2007;

**One residual, non-blocking (F-1.1).** `chapters/ch04-simulation-fundamentals.qmd:77`
and the shape at `:41` present the timestep's iteration as forward-only: work in
Active loops until Active is empty, "only then does it move through the later
regions", "then everything settles". The source describes a back edge the chapter
does not: Rev 1.2 §2.2.9 — "the RTL regions (Active-Inactive-NBA) will re-trigger
if the program execution scheduled any events in those regions in the same time
slot" — and §2.2.10 says the same for the Re-NBA region. So the Active set can run
*again* after the Reactive set. This is a simplification rather than an error, and
in a chapter that teaches the model as a shape it is defensible; but "then
everything settles" is the one clause a careful reader will later find is not the
whole story. *Fix (optional, one clause):* "…then the same three regions repeat
for the testbench — which may in turn wake the design's three again — then
everything settles."

## 2.5 C4: a false bridge between this chapter and Chapter 3

Found while checking the cross-references, and promoted to a blocker because it is
the same class as round B's B2 — a stated cause that is not the cause.

`chapters/ch04-simulation-fundamentals.qmd:79`:

> @sec-ch03 mentioned an `always` block with an **empty sensitivity list** locking
> a simulator into an infinite loop and did not explain it. **Here is the
> mechanism**, in the form that catches people: a non-blocking assignment inside a
> combinational block **retriggers that block's own sensitivity list**, which
> schedules the assignment again, which retriggers it again.

These are two different bugs, and the second cannot be the mechanism of the first.

`chapters/ch03-digital-design-for-verifiers.qmd:46` says: "an empty one can lock
the simulator into an infinite loop while the synthesized result is still an AND
gate" — that is `always y = a & b;`, a procedural block with **no event control at
all**, which restarts immediately because there is nothing to wait on. No
sensitivity list exists to retrigger, and no non-blocking assignment is involved.

What `:79` describes is Sutherland, Mills and Spear 2007 §2.4, verified in the
PDF, and the chapter reports it accurately — but the source's own example is
explicit that a sensitivity list is *present* and is the thing that retriggers:

> `always @(m or n) // combinational logic sensitivity list (no clock edge)`
> `  m <= m + n;    // scheduled change to m after zero-delay clock-to-q delta`
> "…the block returns to the sensitivity list to wait for the next change on m or
> n. After the zero-delay clock-to-q delta, the simulator will update the value of
> m. This change will trigger the sensitivity list."

So a reader who came to this paragraph for the answer Chapter 3 withheld leaves
with a mechanism that does not apply to the case Chapter 3 named — in the chapter
whose stated purpose (`:21`) is to supply the derivations Chapter 3 asserted on
authority.

*Fix (one sentence, and the paragraph gets better).* Say that both are zero-time
loops and that this is a *second* form, rather than presenting it as the first
one's mechanism:

> @sec-ch03 mentioned an `always` block with an empty sensitivity list locking a
> simulator into an infinite loop: with nothing to wait on, the block restarts the
> moment it finishes, and time never advances. The regions explain a second form,
> and it is the one that catches people, because the block *does* have a
> sensitivity list: a non-blocking assignment inside a combinational block
> schedules an update to a variable the block is sensitive to, the NBA region
> applies it, and the block triggers again.
