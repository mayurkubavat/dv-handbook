## Serious (not blocking)

**S1 — `tb_vif.sv:4–5` still makes the "single cause" claim the previous
round's S1 removed from the prose; the listing is spliced at `:111` and
contradicts the Pitfall at `:118`.**

`examples/ch05-testbench-language/interface-vif/tb_vif.sv:3–5`:

```
// A virtual interface is a variable whose value is a handle to an interface
// instance. Like any variable it starts null, and using it then is the
// single cause of every virtual-interface failure a testbench has.
```

The prose was fixed (`:109`: "every virtual-interface failure a
testbench has is a variable's failure: the null dereference when it is
used before it is set, the compile error at the assignment when the
class's declared parameters do not match …"). The comment two listings
later says the opposite, and the reader meets it between the corrected
sentence and the Pitfall. Measured again this round with pyslang
11.0.0 on `virtual itf #(16) vif` assigned an `itf #(8)` instance:

```
sv/pmismatch.sv:3:64: error: value of type 'interface itf#(W=8)'
cannot be assigned to type 'virtual interface itf#(W=16)'
```

That failure is at the assignment, not at a use before assignment.
Fix: "Like any variable it starts null, and every virtual-interface
failure a testbench has is a variable's failure. So the driver checks
before it drives …" — then re-run `scripts/check-examples.sh ch05
interface-vif` (the file is 80 columns; keep it so).

**S2 — `:222` attributes the file-scope classes to a queue the simulator
"could not resolve", and to the support table; the failure is neither
about queues nor in the table.**

`:222`: "Two things in that listing are choices the support table
forced, and both are worth seeing. … the classes are declared at file
scope rather than inside the testbench module, because the simulator
could not resolve a module-scope queue referenced from a class declared
inside the module".

Measured on Verilator 5.030 with the book's flags, a class declared
inside a module that references any module-scope variable fails the
same way, queue or not:

```
$ verilator --binary --timing --timescale 1ns/1ps -Wall -Wno-DECLFILENAME \
    -Wno-UNUSEDSIGNAL --top-module top -Mdir v_inmod inmod.sv   # packet expected[$]
%Error: Internal Error: inmod.sv:10:7: ../V3Scope.cpp:72: Can't locate varref scope
$ … inmod2.sv        # int count; task run(); count++
%Error: Internal Error: inmod2.sv:4:17: ../V3Scope.cpp:72: Can't locate varref scope
$ … inmod3.sv        # same, function void run()
%Error: Internal Error: inmod3.sv:4:26: ../V3Scope.cpp:72: Can't locate varref scope
$ … inmod4.sv        # class inside the module, no module variable referenced
n=1                                                             # runs
$ iverilog -g2012 inmod2.sv && vvp a.out
count=1                                                         # Icarus runs it
```

The constraint is real and the design decision is right, but the
sentence names the wrong construct (a reader will conclude queues are
the problem and avoid them) and the support table has no row for it, so
"the support table forced" is true of the modport only. Fix: "… because
Verilator 5.030 fails with an internal error on a class declared inside
a module that reads a variable of that module, whatever the variable's
type — which is why the scoreboard became a class of its own …", and
"Two things in that listing are choices the tools forced". The
`tb_packet_fifo.sv:10–12` comment needs no change; it states no reason.

**M3 — "catalogue" ×5 where the rest of the book writes "catalog".**
`:13` "catalogued", `:25`, `:32`, `:160`, `:253` "catalogue";
`ch04-simulation-fundamentals.qmd:278`, `ch34-generative-ai-agentic-dv.qmd:109,133`

two rounds recorded this as a book-wide choice; it is not — this
chapter is the only one with the British form. Fix: "catalog".

**M4 — `:25` "two-state types are used for that and for nothing else in
a testbench" drops the guideline's other exception.** The paper's §10.1
(`x2013.raw.txt:2637–2652`) has "two exceptions: • The iterator variable
in for-loops is declared as an int 2-state variable. • Verification
stimulus variables that will (or might) have randomly generated values
are declared as 2-state types." Its closing sentence — "2-state data
types should only be used for generating random stimulus values" — is
what the chapter quotes, so the sentence is defensible, but a reader who
follows the citation finds `int i` allowed. Fix: "for that, for a loop
counter, and for nothing else".

**M5 — `:253` "catalogue every trap in this chapter with a fix for
each".** Three of the chapter's traps are not in either paper: the
Icarus virtual-dispatch result and the Verilator four-state constant
(`:190`), and the wrong-instance virtual interface (`:118`). And the
2006 paper's reset fix is the one `:57` shows failing on Verilator
(measured, §2 below). Fix: "catalogue the language traps in this
chapter, with a fix for each that the event-driven simulator honors".

**M6 — "solve-before and soft constraints, given a solver" is measured
without one.** `k06` scores *wrong* on Verilator for the same missing
solver as the row above it (`pr/`: `%Warning: Unable to communicate with
SAT solver … Tried: $ z3 --in`, then `PROBE k06 FAIL`). The relabel from
last round's M9 names a condition the measurement does not meet, so the
cell still cannot say what the label asks. Fix: drop the row until the
constrained-random chapter's build installs a solver, or label it
"solve-before and soft constraints" and let `:192` explain the cell as
it does for the row above.

**M7 — The caption says "the constructs this chapter teaches"; seven
rows are not taught here.** Nested class, `program` block, `randomize()`
×3, covergroup, mailbox and interface class are measured for "this
chapter and the next two" (`:186`) and exercise 6 says so. Fix in
`matrix.py:102–103`: "the constructs this chapter and the two that
follow it teach". (`matrix.py` is spliced; the line stays under 80.)

**M8 — `:76` "inserting in the middle moves what follows" is an
implementation claim with no source.** The standard characterizes only
insertion and removal at the ends as constant-time; what `insert` does
in the middle is the tool's. The callout's own rule ("say what each
operation costs in shape, not in numbers") is met by "inserting in the
middle is not promised to be cheap".

**M9 — `:13` "every one of the four reduces to the same sentence: the
design started at zero, and zero was legal".** For the first of the four
it is the testbench's reset variable that started at zero (`g2006`
§3.1: "in the testbench, rst_n is a 2-state type, which begins
simulation with a value of zero"), and the sentence has just said one
of the four is in the testbench. The Pitfall at `:32` has the right
form ("a two-state variable starts at zero"). Fix: "something started
at zero, and zero was legal".
