## 5. Technical errors — 3 FIXED, 5 PARTIALLY FIXED

The four blocking findings were claims the chapter made about its own code,
and the fix was to change the code. All four were re-tested on designs
written for this review. **Three of the four are only partly fixed**, and in
each case the surviving failure is reachable from a design the committed

### 5.1 A gated clock in its source's domain — PARTIALLY FIXED

The narrow case is fixed. `tools/dvh/clocks.py:44-55` adds
`primary_clocks()`, `:58-61` adds `_reaches()`, and `:103-109` follows only
the gate inputs whose cone reaches a primary clock, recording the rest as
`gated by <net>`. On the first review's own file the tool now reports one
domain and no crossings, and it does the same for two variants the fixture
does not have:

- a gate whose enable is itself a flop on the same clock — one domain
  `clk`, `through = ['$and', 'gated by en_q']`, 0 crossings;
- the latch-based glitch-free gate the chapter recommends at `:63` —
  one domain `clk`, `through = ['$and', 'gated by en_lat']`, 0 crossings.
  The `$dlatch` string no longer leaks into a domain name, which was the
  worse half of the first review's 5.1.

**What is still broken: the heuristic depends on the gated clock's source
also directly clocking some register through a bare port.** When it does
not, `primary_clocks()` returns nothing useful, `carrying` comes back empty,
`clocks.py:106` falls through to "else nothing here is a clock: keep them
all", and the original bug returns in full — including the false `BUG` and
the non-zero exit.

Two designs, both ordinary:

```systemverilog
// Two independently gated blocks on one clock. No register runs on the
// bare clock, which is what a block-level clock gate looks like.
module t_two_gates (input logic clk, rst_n, en1, en2, d,
                    output logic q1, q2);
  logic gclk1, gclk2;
  assign gclk1 = clk & en1;
  assign gclk2 = clk & en2;
  always_ff @(posedge gclk1 or negedge rst_n)
    if (!rst_n) q1 <= 1'b0; else q1 <= d;
  always_ff @(posedge gclk2 or negedge rst_n)
    if (!rst_n) q2 <= 1'b0; else q2 <= q1;
endmodule
```

reports:

```
domains: {"clk+en2": ["q2"], "clk+en1": ["q1"]}
crossings: 1 unsync: 1
  q1(clk+en1) -> q2(clk+en2) w=1 direct=True sync=False reason='no synchronizer'
```

Two domains where there is one, and a `BUG` on an ordinary synchronous path
— word for word the failure the chapter says at `:238` the walk was built to
avoid. A single fully-gated block (one gate, no ungated register) is the same
class: it reports one domain named `clk+en`.

```systemverilog
// The clock comes out of an analog black box, which is a primary clock by
// the chapter's own definition at :56.
(* blackbox *) module pll (input logic ref_clk, output logic out_clk);
endmodule
module t_pll_clk (input logic ref_clk, rst_n, en, d,
                  output logic q_free, q_gated);
  logic pclk, gclk;
  pll u_pll (.ref_clk(ref_clk), .out_clk(pclk));
  assign gclk = pclk & en;
  always_ff @(posedge pclk or negedge rst_n)
    if (!rst_n) q_free <= 1'b0; else q_free <= d;
  always_ff @(posedge gclk or negedge rst_n)
    if (!rst_n) q_gated <= 1'b0; else q_gated <= q_free;
endmodule
```

reports:

```
domains: {"en+pclk (driven by pll)": ["q_gated"],
          "pclk (driven by pll)": ["q_free"]}
crossings: 1 unsync: 1
  q_free -> q_gated ... reason='no synchronizer'
```

`primary_clocks()` at `clocks.py:53` accepts a clock root only if the CLK bit
is in `mod.port_of_bit`, i.e. only a top-level input port. The chapter's own
Definition callout at `:56` says a primary clock is "a primary input of the
design **or the output of an analog block such as a phase-locked loop treated
as a black box**". The code implements half of the definition the chapter
prints, and the diagnostic string leaks into the report exactly as `$dlatch`
used to.

**What is required.** Either the code recognizes a clock root that is not a
port (a black-box output, and the "no register on the bare port" case), or
`:238` states the condition under which its description holds. As written,
`:238` reads as an unconditional fix, and `:258` still invites a build to
gate on the exit code.

### 5.2 "Following every combinational cell" — PARTIALLY FIXED

**The mux-select half is fixed, and robustly.** `clocks.py:97` gates the
select exclusion on the walk mode (`skip_select = not any_comb and cell.type
in MUX_TYPES`), and `:245` in the chapter describes it correctly. Verified on
three shapes the fixture does not have:

- a select reached through a gate (`out1 <= (sel_b & g) ? a : b`) — found;
- a `$pmux` select from a `unique case` on a two-bit foreign register —
  found;
- both in one design — both found, `crossings: 2 unsync: 2`.

**The latch half is not fixed; it is a different silent miss, and the
chapter now asserts the opposite of what the code does.** `LATCH_TYPES`
(`clocks.py:31-32`) makes both walks stop at a latch, and `clocks.py:88-89`
returns a `Source` of kind `"latch"`. Since `_data_cone_registers` keeps only
`kind == "register"`, a crossing that runs *through* a latch is dropped
entirely:

```systemverilog
module t_latch_path (input logic bclk, brst_n, cclk, crst_n, hold, d_in,
                     output logic q_c);
  logic d_b, lat;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) d_b <= 1'b0; else d_b <= d_in;
  always_latch if (hold) lat <= d_b;
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) q_c <= 1'b0; else q_c <= lat;
endmodule
```

reports `domains: {"bclk": ["d_b"], "cclk": ["q_c"]}` and **`crossings: 0
unsync: 0`**. That is a real one-bit unsynchronized control crossing reported
as a clean design — the same outcome the first review's 5.2 objected to,
produced by the fix rather than by the bug.

A crossing that *lands* on a latch is not reported either, because latches
are not in `registers()` and so are never a destination. So the chapter's
justification at `:245` —

> Both walks stop at a latch, because a latch is a state element and walking
> through one would hide a crossing that lands on it.

— is backwards on both halves. Stopping is what hides the crossing through
the latch, and the crossing that lands on the latch is invisible whichever
choice is made. The honest sentence is that a latch in a data cone is a
blind spot: the walk stops, and neither the path through it nor the path
into it is reported. In a chapter about what tools cannot see, that belongs
in the text rather than in a claim that the case is handled.

### 5.4 The per-bit-synchronizer anti-pattern — PARTIALLY FIXED

**The fixture case is fixed.** `_flag_parallel_synchronizers`
(`clocks.py:184-203`) demotes a group, and on `tests/rtl/per_bit_sync.sv` the
tool now reports 8 crossings, 8 unsynchronized, each with the reason "8
parallel one-bit synchronizers on cfg_b; the bits may arrive in different
cycles". Verified.

**The rule the chapter describes is not the rule the code applies, and the
anti-pattern passes under a one-line change to the sending domain.** The
chapter says at `:249`:

> The tool therefore groups recognized synchronizers by the value they carry
> and rejects any group with more than one bit in it.

The code groups by `(_value_of(c["from"]), c["to_domain"])` — the *source
register's name* with any `[...]` suffix stripped (`clocks.py:179-181,
:196`). It has no notion of the value carried. So declaring the eight sending
flops as eight named signals instead of one vector defeats the check
completely:

```systemverilog
module sync1s (input logic clk, rst_n, d, output logic q);
  logic meta;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin meta <= 1'b0; q <= 1'b0; end
    else        begin meta <= d;    q <= meta; end
endmodule

module t_split_src (input logic bclk, brst_n, cclk, crst_n,
                    input logic [7:0] cfg_in, output logic [7:0] acc);
  logic s0, s1, s2, s3, s4, s5, s6, s7;
  logic [7:0] cfg_c;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) begin
      s0 <= 1'b0; s1 <= 1'b0; s2 <= 1'b0; s3 <= 1'b0;
      s4 <= 1'b0; s5 <= 1'b0; s6 <= 1'b0; s7 <= 1'b0;
    end else begin
      s0 <= cfg_in[0]; s1 <= cfg_in[1]; s2 <= cfg_in[2]; s3 <= cfg_in[3];
      s4 <= cfg_in[4]; s5 <= cfg_in[5]; s6 <= cfg_in[6]; s7 <= cfg_in[7];
    end
  sync1s u0 (.clk(cclk), .rst_n(crst_n), .d(s0), .q(cfg_c[0]));
  // ... u1 .. u7, one per bit, identical
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) acc <= 8'h00; else acc <= acc + cfg_c;
endmodule
```

reports:

```
crossings: 8 unsync: 0
  s0(bclk) -> u0.meta(cclk) w=1 direct=True 2nd=['cfg_c[0]'] sync=True
  s1(bclk) -> u1.meta(cclk) w=1 direct=True 2nd=['cfg_c[1]'] sync=True
  ... eight of these, all sync=True
```

Zero findings, exit 0, build passes. Eight bits of one value cross bit by
bit through eight independent two-flop chains, are reassembled into `cfg_c`
and consumed as one eight-bit value by `acc`. That is the structure the
chapter quotes Ginosar calling "a complete loss of data" at `:93` and which
the tool is now said to reject. The difference from the fixture is only how
the sending flops are declared.

The information needed is present: the eight second stages all drive bits of
one net, `cfg_c`. Grouping on the destination value, or on the net the
recognized chains converge into, would catch both forms. Grouping on the
source register's name catches only the form the fixture has.

Two consequences for the text, and they matter more than the code:

1. `:249` describes a rule the code does not implement ("the value they
   carry"). Say what it does: it groups by the sending register.
2. The first review's **required** chapter-side fix — state in the worked
   example that the tool will approve a shape a person has to reject — was
   dropped in favour of the optional code fix. `:262` now says "the only
   reason the tool rejects a structure whose every part is correct is that
   someone anticipated that particular anti-pattern", which tells the reader
   the case is closed. Exercise 6 at `:307` asks the reader to "find a
   structure it would wrongly accept" — and the answer is the same
   anti-pattern the paragraph above it claims is rejected.

### 5.8 The two smaller code-level issues — PARTIALLY FIXED

**`$dffsr` per-bit set/reset: NOT fixed in substance.** `clocks.py:159-160`
now walks every bit of the reset pin, which was the mechanical part of the
suggested fix. The reported reset is still wrong, for two reasons the walk
does not address. `SET` is never examined at all — `reset_tree` picks
`"ARST" if "ARST" in cell.conns else "CLR"` (`clocks.py:147`) and stops.
And the reset walk skips a multiplexer's select (correctly, for a clock),
which is where a `$dffsr`'s real reset sources live. On

```systemverilog
module t_dffsr (input logic clk, set0, clr1, input logic [1:0] d,
                output logic [1:0] q);
  always_ff @(posedge clk or posedge set0 or posedge clr1)
    if (set0)      q <= 2'b01;
    else if (clr1) q <= 2'b10;
    else           q <= d;
endmodule
```

Yosys emits `$dffsr` with `CLR` and `SET` each driven by a mux tree whose
constants are the data and whose *selects* are `set0` and `clr1`. The tool
reports:

```
q: asynchronous active-high sources=['const 0', 'const 1']
   through=['$mux', 'mux']
```

Neither `set0` nor `clr1` appears. A verifier reading that report learns that
the register has an active-high asynchronous reset driven by constants, which
is false. The first review's alternative — "refuse to classify `$dffsr` and
say so" — is still the safer answer.

**The unknown-domain default: FIXED as written.** `clocks.py:230` is now
`if dom_of.get(src, "unresolved clock") == mine: continue`, so an unknown
source is no longer silently folded into the destination's domain. In
practice the branch is unreachable, because `dom_of` is built from
`tree["registers"]`, which covers every register `_data_cone_registers` can
return; the case it was meant to catch surfaces instead as a domain named
after the diagnostic string, which is §5.1's leak.

Verified still correct, for the record: the two `run.out` files match the
chapter's quoted numbers; the `read` example exits non-zero; the connection
graph still reports 3 instances and 15 connections; the FIFO still reports
one domain, no crossings and sixteen unreset `mem[i]` registers.

## 8. Regressions and new limits in the second pass

The second pass changed `tools/dvh/clocks.py`, `tools/dvh/design.py`,
`tools/dvh/cli.py`, `examples/mk/sv.mk`, `examples/common.mk` and
`scripts/check-examples.sh`. Each of the lead's specific questions was

### 8.1 Register naming where names do not collide — no regression

Answered in §5.5. Non-colliding names are byte-identical to before, the
chapter's pinned report text still matches, the FIFO's `mem[i]` naming still
holds, and an aliased bit-blasted vector names correctly. The full test suite
passes (14 tests).

### 8.2 The clock-root heuristic with no primary clock — FAILS

Answered in §5.1. Two cases, both tested:

- **No register on the bare clock port.** `primary_clocks()` finds nothing
  relevant, `clocks.py:106` keeps every gate input, and the pre-fix behavior
  returns: `t_two_gates` gives two domains and a false `BUG` with exit 1; a
  single fully-gated block gives one domain named `clk+en`.
- **A clock that is not a port.** `primary_clocks()` accepts only
  `mod.port_of_bit` entries, so an analog black-box output — a primary clock
  by the chapter's own Definition at `:56` — is not one. `t_pll_clk` leaks
  the diagnostic string into two domain names and reports a false `BUG`.

A **divided clock** is a third case, and it is not a regression but it is a
limit the chapter does not list. `t_div_clk` (a toggle flop on `clk` driving
`clk_div`) reports `{"clk_div": ["q_slow"], "clk": ["clk_div", "q_fast"]}`
and a `BUG` on `q_fast -> q_slow`, a synchronous path. Given that `:258`
proposes gating a build on the exit code and `:280` proposes running it on
every commit, the chapter should say that a derived clock which is not a
gate — a divider, a mux, a PLL output — becomes its own domain and produces
findings that are not bugs.

An inverted clock is fine: Yosys folds `~clk` into `CLK_POLARITY`, so the
port stays the clock root. Tested.

### 8.3 The parallel-synchronizer grouping — two failures

- **False negative.** Answered in §5.4: split the sending flops and eight
  per-bit synchronizers on one eight-bit value pass with zero findings.
- **Two genuinely independent synchronizers from different sources — no
  false positive.** `t_two_indep` (separate `req_b` and `ack_b` source
  registers, each with its own two-flop chain into `cclk`) reports
  `crossings: 2 unsync: 0`. Correct.
- **The same source into different domains — no false positive.**
  `t_same_src_two_dom` (one `req_b`, synchronized into `cclk` and into
  `dclk`) reports `crossings: 2 unsync: 0`, because the group key includes
  `to_domain`. Correct.
- **False positive when two unrelated one-bit controls share one declared
  vector in the sending domain.**

```systemverilog
module t_indep_bits (input logic bclk, brst_n, cclk, crst_n,
                     input logic req_in, mode_in,
                     output logic req_c, mode_c);
  logic [1:0] ctrl_b;
  logic req_m, mode_m;
  always_ff @(posedge bclk or negedge brst_n)
    if (!brst_n) ctrl_b <= 2'b00; else ctrl_b <= {mode_in, req_in};
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) begin req_m <= 1'b0; req_c <= 1'b0; end
    else         begin req_m <= ctrl_b[0]; req_c <= req_m; end
  always_ff @(posedge cclk or negedge crst_n)
    if (!crst_n) begin mode_m <= 1'b0; mode_c <= 1'b0; end
    else         begin mode_m <= ctrl_b[1]; mode_c <= mode_m; end
endmodule
```

reports two `BUG` findings, "2 parallel one-bit synchronizers on ctrl_b; the
bits may arrive in different cycles", and exits 1. There is no bus here and
no coherency requirement between a request and a mode bit; the only thing the
two crossings share is that the designer packed them into one register. The
tool cannot know the difference, which is the chapter's own point — but the
chapter states the opposite at `:262`, where the group check is presented as
the tool being right and structural recognition as failing only by
*accepting* wrong shapes. It also rejects right ones.

### 8.4 `EXPECT_OUTPUT` with characters special to grep — correct

`scripts/check-examples.sh:69` uses `grep -qF -- "$expect_output"`. `-F`
makes the pattern a fixed string and `--` protects a leading `-`. Tested:
`count[3] .* fail` matches only the literal text, and `-Wall` is handled as a
pattern rather than an option. Correct.

The **extraction** on `:53-54` is not, in two ways neither of which the
current examples trigger:

- `sed -E 's/.*=[[:space:]]*//'` is greedy, so an expected string containing
  `=` is truncated at its last one. `EXPECT_OUTPUT := a=b unsynchronized`
  extracts `b unsynchronized`, and the run then passes on the wrong string.
- Unlike `mkvar` on `:46`, it does not strip a trailing `# comment`, so
  `EXPECT_OUTPUT := x  # note` extracts `x  # note` and can never match.
  `EXPECT := fail   # the tool finds the missing synchronizer` in
  `examples/ch03-digital-design/read/Makefile` shows the comment style is in
  use in exactly these files.

Use `sed -E 's/^[^=]*=[[:space:]]*//; s/[[:space:]]+#.*$//'`, or note in
`common.mk` that the value must contain no `=` and no comment.

### 8.5 Smaller code-level observations, not regressions

- `reset_tree` recomputes `primary_clocks(mod)` inside its per-register loop
  (`clocks.py:157`) rather than once, and then filters a *reset* net's gate
  inputs by whether their cone reaches a primary *clock*. That is
  semantically wrong for a reset tree; it is harmless today only because
  reset cones do not normally reach a clock, in which case `carrying` is
  empty and every input is kept.
- `crossings` recomputes `second_stage` by walking every register's `D` cone
  for every (destination, source) pair, and `_reaches` re-walks a cone for
  every gate input. On the chapter's designs this is instant; on the "every
  commit" scale `:280` proposes it is quadratic in registers times cone size.
- `examples/common.mk:16` and its error message on `:54` still list
  `EXAMPLE_LANG` as `sv | cocotb | systemc`, but `examples/mk/python.mk`
  exists and `examples/ch03-digital-design/read/Makefile` uses
  `EXAMPLE_LANG := python`. Documentation lag in a file this pass touched.
- A data cone follows `D` and `EN` only (`clocks.py:170`). A crossing that
  arrives on `SRST`, `ALOAD`/`AD`, `SET` or `CLR` is not looked for. Yosys
  often lowers a cross-domain synchronous reset into a mux on `D`, so the
  common case is caught by accident rather than by design; a memory
  (`$mem*`) in a cone stops the walk with no report.

## 10. Verdict

The prose findings are done: all six unsourced claims, all three constraint
violations, all six attribution findings, all five template deviations and

**Remaining, by finding number:**

- **5.4 (blocking)** — the chapter says the tool rejects eight per-bit
  synchronizers on a bus; declare the sending flops as eight named signals
  instead of one vector and the same anti-pattern passes with zero findings
  and exit 0. The rule at `:249` ("groups ... by the value they carry") is
  not the rule the code applies (it groups by the sending register's name).
  Either group on the value the recognized chains converge into, or restore
  the statement the first review required: the tool will approve a shape a
  person has to reject.
- **5.1 (blocking)** — the gated-clock fix holds only when the gated clock's
  source also drives some register directly through a bare port. Two
  ordinary designs defeat it: two independently gated blocks on one clock
  (two domains, false `BUG`, exit 1) and a clock from an analog black box,
  which is a primary clock by the chapter's own Definition at `:56` but not
  by `primary_clocks()` (diagnostic string leaked into the domain name, false
  `BUG`). Either the code recognizes a non-port clock root, or `:238` states
  the condition.
- **5.2 (blocking)** — the mux-select half is fixed. The latch half is not:
  a one-bit unsynchronized crossing through a latch reports `crossings: 0`,
  and the sentence at `:245` explains the choice backwards. State the blind
  spot instead of claiming the case is handled.
- **5.6** — "strictest lint" survives, and `IMPERFECTSCH` is described as a
  crossing-adjacent warning with nothing in the evidence record behind it.
- **5.8** — a `$dffsr` register's reset is reported as driven by constants,
  with `SET` never examined. Refuse to classify it and say so, or follow the
  mux selects on a reset walk.
- **8.3** — the group check also produces a false `BUG` on two unrelated
  one-bit controls that share one declared vector in the sending domain.
- **8.4** — `EXPECT_OUTPUT` is grep-safe but its extraction truncates any
  value containing `=` and does not strip a trailing comment.
- **8.2** — a divided, muxed or black-box clock becomes its own domain and
  yields findings that are not bugs; the chapter proposes gating a build on
  the exit code without saying so.
- **9.3, 9.5, 9.7, 9.8, 9.9, 9.10, 9.11** — the new material: the waiver
  definition needs the chapter's own explicit voice; "the last four tests"
