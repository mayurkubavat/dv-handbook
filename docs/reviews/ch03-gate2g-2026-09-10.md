**Verdict: blocking findings remain.**

Headline, answering questions (1) and (2) at once:

* **A clock blended with a *divided* clock is reported as "one clock gated
  differently" and the build gate passes on an eight-bit unsynchronized
  crossing between two unrelated clocks — exit 0, and exit 0 again when both
  clocks are declared with `--clock`.** §1.1. This is `gate2f` §1.1's
  mechanism surviving its fix. The fix made a demoted *clock candidate* set
  `clock_ambiguous`; a derived clock is not in either candidate tier, so it is
  demoted silently exactly as before.
* **Two one-bit synchronizers carrying one two-bit value across one clock
  boundary are both reported `known ... two-flop synchronizer`, exit 0**, when
  one of the two sending flops sits behind a clock gate whose enable the
  netlist cannot see into. §1.2. This is the fourth distinct route past the
  per-bit check, and the third review in a row to find one.
* **An eight-bit crossing whose destination is a latch is not reported at
  all**: `"crossings": []`, `crossings: 0`, exit 0. §1.3. `crossings` only ever
  asks the question about flip-flops.
* **The reset walk is the clock walk, and on the ordinary set/reset flip-flop
  it reports the reset source as `["const 0", "const 1"]`** — the real reset
  port is never named. §1.4.

Thirteen printed sentences about the tool do not describe the code, collected
in §1.5.

## 1. Blocking

### 1.1 A clock blended with a divided clock is excused from the gate, declared or not

`clock_candidates` (`tools/dvh/clocks.py:47-86`) builds two tiers of evidence.
**Strong** is a port that drives some register's `CLK` pin with no logic in
between (`:76-81`), or a register whose `Q` bits are *themselves* one of those
`CLK` bits (`:82-84`). **Weak** is any input port (`:85`). `_tier`
(`:89-94`) adds a third strong case, `kind == "unknown"`.

A divided clock that feeds a *gate* rather than a `CLK` pin directly matches
none of them. Its `Q` bit is not in `used_as_clock`, so `:82-84` never adds it;
it is not an input port, so it is not weak; its `Source.kind` is `"register"`,
so `_tier` returns **0**. At the gate, `_walk_to_sources`
(`clocks.py:165-180`) keeps only the best tier, records the rest as
`gated by ...`, and sets `ambiguous` from `any(t >= 1 ...)` (`:178-179`) — which
a tier of 0 does not satisfy. The demotion is therefore silent, and
`same_clock_source` (`clocks.py:559-565`) sees one shared root bit and drops
the crossing out of `unrecognized` (`:586-587`).

The chapter's own definition makes this a clock, not an enable:
`chapters/ch03-digital-design-for-verifiers.qmd:56` — "A **derived clock** is
any signal produced from another clock by the network in between." And
`clocks.py:52-55`, a docstring the book prints at `:246`, claims the code
already handles it: "**Strong**: the net already drives some register's clock
pin directly, **or is a register output used as a clock (a divider)**". The
code only recognizes a divider that drives a `CLK` pin *directly*. A divider
that is blended or gated — the only way a divider can produce a *new* domain —
is invisible to it.

```systemverilog
// divblend.sv -- Plassan's blending, with the second clock a divider.
// clk2div is a divide-by-two of clk2, an independent asynchronous clock.
// It is a *derived clock* by the chapter's own definition.  It drives no
// register's clock pin directly, so it is not in the `strong` set; it is a
// register output, so it is not an input port and not in `weak` either.
module divblend (input logic clk1, clk2, input logic [7:0] d,
                 output logic [7:0] q);
  logic clk2div, gclk;
  logic [7:0] a, b;
  always_ff @(posedge clk2) clk2div <= ~clk2div;
  assign gclk = clk1 & clk2div;            // blend clk1 with clk2/2
  always_ff @(posedge clk1) a <= d;        // clk1 domain
  always_ff @(posedge gclk) b <= a;        // blended domain, 8 bits, no sync
  assign q = b;
endmodule
```

`gclk` rises either when `clk1` rises with `clk2div` high — a `clk1` edge — or
when `clk2div` rises with `clk1` high, which is an edge placed by `clk2` and
bears no timing relationship to `clk1` at all. `b` therefore samples `a` at an
arbitrary point in the `clk1` period. Eight bits, no synchronizer.

```
$ PYTHONPATH=tools conda run -n dvbook python -m dvh.cli read divblend divblend.sv

  clk1#2: 1 registers
  clk1#21: 1 registers
  clk2: 1 registers

  a  [divblend.sv:12]
  b  [divblend.sv:13]
  clk2div  [divblend.sv:10]

  CHECK a (clk1#2) -> b (clk1#21), 8 bits, no synchronizer shape  [divblend.sv:13]
instances: 0, connections: 0
$ echo $?

```

**Declaring the clocks does not help, which is the worse half.** The chapter
(`:242`) says a declaration means "nothing is left undecided", and
`clocks.py:70-71` says "a declared name is the only strong evidence, everything
else is control, and nothing is left to a guess". With `declared` non-empty,
`clock_candidates` returns `(set(declared), set())` (`:73-74`) — the weak tier
is *empty*, so `_tier` can only return 2 or 0, and `ambiguous` at `:178-179`
can never fire from a demotion. Declaring both real clocks makes the answer no
better, and declaring a name that does not exist makes it *correct*:

```
$ ... read divblend divblend.sv --clock clk1 --clock clk2
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (clk1#2) -> b (clk1#21), 8 bits, no synchronizer shape  [divblend.sv:13]
$ echo $?
0

$ ... read divblend divblend.sv --clock clk1
  ... identical, exit 0

$ ... read divblend divblend.sv --clock nosuchclock
clock domains: 3
  clk1: 1 registers
  clk1+clk2div: 1 registers
  clk2: 1 registers
crossings: 1, shape not recognized: 1
  CHECK a (clk1) -> b (clk1+clk2div), 8 bits, no synchronizer shape  [divblend.sv:13]
$ echo $?
1
```

A misspelled declaration gives the right answer and a correct one gives the
wrong answer. That inversion is worth stating on its own: the declaration
feature, as built, can only ever *remove* findings, and it removes this one.

`crossings --validate` names the mechanism:

```json
{"to": "b", "to_domain": "clk1#21", "from": "a", "from_domain": "clk1#2",
 "width": 8, "direct": true, "second_stage": [], "shape_recognized": false,
 "same_clock_source": true, "note": "no synchronizer shape"}
```

with `"unrecognized": []`. `clock-tree` shows the demotion and shows that it
was never flagged:

```json
"b": {"clock_sources": ["clk1"], "gated_or_muxed": true,
      "through": ["$and", "gated by clk2div"],
      "clock_ambiguous": false, "root_bits": ["2"], "domain": "clk1#21"}
```

**This falsifies printed sentences.** `:238` — "Strong evidence is that the net
already drives some register's clock pin, **or is a divided clock**, or is
something the netlist cannot see into" — is false of the code for any divider
that does not drive a `CLK` pin directly, which is every divider that matters
to this analysis. `:296` — "Where they do not, as with a divider or a
multiplexer between two clocks, it does fail" — is false of `divblend.sv`, in
which there is a divider between two clocks and it does not fail. `:242`'s
"nothing is left undecided" is true but for the wrong reason: nothing is
undecided because the weak tier is empty, so a wrong decision is made in
silence.

**Fix.** Two, complementary.

1. Extend the strong tier from "a register whose `Q` is a `CLK` bit" to "a
   register whose `Q` reaches a `CLK` bit through the clock-tree pass-through
   set" — the walk that answers that question is already written
   (`_walk_to_sources` with `any_comb=False`). Then `clk2div` is strong,
   both inputs of the gate are carried, the register has two root bits, and
   `same_clock_source` is false. This also makes `clocks.py:52-55` true.
2. Independently, `same_clock_source` must not be satisfied by a cone that
   demoted anything: require `not tree["registers"][name]["gated_or_muxed"]`
   on *both* ends, or compare the `through` lists. Two nets that reach one
   root only because a walk discarded a different root have not been shown to
   be one net. That is a two-line change and closes the exit-0 hole on its own.

Fixture: `divblend.sv`.

### 1.2 `shape_recognized: true` on two one-bit chains carrying one value — the fourth route

`_flag_parallel_synchronizers` (`clocks.py:368-459`) has two rules. `gate2f`
§1.3 moved the second from the domain key to the clock *roots*
(`boundary`, `clocks.py:439-442`), keyed on
`(frozenset(from root_bits), frozenset(to root_bits))`. A frozenset is still a
derived key, and it still splits: a sending flop whose clock gate carries an
input the walk cannot see into gets **two** root bits, not one, so its chain
lands in a group of its own and neither rule fires.

The opaque input is not exotic. `_tier` (`clocks.py:92`) treats
`kind == "unknown"` as strong evidence of a clock, and `_walk_to_sources`
returns `"unknown"` for any net driven by a cell outside `PASS_THROUGH`
(`clocks.py:198`) — an adder, a multiplier, a shifter, a memory read port, a
black box. A clock gate enabled by a bit of an arithmetic result is ordinary
RTL. Both inputs are then tier 2, both are carried (`:169-171` never demotes
when the tiers tie), `ambiguous` stays false, and the register's `root_bits`
has two entries.

```systemverilog
// mixroot.sv -- a two-bit value crossing on two one-bit synchronizers.
// Both sending flops are on aclk; one of them sits behind a clock gate whose
// enable the netlist cannot see into (an $add output).  Each chain is a
// correct two-flop synchronizer; together they are the loss of data
// @sec-ch03-cdc describes.  The value leaves through the ports, so no
// register inside reads the two chains together.
module mixroot (input logic aclk, bclk,
                input logic [3:0] x, y,
                input logic d0, d1,
                output logic o0, o1);
  logic [4:0] sum;
  logic g1, a0, a1, p0, p1, r0, r1;
  assign sum = x + y;
  assign g1  = aclk & sum[0];
  always_ff @(posedge aclk) a0 <= d0;
  always_ff @(posedge g1)   a1 <= d1;
  always_ff @(posedge bclk) begin p0 <= a0; p1 <= a1; end
  always_ff @(posedge bclk) begin r0 <= p0; r1 <= p1; end
  assign o0 = r0;
  assign o1 = r1;
endmodule
```

```
$ PYTHONPATH=tools conda run -n dvbook python -m dvh.cli read mixroot mixroot.sv
clock domains: 3
  aclk: 1 registers
  aclk+sum (driven by $add): 1 registers
  bclk: 4 registers
registers without reset: 6
  ...
crossings: 2, shape not recognized: 0
  known a0 (aclk) -> p0 (bclk), 1 bit, two-flop synchronizer  [mixroot.sv:17]
  known a1 (aclk+sum (driven by $add)) -> p1 (bclk), 1 bit, two-flop synchronizer  [mixroot.sv:17]
instances: 0, connections: 0
$ echo $?
0
```

Identical output, and exit 0, with `--clock aclk --clock bclk`. The JSON:

```json
{"to": "p1", "from": "a1", "from_domain": "aclk+sum (driven by $add)#21",
 "width": 1, "direct": true, "second_stage": ["o1"],
 "shape_recognized": true, "same_clock_source": false, "note": ""}
{"to": "p0", "from": "a0", "from_domain": "aclk#2",
 "width": 1, "direct": true, "second_stage": ["o0"],
 "shape_recognized": true, "same_clock_source": false, "note": ""}
```

`"unrecognized": []`. Two bits of one value, synchronized bit by bit across one
physical clock boundary, reported as two recognized two-flop synchronizers.

**This falsifies printed sentences.** Exercise 6 at `:329` — "The tool rejects
parallel one-bit synchronizers across a clock boundary, because someone
anticipated that anti-pattern — three times, after three designs walked past
the first three versions of the check" — is false of `mixroot.sv`, which is
parallel one-bit synchronizers across a clock boundary and is accepted. `:291`'s
taxonomy is one round behind for the same reason: "parallel one-bit chains
carrying one value — three times, by three routes, the last of them two clock
gates off one clock" is now four routes.

**Fix.** The four versions of this check have keyed on a declared name, on a
downstream reader, on the domain pair, and now on the root-bit set. Each is a
*derived* key and each has split. The thing that does not split is the question
the rule is actually asking: do these two chains cross between the same two
physical clock networks? Key rule 2 on a canonical clock identity — the set of
strong roots reachable from each end's `CLK` pin, with demoted and
opaque-driven inputs excluded rather than added — or, more simply, on the
*intersection* of the two ends' root-bit sets being non-empty, which is a
grouping relation rather than an equality and does not split when one end
picks up an extra root. Fixture: `mixroot.sv`.

### 1.3 A crossing whose destination is a latch is not reported at all: `crossings: 0`, exit 0

`crossings` (`tools/dvh/clocks.py:521-523`) builds `by_name` from
`registers(mod)` and iterates it, and `registers` (`tools/dvh/design.py:310-311`)
yields only cells whose type is in `DFF_TYPES` (`design.py:25-28`). A latch is
not in that set. `clocks.py:29-34` states the design intention for latches — "a
path through one is never direct, so it can never be a synchronizer; but
stopping at a latch would hide the crossing behind it, so the data walk passes
through and records the latch" — and that is true of a latch *in the middle* of
a path. A latch at the *end* of one is never asked about, because the loop that
asks the question only visits flip-flops.

```systemverilog
// latchend.sv -- the receiving element is a latch, not a flip-flop.
module latchend (input logic aclk, bclk, input logic [7:0] d,
                 output logic [7:0] q, output logic ben);
  logic [7:0] a;
  logic en;
  always_ff @(posedge aclk) a <= d;      // aclk domain
  always_ff @(posedge bclk) en <= ^d;    // bclk domain
  always_latch if (en) q <= a;           // a (aclk) captured on a bclk enable
  assign ben = en;
endmodule
```

Eight bits leave the `aclk` domain and are captured by a transparent latch
whose enable is a `bclk`-domain register. The latch opens and closes on `bclk`
timing over data that moves on `aclk`: the enable edge can land anywhere in
`a`'s transition, which is the setup/hold violation of @sec-ch03-metastability
with no synchronizer anywhere. The tool reports the design as clean:

```
$ PYTHONPATH=tools conda run -n dvbook python -m dvh.cli read latchend latchend.sv
clock domains: 2
  aclk: 1 registers
  bclk: 1 registers
registers without reset: 2
  a  [latchend.sv:6]
  ben  [latchend.sv:7]
crossings: 0, shape not recognized: 0
instances: 0, connections: 0
$ echo $?
0
```

Identical, exit 0, with `--clock aclk --clock bclk`. And the JSON is empty, not
merely unflagged:

```
$ ... crossings latchend latchend.sv --validate
{
  "crossings": [],
  "unrecognized": []
}
```

The netlist has the latch; only the tool does not look at it:

```
$ yosys -p "read_verilog -sv latchend.sv; hierarchy -check -top latchend; \
    proc; opt_dff; memory_collect; memory_map; flatten; opt_clean; stat"
=== latchend ===
        4 cells
        2   $dff
        1   $dlatch
        1   $reduce_xor
```

The escape route is the one the chapter already worries about for per-bit
chains: the latched value leaves the block through a port, so no flip-flop
inside this netlist ever reads it. Put a `bclk` flop on `q` instead and the
crossing *is* found, through the latch, exactly as `clocks.py:29-34` promises —
which is what makes this a gap in the destination set rather than in the walk.

Latch-terminated paths are not exotic: retention and isolation latches on a
power domain boundary, level-sensitive legacy interfaces, and the enable latch
of a clock gate are all of this shape, and the last of those is a structure the
chapter names in its own text (`:63`, "A clock gate is normally built with a
latch").

**This falsifies printed sentences.** `:268` — "Notice what the report does not
say... It says one matches a shape it recognizes and two do not, which is a
fact about structure" — and `clocks.py:515-517`, printed at `:246`: "**Nothing
is ever suppressed**, and where the walk cannot resolve a clock it says so."
Here a crossing is not suppressed by a rule; it is never constructed, and the
report contains no trace that a state element it does not model exists in the
design at all. `:291`'s taxonomy lists "because a walk stopped at a latch, or
passed through one by its data input only" — a *third* latch route is now open
and the sentence does not cover it.

**Fix.** Two parts, and the first is cheap.

1. Treat a latch as a crossing destination. `LATCH_TYPES` is already defined
   (`clocks.py:33-34`); a latch's domain is not a clock domain, but the
   question "does this latch's data come from a register whose clock differs
   from the domain of whatever drives its enable" is answerable with the walks
   already written, and the answer belongs in `crossings` with
   `shape_recognized: false` and a note saying the destination is a latch.
2. Failing that, make the silence impossible: count the latch cells in the
   flattened netlist and print them, so `crossings: 0` on a design holding
   eight bits in a `$dlatch` is not the whole of what the reader is told. A
   tool whose contract is "a fact about structure" must not omit a state
   element from the structure.

Fixture: `latchend.sv`.

### 1.4 The reset walk applies the *clock* heuristic to a reset net, and reports a reset source that is false

`reset_tree`'s inner `control` (`tools/dvh/clocks.py:299-307`) walks each reset
pin with `_walk_to_sources(mod, b, None, False, prim)` where `prim` is
`clock_candidates(...)` (`clocks.py:297`). That is the *clock* walk. Two of its
rules are wrong on a reset net, and both are reached by ordinary RTL.

**(a) A multiplexer's select is skipped — but on a reset net the select *is* the
reset.** `clocks.py:146-150` drops port `S` whenever `any_comb` is false, and
`clocks.py:160-163` then computes `roots` from the remaining inputs only. For
the standard set/reset flip-flop Yosys builds the `CLR` and `SET` nets out of
`$mux` cells whose select carries the reset:

```systemverilog
// sr.sv -- the ordinary asynchronous set/reset flip-flop.
module sr (input logic clk, s, r, input logic d, output logic q);
  logic v;
  always_ff @(posedge clk or posedge s or posedge r)
    if (r) v <= 1'b0; else if (s) v <= 1'b1; else v <= d;
  assign q = v;
endmodule
```

Yosys's own netlist, with the tool's own script, shows `CLR` driven by
`$mux(A=0, B=1, S=r)` — that is, `CLR = r`:

```
$mux $auto$proc_dff.cc:78:gen_dffsr_complex$12
   conns {'A': ['0'], 'B': ['1'], 'S': [4], 'Y': [9]}      # bit 4 is port r
$dffsr $procdff$14
   conns {'CLK': [2], 'CLR': [9], 'D': [5], 'Q': [6], 'SET': [8]}
```

The tool reports the reset as coming from two constants, and never names `r` or
`s` at all:

```
$ PYTHONPATH=tools conda run -n dvbook python -m dvh.cli reset-tree sr sr.sv --validate
{ "registers": { "q": {
      "kind": "asynchronous", "active": "high",
      "sources": [ "const 0", "const 1" ],
      "through": [ "$mux", "ambiguous: clock not distinguishable here",
                   "mux" ],
      "controls": [ { "pin": "CLR", "kind": "asynchronous", ...
                      "sources": [ "const 0", "const 1" ], ... },
                    { "pin": "SET", "kind": "asynchronous set", ...
                      "sources": [ "const 0", "const 1" ], ... } ] } },
  "no_reset": [] }
```

`reset-tree.schema.json` calls `sources` "Sorted roots of the reset net", and
`clocks.py:279`, a docstring the book prints at `:246`, calls the output
"Every register's reset: kind, polarity, **source**". Here the source is
reported as a pair of constants. That is not an incomplete answer; it is a
wrong one, in the field a reader of @sec-ch03-reading step 3 is told to read
("Kind, polarity, source, synchronizer, release order", `:184`). It also prints
the string `"ambiguous: clock not distinguishable here"` inside a *reset*
report, where the word "clock" is simply wrong.

**(b) The evidence tiers demote a real reset source.** For a reset built from
an external reset and a software-controlled soft reset — an entirely ordinary
reset tree — the soft reset is a register output, so `_tier` gives it 0
(§1.1's mechanism), the external reset is a port, so it gets 1, and `:171-180`
keeps only the port and records the other as gating:

```systemverilog
// softrst.sv -- the reset tree of an ordinary block: an external reset
// combined with a software-controlled soft reset held in a register.
module softrst (input logic clk, rst_n, input logic wr,
                input logic d, output logic q, output logic sr);
  logic soft, rst;
  always_ff @(posedge clk) soft <= wr;      // soft reset, a register
  assign rst = ~rst_n | soft;               // either resets the block
  logic v;
  always_ff @(posedge clk or posedge rst)
    if (rst) v <= 1'b0; else v <= d;
  assign q = v;
  assign sr = soft;
endmodule
```

```
$ ... reset-tree softrst softrst.sv --validate
"q": { "kind": "asynchronous", "active": "high",
       "sources": [ "rst_n" ],
       "through": [ "$not", "$or", "gated by soft" ], ... }
```

Two signals reset this register and the report names one. `soft` survives only
in `through`, as `gated by soft` — a phrase that describes a clock gate and
means nothing about a reset. A verifier asking "which resets reach this
register, and in what order are they released" (exercise 7, `:330`) is given
half the answer in the field that answers it.

**Fix.** The reset walk must not be the clock walk. Call `_walk_to_sources`
with `clock_roots=None` for reset pins — every input that reaches the pin is a
reset source, there is no clock to separate from an enable — and let the `$mux`
select be followed, which `skip_select` (`clocks.py:146`) already keys on
`any_comb` rather than on a flag that says which kind of net is being walked.
The cleanest form is a third mode: `any_comb=False` for the *cells* walked
through, `skip_select=False` and no tier filtering, because "which nets reach
this pin" is the whole question for a reset. Fixtures: `sr.sv`, `softrst.sv`.

## 3. Serious (not blocking, but they belong in the next patch)

### 3.1 `_walk_to_sources` is still recursive, so a deep *clock* cone still ends in `RecursionError`

`gate2f` §2.1 was fixed in `_data_cone_registers`, which is now iterative
(`clocks.py:334-365`, and its docstring says why). `_walk_to_sources`
(`clocks.py:97`) — the clock and reset walk — still recurses once per net bit,
so the same cone on a *clock* net ends the run:

```systemverilog
// deepclk.sv -- a 1500-level XOR chain between bclk and a register's clock.
module deepclk (input logic aclk, bclk, input logic d, e, output logic q);
  logic [1500:0] c;
  logic a, b;
  always_ff @(posedge aclk) a <= d;
  assign c[0] = bclk ^ e;
  assign c[1] = c[0] ^ e;                 // ... 1500 of these
  always_ff @(posedge c[1500]) b <= a;
  assign q = b;
endmodule
```

```
$ PYTHONPATH=tools conda run -n dvbook python -m dvh.cli read deepclk deepclk.sv
dvh: RecursionError: maximum recursion depth exceeded
dvh: this is a defect in the tool, not a finding about the design
$ echo $?
2
```

Not blocking, for the reason `gate2f` gave and `:302` states: this is the
three-way exit contract working, and a gate stops. Listed because the fix is
the one already applied next door, and because `_tier` (`clocks.py:91`) calls
`_walk_to_sources` from inside the recursion, so the effective depth limit is
lower than the chain length suggests.

### 3.2 A register with no reset at all is reported as having one: `registers without reset: 0`

`RESET_PINS` (`clocks.py:271-275`) includes `ALOAD`, and `reset_tree`
(`clocks.py:282-285`) puts any register carrying one of those pins into
`registers` rather than into `no_reset`. `clocks.py:269-270` states the
opposite intent in terms: "An asynchronous load is reported as what it is: it
forces a value, not a constant, so it is not a reset and a reader should not
read it as one." The `read` report does exactly what that sentence forbids:

```systemverilog
// aload.sv -- one register, asynchronously loaded, with no reset at all.
module aload (input logic clk, ld, input logic [7:0] d, v,
              output logic [7:0] q);
  logic [7:0] r;
  always_ff @(posedge clk or posedge ld)
    if (ld) r <= v; else r <= d;
  assign q = r;
endmodule
```

```
$ ... read aload aload.sv
clock domains: 1
  clk: 1 registers
registers without reset: 0
crossings: 0, shape not recognized: 0
```

The JSON is honest — `"kind": "asynchronous load"`, `"no_reset": []` — but the
human report, which is the artifact the chapter presents as the gate, says the
design has no unreset registers when its only register has no reset. `:129`'s
"The tool later in this chapter reports every unreset register it finds" is
false of this design. Fix: `no_reset` should hold any register whose only
forcing control is a set or a load, or the report should print a third line for
them. Fixture: `aload.sv`.

### 3.3 `(* keep_hierarchy *)` on the *instance* makes the tool unable to answer at all

`design.py:127` strips the attribute with `setattr -mod -unset keep_hierarchy`.
`-mod` reaches modules only, and Yosys's `flatten` honors the attribute on
*cells* as well. The belt-and-braces check at `design.py:283-288` then fires,
which is the right outcome given the input — but it means the ordinary way of
keeping one instance out of a flatten turns the whole analysis off:

```systemverilog
module cellkeep (input logic aclk, bclk, input logic [7:0] d,
                 output logic [7:0] q);
  (* keep_hierarchy *)
  lane3 u_lane (.aclk(aclk), .bclk(bclk), .d(d), .q(q));
endmodule
```

```
$ ... read cellkeep cellkeep.sv
dvh: cellkeep still instantiates lane3 after flattening, so the registers
     inside them would not be analyzed at all
$ echo $?
2
```

Loud, so not blocking. Fix: add `setattr -unset keep_hierarchy` (no `-mod`)
alongside the module form, which reaches cell attributes. One extra word in the
script. Fixture: `cellkeep.sv`.

### 3.4 `--clock` is accepted without any check that the names exist

`_main` (`cli.py:131-137`) passes `args.clock` through untouched, and
`clock_candidates` (`clocks.py:73-74`) turns it into `strong` with an empty
`weak`. Nothing tests that a declared name is a port of the design, and nothing
reports a port that drives a `CLK` pin and was *not* declared. The
consequences, all demonstrated above:

* A typo declares nothing, so every tier is 0, no gate demotes, and the run is
  *more* conservative than an undeclared one — `divblend.sv --clock nosuchclock`
  exits 1 where `--clock clk1 --clock clk2` exits 0 (§1.1).
* An incomplete list silently reclassifies the clocks left out as control.
  `divblend.sv --clock clk1` is byte-identical to declaring both.

The chapter sells the option as the thing that "turns a guess into an answer"
(`:298`). An answer that changes silently with a misspelling needs a diagnostic:
fail with exit 2 when a declared name is not an input port of the top module,
and print a warning naming every port that drives a `CLK` pin directly and was
not declared.

### 3.5 Three schema descriptions are falsified by the code

`tools/dvh/schema/crossings.schema.json` and `clock-tree.schema.json` are the
published contract, and `appendices/appI-agent-tool-layer.qmd:204` prints the
first of them and tells the reader the descriptions are where the tool records
what it cannot decide.

| file | keyword | text | falsified by |
|---|---|---|---|
| `clock-tree.schema.json` | `clock_ambiguous.description` | "True when clock and enable were not separable." | `divblend.sv`, `gatedreg.sv`: not separable, reported `false` (§1.1) |
| `crossings.schema.json` | `same_clock_source.description` | "Both clocks resolve to one net, as a gate does." | `divblend.sv`: two clocks, one of which the walk discarded (§1.1) |
| `crossings.schema.json` | `shape_recognized.$comment` | "Two-flop, and not one of several carrying one value." | `mixroot.sv`: two chains carrying one value, both `true` (§1.2) |

### 3.6 `reset_tree` recomputes `clock_candidates` once per register

`clocks.py:297` sits inside the `for name, cell in registers(mod)` loop that
starts at `:281`, and `clock_candidates` walks `registers(mod)` twice
(`:76-84`). That is O(n²) in the register count for a value that cannot change
between iterations. It is not currently visible — `bigrst.sv`, 4096 reset bits,
runs in 1.52 s, because Yosys keeps a wide register as one cell — but a
bit-blasted reset tree of the same size would pay for it, and hoisting the call
above the loop is a one-line change. Note also that the reset walk is the only
caller that passes `declared` this way; `cli.py:158` does not pass `declared` to
`crossings` at all (see §4.3).

## 7. Answers to the questions asked

**1. Can a real crossing be made to disappear, or the gate made to pass on one?
Yes, three ways, and two of them survive `--clock`.**

* `divblend.sv` (§1.1): `gclk = clk1 & clk2div`, where `clk2div` divides an
  independent clock. Printed and excused as "one clock gated differently",
  exit 0 — with no declaration, with `--clock clk1`, and with
  `--clock clk1 --clock clk2`. A *misspelled* declaration is the only one of
  the four that gives the right answer.
* `latchend.sv` (§1.3): the crossing's destination is a latch. `"crossings":
  []`, exit 0, declared or not.
* `gatedreg.sv` (§1.5, same mechanism as §1.1): an ordinary clock gate whose
  enable is a register is excused with no declaration at all, which is what
  `:298` says cannot happen. Here the excusing is the *right* answer and the
  reasoning that produces it is the same reasoning that produces `divblend.sv`;
  the tool cannot tell the two apart and is silent in both.

**2. Can the tool be crashed, or `shape_recognized: true` be made false, or a
source location made to point at the wrong line?**

* Crash: yes, `RecursionError` on a 1500-level *clock* cone — exit 2 with "this
  is a defect in the tool, not a finding about the design" (§3.1), which is the
  contract working. `gate2f`'s data-cone case is fixed. Bad top, missing file,
  duplicate file and unparsable RTL all exit 2.
* `shape_recognized: true` on a non-synchronizer: yes, `mixroot.sv` (§1.2), two
  one-bit chains carrying one two-bit value, both `known`, exit 0, declared or
  not.
* Wrong source location: **no.** See §5.
* Pathological run time: **not found.** `gate2f` §2.2 is decisively fixed — a
  1024-entry × 32-bit dual-clock RAM now runs in 4.60 s against "killed after
  43 minutes".

**3. The previous round's findings.** All three blocking and five of six
serious findings of `gate2f` are fixed, verified by re-creating and running the
reviewer's own designs. §2 has the table. The sixth, §2.1, is fixed on the data

**4. Does the chapter describe the code?** Thirteen sentences do not; §1.5 has

four of the five findings above are instances of it.

* **§1.1 is the fourth appearance of "two clocks were treated as one".** The
  fix history is: identity by net rather than by name; `same_clock_source`
  comparing root bits rather than source names; a demoted *candidate* setting
  `clock_ambiguous`. Each fix closed the case the last review built. What has
  never been fixed is the shape of the rule: an input is demoted unless it can
  produce evidence of clockhood from a fixed list, and the list has now failed
  three times because the list is what a reviewer writes a design against. The
  inverse rule does not have that property: *carry every input unless it can be
  shown to be control*, where "control" means a cone of non-clock registers and
  ports, and let the register have several roots. A false alarm on a clock gate
  is the cost, and `--clock` is exactly the mechanism for paying it down —
  which is the argument `:242` already makes and the code does not implement.
* **§1.2 is the fourth route past the per-bit check**, and the fourth *derived*
  key: declared name, downstream reader, domain pair, root-bit set. Every one
  of them has split under a transformation the previous reviewer did not think
  of. A grouping relation that is a partial overlap rather than an equality
  cannot split that way.
* **§1.3 and §1.4 are new classes, and both are one question the code never
  asks.** `crossings` asks its question only of flip-flops; `reset_tree` asks
  the clock walk's question of a reset net. Neither is a heuristic that was
  tuned wrong; both are a scope that was never stated. §1.3's cheap half — print
  the latch count — and §1.4's fix are each a few lines.
* **The `--clock` declaration, as built, can only remove findings.** It empties
  the weak tier, which disables the one mechanism (`clocks.py:181-184`) that
  reports a tie. Declaring a design's clocks correctly should never produce a
  *less* conservative answer than misspelling them, and on `divblend.sv` it
  does. §3.4.
