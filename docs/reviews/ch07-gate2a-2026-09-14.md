# Chapter 7 (Constrained-Random Stimulus) -- gate-2 review A, 2026-09-14

Independent review of `chapters/ch07-constrained-random.qmd` and
`examples/ch07-constrained-random/` in the working tree, on Verilator 5.052
(2026-09-05) with z3 5.1.0 in `dvbook` and Icarus 13.0. The reviewer never
saw the drafting conversation. Line numbers refer to the `.qmd` as of this
review.

## Verdict

**NEEDS ANOTHER PASS.** Every example builds, runs, and prints exactly what
the chapter splices; the checker is green; every citation key resolves; every
cross-reference label exists; the template is followed. The blocking findings
are all in the prose's claims *about* the tool and its sources, and the largest
one (B1) is a claim the chapter's own example was built to support and that a
one-line change to the example refutes. Eight blocking findings, seven
serious, and a list of minor ones follow. Fix, re-run the seeds example and the
matrix, and send to a fresh reviewer.

## Blocking findings

### B1. `$urandom(seed)` does replay on 5.052; the chapter, the matrix and the summary say it does not

Chapter, seeds section (line 130): *"The third line is the one to remember:
`$urandom(42)` called twice in one thread, with the result used each time, did
*not* replay the values that followed it on this release. On the previous
release the call was optimized away altogether when its result went unused,
which was filed and fixed [@verilator-issue-5703]; on this one it is executed,
and the sequence still differs."* Summary bullet: *"`$urandom(seed)` did not
replay on the release measured."* Tools section (line 152): *"The one *wrong*
cell is the `$urandom(seed)` measurement of @sec-ch07-seeds."* Matrix row 20:
`$urandom(seed)` replays a sequence -- Verilator: **wrong**.

Three statements are false, one is unsupported:

1. *"with the result used each time"* -- `tb_seeds.sv:43,45` write
   `dummy = $urandom(42);` and `dummy` is never read anywhere in the file. The
   probe `r20_urandom_seed.sv` has the same dead store. The result is not used.
2. *"on this one it is executed"* -- it is not, not the first one. I ran the
   probe `r20_urandom_seed.sv` unchanged on 5.052: it prints
   `s1[0]=1604469840 s2[0]=1984119072` and `PROBE r20 FAIL`. `1604469840` is
   the run's first `$urandom()` draw under the default seed (the seeds
   example's own `first draw of this run: 1604469840`), so the first
   `dummy = $urandom(42)` was removed as a dead store exactly as #5703
   describes, and the second (the last write to `dummy`) survived. The same
   probe with both calls written `void'($urandom(42));` prints
   `s1[0]=1984119072 s2[0]=1984119072` and `PROBE r20 PASS`.
3. *"and the sequence still differs"* -- in a plain thread it does not. A
   standalone module with `void'($urandom(42))` twice, or with the result
   printed, replays `1984119072 1719268783 4061232550` after each call, under
   the default seed and under `+verilator+seed+5`. The chapter's own
   `tb_seeds.sv` with the fork section (the `process::self().srandom(11)`
   threads) removed and the calls written `void'()` prints
   `$urandom(42) twice: 1984119072 1984119072 ... same sequence`.
4. What the chapter's testbench actually measured is different and
   unexplained: with the fork section present, even `void'($urandom(42))` and
   even a printed result give `893602905 685465672 ... different`, and a
   standalone module that calls `process::self().srandom(11)` before two
   `void'($urandom(42))` blocks prints two different sequences. So on 5.052,
   once `process::srandom()` has been used, `$urandom(seed)` no longer reseeds
   the generator that `$urandom()` reads; that is the finding, and it is not
   what any sentence in the chapter says.

Consequences: the matrix cell is an artifact of the probe's dead store (the
same optimization #5703 reported, still present for a store that is
overwritten before being read); the *wrong* cell becomes *runs* once the probe
says `void'($urandom(42))`; the "twenty-eight of thirty-one" count (B3) and
the "one wrong cell" sentence change; the "release" attribution in the same
paragraph is wrong (B2). The chapter must either drop the `$urandom(seed)`
claim or measure the construct properly (both calls `void'()`, no earlier
`process::srandom` in the thread) and, if it wants to show the
`process::srandom` interaction, show it as what it is.

### B2. "On the previous release the call was optimized away" (line 130) -- the fix is under 5.034, not 5.050

Change log: `* Fix mis-optimizing away $urandom (#5703). [Parker Schless]` sits
under the header `Verilator 5.034 2025-02-24`. The release before this book's
baseline (5.052) is 5.050 (2026-07-01), which had that fix for five releases.
The bug was in the book's *former* baseline 5.030; the sentence must name
5.030 (or "the 5.030 the book used to measure") and 5.034, not "the previous
release". Compounded by B1: the dead-store removal is still observable on
5.052.

### B3. "twenty-eight of thirty-one constructs" (line 152 and Summary) contradicts the matrix

`matrix.md` caption: *"Of 31 constructs, 2 run on both, 28 on Verilator only,
0 on Icarus only and 1 on neither."* The Verilator column has 30 *runs* cells
and one *wrong* (row 20). Verilator runs 30 of 31; "twenty-eight" is the
Verilator-*only* count and excludes the two rows Icarus also runs. Both
sentences -- *"twenty-eight of thirty-one constructs, including the
distribution forms"* and *"runs twenty-eight of the chapter's thirty-one
constructs"* -- state a wrong number for what the column shows. After B1 is
fixed the true count is 31 of 31 (29 Verilator-only).

### B4. "the distribution the opening bug's reporter expected and did not get, on the release before this one" (line 105) -- the fix is in 5.050

Change log: `* Fix biased bit distribution under value < (1 << N) constraints
(#7563) (#7684). [Yilou Wang]` is under `Verilator 5.050 2026-07-01`. The
release before 5.052 is 5.050, which contains the fix. The reporter measured
master between 5.048 (2026-04-26) and 5.050; issue opened 2026-05-10, PR merged
2026-05-30. Say "before the 5.050 release" or "on the 5.048 release".

### B5. Pitfall (line 110): "the release before this book's baseline issued [CONSTRAINTIGN] for all three of these" -- wrong on either reading

The three are `dist`, `solve … before` and `soft`. Read literally, "the release
before this book's baseline" is 5.050, and none of the three drew
`CONSTRAINTIGN` there: `solve..before` support is under 5.046
(`* Support solve..before constraints (#5647) (#7123)`), `soft` and `dist`
weights under 5.048 (`* Support soft constraint solving (#7124) (#7166)`,
`* Support constraint imperfect distributions (#6811) (#7168)`). Read as
"5.030, the book's former baseline", the research note's Part C measurement
says `dist` and `solve … before` drew `CONSTRAINTIGN` and **`soft` did not**
(§2.4: "No `CONSTRAINTIGN` is printed for `soft` (the r12 build log has no
warning)"; §4.2 table: "`soft` is treated as hard with **no** warning"). So
"all three" is false on 5.030 and the release name is wrong for 5.050. Name
5.030 and say two of the three.

### B6. "the standard does not say the solver must sample it uniformly" (line 98) and "The standard does not promise uniformity either [@ieee1800-2023]" (Pitfall, line 110) -- the only quoted evidence says the opposite

The chapter attributes to IEEE 1800-2023 a negative that nobody on the project
has checked (`refs.bib` note: "clause text not consulted"). The one primary
source the chapter itself cites for this topic, issue #8024
(`[@verilator-issue-8024]`, same Pitfall), quotes the standard, clause 18.5.9:
*"The solver shall assure that the random values are selected to give a
uniform value distribution over legal value combinations (that is, all
combinations of legal values have the same probability of being the
solution)."* The research note flagged this twice (Part B unsourced-claims
table; Part C §3.3: "The chapter's claim that a solver gives 'a uniform
distribution over legal combinations' is the standard's requirement, not what
the installed tool does; it must be phrased that way"). PR #7684's body says
"IEEE 1800-2023 18.5 does not mandate uniform randomization", so the two
Verilator sources disagree with each other; the chapter may report that
disagreement, but it may not cite the standard for a claim contradicted by
the standard's only quoted sentence. The same error is restated in the Summary
("nothing in the language says which. Uniformity is a tool property") and the
opener's "Nothing in the language had been violated". Rewrite around: the
standard (as quoted in #8024) requires uniformity over legal combinations;
what a tool delivers is measured; on this release the measurement is
`49–50%`.

### B7. "a constraint in OpenTitan's base configuration casts two unsigned frequencies to `int` before taking their difference" (line 78) -- the source casts the difference

`cip_base_env_cfg.sv`, fetched today:

```systemverilog
// cast to `int`, as edn_clk_freq_mhz and clk_freq_mhz are unsigned.
int'(edn_clk_freq_mhz - clk_freq_mhz) inside {[-2 : 2]};
```

The subtraction is performed on the unsigned operands and the *result* is cast.
That is a different idiom from the chapter's `int'(a) - int'(b)`
(`tb_arithmetic.sv:43`), and it is called "the production idiom in so many
words". It is not. (It works for OpenTitan because the operands are 32-bit and
the wrapped difference reinterpreted as `int` is the signed difference; for
the chapter's 8-bit fields `int'(8'(a - b))` would never be negative.) Either
describe what OpenTitan does and why it works at 32 bits, or drop the
attribution.

### B8. Opener (line 11): "The test that found it was a coverage measurement, not a failing check" -- the issue says the test failed

Issue #7563 body, first line: *"Uvm test tests/70regs/01fields/03rand fails due
to bits not properly randomizing."* The test counted which bit patterns
appeared over 20 randomizations and failed. The chapter's sentence is the
opposite of the record. The point the chapter wants (a count of what was
generated, made into a check) can be made truthfully.

## Serious

### S1. Opener: "filed a bug against its own constraint solver" (line 11) contradicts "Verilator does not solve constraints itself" (line 86)

The bug was in Verilator's randomizer (the code that turns a model into a
draw), not in a solver Verilator owns. Say "against its own randomizer".

### S2. "three calls returning 0" (line 96) -- the spliced output shows one line, because the runner deduplicates

`run_nosolver.sh:17` pipes the no-solver run through `sort -u`, so the three
identical `randomize() returned 0, len=99` lines collapse to one and the
prose count is not visible in the output. Use `uniq -c`, or print an index in
the testbench, or drop `sort -u` and keep the three lines.

### S3. "the request changed nothing measurable" (line 71) and "still changes nothing measurable for `solve … before`" (Pitfall) -- the numbers beside the sentence say otherwise

Without the request `s == 1` came up 8 times in 2000 (the joint-uniform
expectation is 2000/257 ≈ 7.8); with it, 0 of 2200. Zero is not "nothing
measurable": the request moved the count away from the joint-uniform figure
in the wrong direction, and far from the ~1000 the request asks for. The
research note (Part B §3.4) records that 5.052 disables UniGen2 for
`solve..before`. Say what was measured: neither honored nor neutral.

### S4. "UVM then reseeds every object from a hash of its type name and instance path" (line 132) -- overstated

Per the research note's reading of the 1.2 kit (Part A §4): `uvm_component::new`
calls `reseed()`, `uvm_sequence_item::set_item_context` calls it, and the
sequencer calls it on a default sequence; `uvm_object::new` does not. "Every
component and sequence item", not "every object".

### S5. "every SystemVerilog example in this chapter runs on Verilator, and their Makefiles say so" (line 150); Appendix F line 144 repeats it

No `Makefile` under `examples/ch07-constrained-random/` says the example is
Verilator-only or needs a solver. Five of the eight SystemVerilog examples
(`randomize-check`, `randc`, `arithmetic`, `distribution`, `seeds`,
`packet-stream`) contain no such statement; `constraint-forms` mentions
Verilator only in a lint-waiver comment; `support-matrix` mentions z3. Either
add the line to each Makefile or delete the claim (in both places).

### S6. Summary bullet "Icarus has no `randomize()`; Verilator has it with a solver on the path, and runs twenty-eight of the chapter's thirty-one constructs" -- see B3; and the `$urandom(seed)` bullet -- see B1

### S7. Matrix caption and prose "with the flags the book's build uses" -- the runner adds `-Wno-fatal`

`matrix.py:24-27` appends `-Wno-fatal` to the book's flags so a lint warning
does not become a refusal. That is the right choice, and the caption should
say it (Chapter 6's table may have the same wording; check).
