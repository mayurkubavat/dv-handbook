# Chapter 3 gate-2 re-review (thirteenth pass)

Scope, in the order asked for: (1) make `dvh read` exit 0 on an
unsynchronized crossing between two genuinely asynchronous clocks, with a
complete and correct `--clock` declaration and without one; (2) crash the
tool, make `shape_recognized: true` on a non-synchronizer, or make a source
location point at the wrong line; confirm the multi-driver refusal is loud
and does not fire on a single-driven design; measure run time; (3) re-run
every design quoted in `gate2j`; (4) check the prose against the code as it
stands; (5) house rules.

Method. Every claim about the code below was produced by running the code.
Designs written for this review live in a session scratchpad outside the
repository (`review-k/`); each is quoted in full where it is used. The
fixtures under `tools/dvh/tests/rtl/` were read and never used as evidence,
and the test suite is not treated as evidence that anything works.

`PYTHONPATH=tools`. The command abbreviated `$ dvh` below is
`PYTHONPATH=tools conda run -n dvbook python -m dvh.cli`, run from the
repository root; `exit N` after each run is the exit status.

**Verdict: no blocking findings.**

Headline, answering question (1): **no.** With both clocks declared, every
design written for this round that puts a second clock on any input of
any register cell Yosys can emit -- `$dffsre`'s asynchronous set, a
`$dlatch`'s enable, an `$adlatch`'s asynchronous clear, an `$aldff`'s
load value (re-run from `gate2j`), a `$dffe`'s enable, a gate inside a
submodule, a wired-OR, a tri-state pair -- either fails the gate with the
second clock named in the domain label or is refused with exit 2. Without
a declaration every one of them is undecided and exits 1. The
`SYNCHRONOUS_PINS` exclusion list holds: `D`, `EN` and `SRST` are the
three pins of Yosys's register cell library that are sampled on the clock
edge and no other, and a value arriving on any of the three cannot move
the output between clock edges, so excusing a register whose `EN` is
clk2 (`dffe.sv`, §3.3) is the right answer rather than an escape.

Both blocking findings of `gate2j` are fixed and stay fixed under the
variations tried (§2). The two serious findings there (`clk` in the
control list; the last-driver-wins dictionary) are fixed. Two of the four
carried minors are fixed (trailing whitespace; two of the three
weak-evidence statements now agree); §4.2 and §4.3 carry.

What this round found instead, neither of which is an unsynchronized
crossing between two declared clocks that exits 0, is in §3: a register
cell type the tool does not list (`$ff`, a register with no clock pin)
is dropped in silence rather than refused, so a crossing onto it is never
constructed; and the hidden-clock defense -- the list of ports read as
gating control -- does not name a clock that reaches the gate through a
latch, where it does name one that reaches it through a register.

## 3. Serious (not blocking, but they belong in the next patch)

### 3.1 A register cell the tool does not list is dropped in silence, not refused

`registers()` (`design.py:315-329`) yields only cells whose type is in
`DFF_TYPES` (`:26-29`). Yosys has one more flip-flop cell, `$ff`, a
register with a `D` and a `Q` and no clock pin, which `proc` emits for a
process sensitive to `$global_clock`. It is in neither `DFF_TYPES` nor
`LATCH_TYPES`, so it is not a register to any walk: `clock_tree` never
lists it, `crossings` never asks what feeds it, and `reset_tree` never
reports it as unreset. A crossing onto it does not exist in the report.

```systemverilog
// gclk.sv -- b is a register with no clock pin; a (clk1) feeds it.
module gclk (input logic clk1, clk2, input logic [7:0] d,
             output logic [7:0] q, output logic t);
  logic tog;
  logic [7:0] a, b;
  always_ff @(posedge clk1) a <= d;
  always_ff @($global_clock) b <= a;
  always_ff @(posedge clk2) tog <= ~tog;
  assign q = b; assign t = tog;
endmodule
```

The cells Yosys emits, dumped from the `Module` the tool reads:

```
$dff $procdff$7 {'CLK': ['clk1'], 'D': ['d', ...], 'Q': ['a', ...]}
$ff  $procdff$6 {'D': ['a', 'a', 'a', 'a', 'a', 'a', 'a', 'a'],
                 'Q': ['b', 'b', 'b', 'b', 'b', 'b', 'b', 'b']}
$dff $procdff$5 {'CLK': ['clk2'], 'D': [...], 'Q': ['t']}
registers: ['t', 'a']
```

```
$ dvh read gclk gclk.sv --clock clk1 --clock clk2
clock domains: 2
  clk1: 1 registers
  clk2: 1 registers
registers without reset: 2
crossings: 0, shape not recognized: 0
instances: 0, connections: 0
exit 0
```

Undeclared: the same output, exit 0. Three registers in the design, two
in the report, and no message. Used on a clock path (`gclkgate.sv`: `r`
is a `$ff` toggling itself, `gclk = clk1 & r`, `--clock clk1`) the walk
treats the `$ff` as an ordinary combinational `$` cell at
`clocks.py:201-204`, follows its `D` round to itself, finds it depends on
nothing, calls it control, and exits 0 with `r` in no domain at all.

This is not a crossing between two declared clocks, and `$global_clock`
is a formal-verification construct rather than ordinary RTL, which is why
it is not blocking. It is serious because the chapter's own contract at
`:302` -- "a gate has to be able to tell a finding from a failure" -- and
the `AssertionError` guard in `reset_tree` (`clocks.py:490-495`) exist
for exactly this case, an unanticipated register cell, and the guard is
on the wrong side of the filter: a cell `registers()` never yields never
reaches it. `load_flat` (`design.py:296-306`) already refuses a design
with anything still instantiated; the same refusal belongs on a cell type
the walks cannot classify.

**Fix.** In `_parse` or `load_flat`, raise `DesignError` for any cell
whose type is `$ff` or `$ffe` (Yosys's two clockless flip-flops), naming
the cell; more generally, for any `$`-cell type that is sequential in
Yosys's cell library and is in neither `DFF_TYPES` nor `LATCH_TYPES`.
Fixture: `gclk.sv` under `tests/refused/`.

### 3.2 A hidden clock that reaches the gate through a latch is not listed as gating control

`clock_tree` (`clocks.py:437-460`) lists the ports read as control at a
gate: a demoted *port* by name, and a demoted *register* by the ports
that clock it (`:445-455`, walking `_timing_pins`). A demoted *latch* is
neither -- `by_name` is `dict(registers(mod))`, which holds no latches --
so a clock that reaches the gate only through a latch's enable is
demoted and named nowhere.

```systemverilog
// hidlatch.sv -- hclk never drives a clock pin, so --clock clk1 is
// accepted as complete. It opens a latch whose output gates clk1.
module hidlatch (input logic clk1, hclk, x, input logic [7:0] d,
                 output logic [7:0] q);
  logic flag, gclk;
  logic [7:0] a, b;
  always_latch if (hclk) flag = x;
  assign gclk = clk1 & flag;
  always_ff @(posedge clk1) a <= d;
  always_ff @(posedge gclk) b <= a;
  assign q = b;
endmodule
```

```
$ dvh read hidlatch hidlatch.sv --clock clk1
clock domains: 2
  clk1#2: 1 registers
  clk1#22: 1 registers
registers without reset: 2
  a  [hidlatch.sv:7]
  b  [hidlatch.sv:8]
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (clk1#2) -> b (clk1#22), 8 bits, no synchronizer shape
         [hidlatch.sv:8]
instances: 0, connections: 0
exit 0
```

No `ports treated as gating control` line. Compare `subhidden.sv` (§5),
the same hidden clock arriving through a submodule's gate, which prints
`ports treated as gating control: clk2`, and `hidlatchreg.sv` (§5), where
the latch's output clocks a register that gates clk1: the register is
demoted, its clock walk reaches the latch and stops (`_walk_to_sources`
`:283-285` emits kind `latch`, not `port`), and again nothing is listed.
With `--clock clk1 --clock hclk` the design fails correctly
(`b (clk1+flag)`, exit 1); undeclared it is undecided, exit 1. So the
declaration the tool *accepts* is not the one the specification would
give, which is the situation the list exists to expose, and it does not.

This is the latch twin of `gate2i` §3.1 (the register route), which was
rated serious and fixed by walking the register's pins. It is not
blocking by the brief's own criterion: the complete declaration fails the
design.

**Fix.** In the demoted-net loop at `:442-455`, look the net up among
the module's latch cells as well as its registers, and for a latch walk
every input (`_data_inputs`, which is what `clock_deps` already does at
`:196-200`). Then the chapter's `:242` sentence -- "directly or through
the register it demoted" -- should say "through the register or latch it
demoted". Fixture: `hidlatch.sv` with `--clock clk1` expecting `hclk` in
`ports_treated_as_control`.

### 3.3 A declared clock sampled as data is a crossing the tool could name and does not (carried from `gate2j` §4.1)

`dffe.sv` (a `$dffe` on clk1 whose enable is the clk2 *port*, gating
clk1): declared, exit 0, and correctly so for the register-to-register
question -- `flag` moves only on clk1's edge. But `flag` samples clk2,
an input the declaration says is asynchronous to clk1, with no
synchronizer, and that is the textbook control crossing; it goes
unreported because ports have no domain (`crossings` `:812-821` iterates
registers only). Under a declaration the tool knows more than it uses: a
*declared clock port* has a domain by definition. Still not blocking --
the chapter scopes the tool to register-to-register crossings and its
own design takes its inputs from ports -- but a declared clock is the one
port whose domain is known, and one sentence at `:251` should say the
crossing from it is not looked for. Or look for it: in `crossings`, for
every register, any declared clock bit reachable through
`_data_cone_registers`'s walk that is not the register's own root.

## 4. Minor

### 4.1 Run time grows with receivers times registers, not with crossings

Two arrays of the same order, timed with `/usr/bin/time -p`, declared:

| design | shape | crossings | wall |
|---|---|---|---|
| `ram16k.sv` | 16384 x 1, written on clk1, read register on clk2 | 16384 | **11.7 s** |
| `ramx.sv` | 8192 x 8, written on clk1 from a clk2-registered `wdr`, read on clk1 | 8192 | **65.6 s** |

Half the crossings, five and a half times the time. In `ramx` the
receivers are the 8192 lowered registers, and for each of them
`crossings` (`clocks.py:839-842`) scans every register in the module
calling `_feeds_directly` to find a second stage: 8192 x 8194 calls. In
`ram16k` the receiver is one register with 16384 sources, and the same
scan runs 16384 times over 16386 registers, but every candidate's `EN`
is a real net so `_feeds_directly` returns at its first line. The scan
is quadratic in the register count and only its constant is cheap.
`cProfile` over `crossings` on `ramx.sv` confirms it: 67,108,864 calls
to `_feeds_directly` (8192 x 8192), 164 s of the 186 s profiled.
Neither run is the forty-minute pathology `:291` describes, so this is
minor; the fix is to build "registers fed directly by X" once, as a
dictionary over the module, before the loop, which `_feeds_directly`'s
own comment (`:724-728`) already half-describes.

### 4.2 The chapter's weak-evidence sentence still omits the latch (carried from `gate2j` §4.2)

`clock_candidates` (`clocks.py:62-64`): "an input port, a register's
output or a latch's". `_tier` (`:221`) scores register and latch. Chapter
`:238`: "Weak evidence is that it is an input port or a register's
output". The two code statements now agree with each other; the prose is
one term short. One clause.

### 4.3 A constant is recorded as gating control (carried from `gate2j` §4.3)

`tri1.sv` (a single tri-state driver, `gclk = en ? clk1 : 1'bz`,
`--clock clk1`): `"through": ["gated by const z", "gated by en", ...]`,
exit 0, correct. A constant is not control; `_classify_gate` `:352`
could skip non-integer bits when building `control`. Cosmetic.

### 4.4 A register whose clock is tied off gets a domain named after the constant

`constclk.sv` (a submodule instantiated with `.clk(1'b0)`): `clock
domains: 2`, one of them `const 0: 1 registers`, exit 0. Not wrong -- the
register genuinely never clocks -- but a reader would rather be told the
instance is tied off than see a domain called `const 0`. Cosmetic.
