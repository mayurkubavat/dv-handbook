# 1. Verdict

**blocking findings remain.** Two blockers, three serious findings, six minor.

**B-1 (`appendices/appI-agent-tool-layer.qmd:42`, `:47`).** The previous
blocker was closed by making a location *exist*. It did not make the location
*correct*. Every register that the memory passes lower out of an array now
borrows its location from the clock port in the module header, so the report
names a line that has nothing to do with the register. This is true **on a
fixture this repository already ships** — `tools/dvh/tests/rtl/ram_crossing.sv`,
the fixture added last round to close the previous blocker — where all sixteen
storage registers are reported at `ram_crossing.sv:10.34-10.38`, the token
`aclk` in the port list, while the array is declared on line 12 and written on
line 13. The appendix's *Grounding* paragraph, the sentence the whole argument
rests on, says each register "names the file and line of the RTL that produced
it". For array storage it names the clock port. The suite is 31 green because
the only test that checks a location's *correctness* still runs on the one
design that has no array — exactly the narrowness the previous round fixed for
the *existence* test and left in place for the correctness test.

**B-2 (`:220`).** The vendor sentence that survived this pass: "**AMIQ EDA's
published tool list covers much of what @sec-appI-catalog specifies.**" The
catalog specifies 33 tools. AMIQ's documented list maps onto about six of them
cleanly and three partially, and onto none of the five testbench tools, none of
the five running-and-measuring tools, and one of the four waveform tools. The
research note supports "a programmatic door over a compiled database exists",
which is a different and true claim.

Nothing was edited. Nothing was broken: the book was rebuilt (`rc=0`, 202
pages) and the tool suite and example checks were run, all green.

# 2. B-1: a location that exists, is well formed, and is wrong

## 2.1 What the appendix claims

`:42` — "It does keep a thread back to the source: the netlist records a file
and line for each cell, which is enough to say where a finding came from."

`:47` — "The book's own tools carry the source location the netlist records
into every report: each register in the clock and reset trees, each crossing,
and each instance in the connection graph **names the file and line of the RTL
that produced it**."

## 2.2 What the tool does

Run, from the repository root:

```
$ python3 -m dvh read ram_crossing tools/dvh/tests/rtl/ram_crossing.sv
clock domains: 2
  aclk: 16 registers
  bclk: 1 registers
registers without reset: 17
  mem[0]  [tools/dvh/tests/rtl/ram_crossing.sv:10]
  mem[1]  [tools/dvh/tests/rtl/ram_crossing.sv:10]
  ... (all sixteen)
```

The exact span is `ram_crossing.sv:10.34-10.38`. Line 10 column 34 is the
identifier `aclk` inside `module ram_crossing (input logic aclk, bclk, we, ...`.
The array is `logic [7:0] mem [16];` on line 12; it is written on line 13. A
reader who follows the pointer lands on a port declaration and finds no
register there at all.

The same is true of three designs constructed for this review, none of which is
exotic:

| design | registers | reported at | what is actually there |
|---|---|---|---|
| `regfile_async_read.sv` (asynchronous-read register file) | 8 | `:2.40-2.43` | the `clk` port declaration; `rf` is on line 6 |
| `mem_init.sv` (array with `initial` values) | 16 | `:2.30-2.33` | the `clk` port declaration; `mem` is on line 5 |
| `mem_two_clock.sv` (dual-clock RAM) | 16 | `:2.35-2.39` | the `wclk` port declaration; `mem` is on line 5 |

And the same in a flattened submodule: `sub_array.sv` reports `u_i.m[0..7]` at
`sub_array.sv:11.31-11.34`, the *parent* module's `clk` port, for an array
declared on line 4 of a different module.

## 2.3 Cause

`tools/dvh/design.py:139-153`. `_fill_missing_src` borrows a location from the
first bit the cell touches that has one, outputs first and then **all** inputs:

```python
ordered = ([b for p, bits in cell.conns.items()
            if cell.dirs.get(p) == "output" for b in bits]
           + [b for p, bits in cell.conns.items()
              if cell.dirs.get(p) != "output" for b in bits])
```

For a register that `memory_map` synthesized, the `Q` net is a generated
lowering net with no `src`, and the first *input* bit with one is `CLK`, whose
net is the top-level clock port, whose `src` is the port declaration. The
comment above the code says the borrow is "the same line of RTL"; for these
cells it is not.

The docstring's own premise is also worth correcting. The commit that added
this function made `:42`'s sentence — "the netlist records a file and line for
each cell" — false: the netlist records **nothing** for these cells, which is
why the function exists.

## 2.4 Why the suite stayed green, and this is the part that matters

`tools/dvh/tests/test_ch03.py:330` `test_every_finding_carries_a_real_source_location`
checks that a location is non-blank, relative, starts with a digit after the
colon, and names an existing file. All four hold for `ram_crossing.sv:10.34-10.38`.

`tools/dvh/tests/test_ch03.py:357` `test_the_source_location_points_at_the_right_line`
is the only test that checks whether a location is *right*, and at
`test_ch03.py:364-365` it still loads `TWO_CLOCK` and nothing else — the one
design in the repository with no array. Last round widened
`test_every_fixture_validates_and_is_located` to every fixture and every
command, and left this one on a single design. That is the same defect class,
one level down: the previous round fixed *whether a location is emitted* and
did not fix *whether it is true*.

The test as written would catch it. Running its own helper
`_names_the_construct(src, "always_ff", name)` over every register of every
shipped fixture produces exactly 16 failures, all of them `ram_crossing.sv`, and
zero on the other fifteen fixtures.

## 2.5 Fix

Three parts; the first two are the code, the third is the prose if the code
cannot be made true.

1. **Do not borrow from a control pin.** Exclude `CLK`, `ARST`, `SRST`, `CLR`,
   `SET`, `EN`, `ALOAD` from the borrow candidates in
   `design.py:146-149`. Verified consequence: `ram_crossing` and
   `regfile_async_read` then report *no* location for the array registers rather
   than a wrong one, because no data-side net of those cells carries a `src`
   either. That is honest but it re-opens the previous blocker against the
   schemas' `"pattern": "^[^:]+:\\d+"`, so it is not sufficient alone.

2. **Recover the array's real location.** The location that belongs on these
   registers is the array declaration, which Yosys holds on the `$mem_v2` cell
   before `memory_map` lowers it. Capture it — a second `write_json` after
   `memory_collect` but before `memory_map`, keyed by the memory's name, or a
   `memory_map` invocation that preserves the attribute — and attribute the
   lowered registers to it. This is the fix that makes `:47` true.

3. **Widen the correctness test the same way the schema test was widened last
   round.** `test_the_source_location_points_at_the_right_line` must run over
   every fixture in `tests/rtl` and over the FIFO, not over `TWO_CLOCK` alone,
   asserting for each register that the named span contains either the
   register's declared base name or an `always`/array construct. Without this,
   the next tool change repeats the pattern a fourth time.

4. **If the location genuinely cannot be recovered**, `:42` and `:47` have to
   say so rather than overclaim. `:42` should say the netlist records a file
   and line for each cell the front end wrote, and that cells synthesis creates
   — the registers an array becomes — carry none, so the tool borrows one.
   `:47` should say each register names a file and line and that for lowered
   array storage that line is the declaration the borrow reached, not the
   statement that wrote it. The appendix is already candid about the previous
   gap in this same paragraph; the candour has to extend to the current one.

**Note the shipped fixtures that escape by luck, not by design.**
`examples/ch01-what-is-dv/rtl/fifo.sv` reports its sixteen `mem[...]`
registers at `fifo.sv:34.3-53.6`, a correct `always_ff` span, because that
block's nets happen to carry a location. `tools/dvh/tests/rtl/ram_crossing.sv`
does not. The difference is which net the borrow reached first, not anything a
reader could predict — which is precisely why the report must not print a
location it cannot stand behind.

## A note on the pattern, since this is the fifth round

Three of the last four rounds have found a defect in the same place: a claim in
the *Grounding* paragraph about source locations, falsified by a `tools/dvh/`
change that landed without this page being rechecked. Each fix has closed the
symptom one level down — first the connection graph never read the field, then
the memory passes produced cells with no field, now the borrow produces a field
that is wrong. The common cause is that the appendix states a property of the
tool's *output* while the tests check a property of its *shape*. Until one test
asserts, for every design the repository ships, that a reported location names
the construct it claims to name, the sentence at `:47` will keep going false
without the build noticing. That test costs about ten lines — the helper already
exists at `test_ch03.py:374` — and it is the one change that would let a sixth
round be about something else.
