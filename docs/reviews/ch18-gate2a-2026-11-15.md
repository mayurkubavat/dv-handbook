## Blocking findings

**B1. Line 141: the last step of the decoded path is a write, not a read.**
The prose says the path ends with "a read with the count somehow at zero and
the pointers apart". `kind/run.out` lines 14 to 15: state 2 is
`wr_ptr=1 rd_ptr=1 count=3`, state 3 is `wr_ptr=0 rd_ptr=1 count=0`. The write
pointer moved and the read pointer did not. In
`examples/ch09-temporal-properties/rtl/fifo_fixed.sv` a read moves `rd_ptr`
and decrements `count` (it would give `wr=1 rd=0 count=2`); the step printed is
a write with `count` at 3, which is not `full` (full is `count == 2`), so the
write is accepted and the two-bit count wraps from 3 to 0. The same step
appears in `ic3/run.out` line 11 (predecessor `count=3` of the bad state).
Fix: "and then a write, accepted because a count of three is not *full*,
wraps the count to zero and leaves the pointers apart: the bad state." (The
second path of the figure, line 162, does end with a read; that one is right.)

**B2. Line 395: the lasso trace is cut off after cycle 1.**

`theme/include-code.lua` is 1-based and inclusive). The table has five rows,

cycle 3 and 0 in the last row") and exercise 11 all read rows that the listing

**B3. Line 442 table, its caption, and line 444: the external engine was not
run on the liveness row, and the table says it ran out of time.**
`engine-guide/tbl-engines.md` prints `no verdict in 4 s` under `ric3-ic3` for
"liveness under a fairness assumption", the caption says "*No verdict* is a
statement about the limit, not about the engine", and the prose says "the
external engine returned none". InFormal's `docs/fpv-shell.md` (SVA subset,
on `s_eventually`) says of liveness properties: "External engines are not run
on them", and `docs/engines.md` says rIC3 has no liveness support for Btor2
`fair`/`justice`. The research note records the same (measurement M7: the
external engine returns `undetermined` at once on any liveness property). So
for this one cell the caption's sentence is false, and the reader is told that
a named third-party engine failed to prove something in four seconds that it
was never given. Fix: print "not run" in that cell (the generator
`engine-guide/guide.py` already special-cases the engine at its line 62), add
to the caption "the tool does not send liveness properties to external engines
[@informal-tool]", and change the last sentence of line 444 to say so.

**B4. Line 378: "A depth printed beside a covered cover ... is the length of
the shortest trace to the situation".** False in general and contradicted
twice by the chapter itself: line 99 (`informal-bmc-10` prints depth 66 where
the shortest is 65) and line 409 (the same lasso printed at depth 7 and at 4).
The conclusion drawn from it, "a lower limit on the bound a bounded check ...
needs", then fails too: a non-minimal depth is an upper bound on the shortest
trace, not a lower one. Fix: "When the cover was found by a bounded search
that tries every bound in order, as `informal-bmc` does, the depth is the
length of the shortest trace ...; from another engine it is only the length of
a trace."

**B5. Line 444: "Induction and IC3 found every trace as well, at the same
depths, since both contain a search from reset."** True of induction (its base
case). Not true of IC3 as this chapter defines it (lines 236 to 245): IC3 has
no forward search; it finds a counterexample when a chain of proof obligations
reaches frame 0. The equal depths have a different reason, which the chapter
can state from its own definitions: a frontier $k$ is opened only after every
frame below it holds no bad state, so the chain that reaches frame 0 from
$F_k$ has exactly $k$ steps and nothing shorter exists. As a statement about
the tool's engine it is also unsourced. Fix: "... at the same depths:
induction's base case is a bounded search, and IC3 clears each frontier
before opening the next."

**B6. Sourcing: four claims rest on sources the research note marks as

(a) Line 113, "The term is from Clarke, Kroening, Ouaknine and Strichman

consulted"), the title does not contain the term, and an origin claim needs
the paper. This reviewer's recollection, unverified, is that the term is
already used in Kroening and Strichman's 2003 paper on recurrence diameters.
Fix: read the abstract and first page and say what they say, or write "the
bound is known in the literature as a completeness threshold; see
[@clarke2004completeness]" and drop "the term is from".
(b) Line 34, "introduced under the name *model checking* ... by Clarke and
Emerson and, independently, by Queille and Sifakis": neither text was read,
and "under the name" is a claim about wording; the second title speaks of
specification and verification in CESAR. Fix: "The method now called model
checking was introduced in the early 1980s by ... and, independently, by ...".
(c) Line 310, "certifying model checking results in a common format is the

(d) `refs.bib`, `een2011pdr`: no DOI, no URL, no access date; the note says

**B7. Line 401, Definition of a lasso: the last sentence is false as
written.** "A liveness property over a finite-state system is false exactly
when some lasso violates it: the awaited event does not occur anywhere in the
loop." (i) Absence of the event from the loop is not a violation of
`req |-> s_eventually gnt`: a lasso with a request and its grant on the stem
and an idle loop has no grant in the loop and satisfies the property. The
violation needs a trigger whose grant comes neither later on the stem nor in
the loop. (ii) "Exactly when" holds for properties written in a temporal logic
such as SVA or LTL (every violated one has an ultimately periodic
counterexample on a finite system), not for liveness in the general sense of
the paper cited at line 386. (iii) "State" must include the registers the
tool adds for the property, which the Pitfall at line 409 relies on. Fix: "A
liveness property written in SVA, over a finite-state system, is false exactly
when some lasso violates it. For `a |-> s_eventually b` that is a lasso on
which `a` holds in some cycle and `b` holds in no later cycle of the stem and
in no cycle of the loop. The state that repeats includes the registers the
tool adds to follow the property."

## Non-blocking findings

**N1. Line 113, "For the counter above ... the threshold is of the order of
65,536."** Under the definition at line 110 a threshold is not one number:
for a true property every $k$ is one, and for the bug 1,024 steps away the
least is 1,025. What is of the order of 65,536 is the depth of the deepest
reachable state, which is a threshold for every safety property of the design
and the only kind one can use without knowing the answer. Suggested: "the
deepest reachable state of the counter is about 65,536 steps from reset, and
that depth is the threshold one could rely on without knowing the answer".
The same care for line 113's "computed a threshold directly".

**N2. Lines 152 to 166: the bound at which unique-states induction becomes
complete is given only as $2^n$.** The exact statement is short and explains
the 7: the step case at $k$ is unsatisfiable exactly when no path of $k$
pairwise different good states ends with a step into a bad state, so the
least $k$ that works is one more than the number of states on the longest
such path (at most the recurrence diameter of the system plus one). On the
two-entry model the path is confined to the eight white states (the reachable
set is closed, and a first-cycle state steps only to the empty state), so
$k \le 9$ by counting alone and 7 by the run. The chapter never uses the word
*diameter*; a golden reference should name the recurrence diameter once, in
its own words, without attributing it (the research note forbids attribution
to the 1999 paper).

**N3. Lines 56, 71, 187, 536: "six", "eight" and "fourteen" states are called
inductive or candidate invariants, but by the Definition at line 63 an
inductive invariant contains every initial state**, and the sixteen
first-cycle states are initial. `reach/run.out` says "14 states after reset"
and line 273 says "22 states with the reset cycle's sixteen". Say once, at
line 71, that each candidate is taken together with the sixteen first-cycle
states.

**N4. Line 155, soundness of the constraint.** "Removing a repeated stretch
from a path does not lose a counterexample" is about paths from reset, and
the constraint is on the step case, which does not start in reset. The
argument that fits line 129: a shortest counterexample never repeats a state,
so its last $k + 1$ states are still a model of the constrained step case.

**N5. "Frame" has three meanings and none is flagged.** Line 99 (frames of an
unrolling, as defined in the logic chapter's unrolling Definition), line 212
(an IC3 frame, a set of states), and the tool's lasso comment in
`lasso/run.out` (a cycle of a trace). One sentence at line 212.

**N6. Lines 329 to 332, contradictory assumptions.** The Definition says
"no trace satisfies all of them; then ... every cover is unreachable". The
third case is headed "a contradiction" in `over-constraint/run.out` and its
constant cover is covered at depth 1. The prose explains this with finite
traces that end; name the thing (a *dead end*: a reachable state with no
allowed successor) and say that the verdict on a cover before a dead end is
this tool's behavior at this commit, since a tool that counts only traces
that can be continued for ever would call that cover unreachable.

**N7. Line 295, "induction with unique states and IC3 decide every case".**

row for IC3; IC3's result is only implied by "wrong verdicts ... 0". Print an
IC3 row or soften the sentence.
