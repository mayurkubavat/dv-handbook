## Blocking findings

### B1. `support-matrix/matrix.md` is not reproducible: a clean run and a re-run print different tables

`examples/ch09-temporal-properties/support-matrix/matrix.py:124`
(`warned = "; warns NEVERMATCH" if "NEVERMATCH" in out else ""`) reads the
warning from Verilator's build output. On a re-run over an existing `build/`
Verilator skips the unchanged probe and prints nothing, so the cell loses its
note. The committed `matrix.md` (spliced by the chapter at
`chapters/ch09-temporal-properties.qmd:289`) is the re-run variant; a clean
checkout produces the other one, which is why the working tree showed
`M examples/ch09-temporal-properties/support-matrix/matrix.md` when this
review began.

Evidence (copy of `HEAD`, `make clean` first, `scripts/check-examples.sh
ch09-temporal`, twice from scratch, then once more without cleaning):

```
$ diff committed/support-matrix/matrix.md run1/support-matrix/matrix.md
54c54
< | antecedent that can never match | runs | runs | no build ...
---
> | antecedent that can never match | runs — warns NEVERMATCH | runs — warns NEVERMATCH | no build ...
$ diff -q run1/support-matrix/matrix.md run2/support-matrix/matrix.md   # both clean: same
$ make -s run            # third run, build/ kept: 4.7 s
$ diff committed/support-matrix/matrix.md matrix.md && echo same
same
```

The chapter says the tables "are generated from the probes each time the
examples are checked" (line 287); as shipped, checking the examples on a clean
tree changes a tracked file that the chapter prints.

Fix: make the note independent of whether Verilator re-ran. Either remove the
probe's `Mdir` before building it, or write the build output to a file in
`Mdir` when Verilator runs and read the warning from that file, or take the
warning from a separate `--lint-only` pass. Then regenerate from a clean
`build/` and commit the result. (All other `run.out` files were byte-identical
to the committed ones on both clean runs.)

### B2. Three simulation examples pass when the rule they exist to show is switched off

`fifo-checker/run_checker.sh:25-33`, `vacuity/run_vacuity.sh:11-21` and
`axi-rules/run_axi.sh:21-29` print their `verdict:` line (the
`EXPECT_OUTPUT` string) unconditionally, or accept any failure as the
expected one. In a copy of the tree, with one assertion neutered each time:

```
# fifo_sva.sv:  FullBackward_A  "full |-> occ == 5'(DEPTH)"  ->  "full |-> 1'b1"
$ scripts/check-examples.sh ch09-temporal-properties/fifo-
examples/ch09-temporal-properties/fifo-checker lint=pass    run=pass
examples/ch09-temporal-properties/fifo-formal  lint=pass    run=fail
$ cat fifo-checker/run.out
=== simulation: the original FIFO, same test, same seed
the same run allowed to continue past its failures:
covers:  FullReached_C=0  PushFull_C=69  PopEmpty_C=51  Drained_C=97
verdict: the repaired FIFO passes with every cover hit; the original fails FullBackward_A

# ack_check.sv:  Ack_A  "req |=> ack"  ->  "req |=> 1'b1"
examples/ch09-temporal-properties/vacuity lint=pass    run=pass
  Ack_A failed 0 times        (both runs)
verdict: a pass with the cover at zero proved nothing

# axil_master_sva.sv:  ArHeld_A antecedent "&& 1'b0" added
examples/ch09-temporal-properties/axi-rules lint=pass    run=pass
=== mutant drop: leave the address state after one tick
                              <- no "first: ArHeld_A failed" line
verdict: no rule failed on the design; each mutant failed the rule it breaks
$ grep -o 'Assertion failed in [^:]*' build/drop.log | sort | uniq -c
      1 Assertion failed in tb_v2          <- the testbench's own $fatal, tb_v2.sv:301
```

In `run_axi.sh` the test `grep -q 'Assertion failed' "build/$1.log" || exit 1`
(line 27) is satisfied by the case study's own testbench check, so the
"drop" mutant counts as caught although the bound checker reported nothing.
The chapter says "Each mutant fails the assertion written for the rule it
breaks" (line 452); the build does not enforce it. The formal twins
(`fifo-formal`, `vacuity-formal`, `axi-formal`) and the scripts
`run_handshake.sh` and `run_response.sh` did fail under the same treatment,
which is the behavior wanted.

Fix: make each script test what its verdict line says, and exit 1 otherwise.
`run_axi.sh`: give `mutant` the label it expects and require
`grep -q "Assertion failed in [^ ]*\.$3:"`. `run_checker.sh`: require that
the default run on the original prints `FullBackward_A`, that the long run
names no other label, that every cover on the repaired FIFO is non-zero and
that `FullReached_C=0` on the original. `run_vacuity.sh`: require 0 failures
and `Req_C=0` in the first run, and failures > 0 and `Req_C` > 0 in the
second.

### B3. "`$past` reads zero on the first tick, whatever the reset value" is not true of Verilator in general

The chapter says it three times: line 135 ("returns zero from `$past` there,
whatever the signal's reset value"), line 297 ("On the first tick `$past`
returns zero, not the signal's reset value") and the Pitfall at line 473
("a `$past` that reads zero on the first tick whatever the reset value").
The shipped probe (`support-matrix/probes/p30_past1.sv`) measures one case,
`$past` of a wire. A probe written for this review, on 5.052 and 5.054, with
the book's flags:

```
logic [3:0] r = 4'd5;                    // declaration initializer
always_ff @(posedge clk) if (t == 2) r <= 4'd2;
logic [3:0] q;  initial q = 4'd6;        // set in an initial block
wire  [3:0] w = r;   wire [3:0] tn = ~t[3:0];

t=0  r=5 $past(r)=5 | q=6 $past(q)=0 | w=5 $past(w)=0 | tn=15 $past(tn)=0
t=1  r=5 $past(r)=5 | q=6 $past(q)=6 | w=5 $past(w)=5 | tn=14 $past(tn)=15
assertions claiming $past==0 on tick 0: 1 failed (A_r, A_tn)      # A_r failed
```

For a variable with a declaration initializer, `$past` on the first tick is
the initializer, not zero (identical on both releases). It is zero for a
wire, for a variable set in an `initial` block, and for a register that is
reset by a signal (which on the first edge has not yet been reset: an
`rst_n` that is low from time zero produces no edge in this simulator, so the
register itself still reads 0 there).

Fix: say what was measured. "On the first tick `$past` returned zero for a
net and for a register reset by a signal, and the declaration initializer for
a variable that has one" and add that case to `p30_past1.sv` so the table
carries it. The chapter's advice (write the rule forwards) is unaffected and
is in fact strengthened: the first-tick value depends on how the signal is
declared.

### B4. The caption of the attempts figure miscounts the checks

`chapters/ch09-temporal-properties.qmd:150`: "twice it passed, once it

(`valid && !ready`) holds at ticks 2, 3, 6, 7, 10 and 13 of

### B5. `expect` in `examples/mk/informal.tcl` accepts a refuted property when another instance has the same label

`examples/mk/informal.tcl:11-27`. The comment says "each named property must
have this status ... a name given here matches it by its last component". The
loop keeps the status of the *last* match, so with two instances of one
checker the verdict of all but one is never looked at. The chapter prints
this file (line 351) as what stands between the tool's exit status and a
false pass.

```
module leaf #(parameter bit BAD = 0) (input logic clk, input logic d, output logic q);
  always_ff @(posedge clk) q <= BAD ? ~d : d;
  Same_A: assert property (@(posedge clk) d |=> q);
endmodule
module two (...);  leaf #(.BAD(1)) u_bad (...);  leaf #(.BAD(0)) u_good (...);  endmodule

$ examples/mk/informal.sh two.tcl w2        # two.tcl: prove -all; expect proven Same_A; finish
two.u_bad.Same_A             assert  cex           informal-kind depth 1
two.u_good.Same_A            assert  proven        informal-kind
unexpected count: 0
informal.sh rc=0
```

No shipped script has two properties with the same last component today, so
no committed example passes falsely through this; the helper is the defect.
Fix: collect every match and require all of them to have the status (and
report each one that does not); a full hierarchical name still selects one.

A related hardening, not blocking: a script that omits `finish` exits 0 with
`unexpected:` lines in its report (tested on `fifo.tcl` with `finish` deleted
and one expectation falsified: `make run` exit status 0, verdict line
printed). All six shipped scripts end in `finish`. `informal.sh` could
`grep -q '^unexpected:'` in the report and exit 1, which makes the status
independent of the script's last line.

### B6. "Every testbench in this chapter drives the design's inputs on the falling edge" (line 158) is not what the files do

`fifo-checker/tb_fifo_sva.sv`, `bounded-response/tb_responder.sv` and
`vacuity/tb_vacuity.sv` do (`@(negedge clk)` before each assignment).
`handshake/tb_handshake.sv:14-24` does not: `rst_n`, `valid`, `ready` and
`data` are continuous assignments from a counter clocked on `posedge clk`, so
they change in the rising edge's time step. `goto-miss/tb_goto.sv` builds its
stimulus the same way, as do the matrix probes. Nothing goes wrong there,
because those files contain only concurrent assertions (sampled in the
Preponed region) or registers clocked by the same nonblocking counter, but
the sentence as written is false of two listings the reader has just seen.
Fix: restrict it to the testbenches whose checkers carry monitor registers
(the three named above), or say that the handshake
and goto listings derive stimulus from a clocked counter and why that is
also race-free.

### N3. The Pitfall at line 228 is stronger than the tool's behavior for a contradiction that bites late

"contradictory assumptions prove every assertion". On a one-flop design of
my own (`reset -none`, engine `informal-kind`, same result with
`informal-ic3`):

```
--- contradiction on one tick: sel and !sel
False_A   assert  proven        (sel |=> out != $past(in), false of the design)
Absurd_A  assert  proven        (1'b0)
Sel_C     cover   unreachable
--- contradiction on the second tick: sel, and sel |=> !sel
False_A   assert  proven
Absurd_A  assert  cex           depth 0
Sel_C     cover   covered       depth 0
SelNext_C cover   unreachable   (sel ##1 1'b1)
--- contradiction on the fourth tick: sel, and sel |-> ##3 !sel
False_A   assert  cex           depth 1
Sel4_C    cover   unreachable   (sel ##3 1'b1)
```

So the chapter's specific claim about the two-tick case is right in every
detail (the antecedent cover is reached at depth 0, the `|=>` assertion is
proven, and only the cover that spans the same ticks is unreachable), and
the rule "the cover spans the same ticks as the assertion" is exactly what
the third block shows. But an assertion judged before the contradiction
bites is still refuted, so "every assertion" holds only when the assumptions
conflict on the first tick. With `informal-bmc` alone the same runs print
*undetermined*, not *proven*. Suggested wording: "prove every assertion whose
check reaches the tick where they conflict".

### N4. Registers are arbitrary in the reset cycle only when they have no initializer

Lines 343 and 473. Confirmed on an asynchronous-reset register of my own:
`$past(v && !rdy) |-> v` under `disable iff (!rst_n)` is *cex* at depth 1
(trace: cycle 0 `rst_n=0 v=1`, cycle 1 `rst_n=1 v=0`) and `v && !rdy |=> v`
is *proven*, on `informal-kind` and `informal-ic3`. The same two verdicts
come from a synchronous-reset copy of the register, which supports the
chapter's explanation. With `initial v = 1'b0;` added, the backward spelling
is *proven*: the tool takes a constant `initial` assignment as the register's
starting value (its documentation says so). A reader whose RTL has
initializers will not reproduce the Pitfall; one sentence would cover it.
Also measured: a property with no `disable iff`, `!rst_n |-> !v`, is *proven*
although the trace above has `v=1` under reset, so no property is judged in
the reset cycle, with or without the reset term (line 343 says so only for
properties under `disable iff`).

### N5. The depth is not always the earliest failing cycle

Line 333 ("The depth is the index of the cycle in which the property
fails"). True for every property in the chapter's subset that I ran. For
sequences with a ranged delay the reported depth is the end of the window:
`first_match(a ##[1:3] b) |-> c` with the first match and the missing `c` in
cycle 6 reports depth 7, and `(a ##[1:3] b) |-> c` failing in cycle 4 reports
depth 6. The verdicts were right. Worth a clause only if the reading guide
ever recommends those operators on the formal tool.

### N8. `scripts/check-examples.sh`: the new skip test

`git diff main -- scripts/check-examples.sh` changes one condition:
`[[ -n "$requires" ]] && ! command -v "$requires"`. Attempts to break it:

- `informal` absent: all six formal examples report `run=skipped (informal)`,
  `lint=pass`; `make run` alone prints `skipped: informal is not on the PATH`
  and exits 0. No false pass: the checker never records `pass` for them.
- `informal` present, unexpected verdict (`expect proven FullBackward_A`),
  misspelled property name, or a script error (`clock clkk`): `make run`
  exits 2 and the checker records `fail`. Good.
- `informal` visible to the checker but not inside the `$RUN` environment:
  `informal.sh` would print `skipped` and exit 0, and the `EXPECT_OUTPUT`
  line then turns that into `fail (passed, but without ...)`. All six formal
  Makefiles set `EXPECT_OUTPUT`, so this path is closed. Keep that as a rule
  for future formal examples.
- `command -v` also succeeds for shell builtins, keywords and functions
  (`REQUIRES := time` or `test` would "be on the PATH"). The three values in
  the tree today (`commercial`, `uvm-systemc`, `informal`) are safe.
  `type -P "$requires"` tests for a file and closes the gap.
- A skipped example still has its `run.out` rewritten from whatever
  `run.log` is lying in the directory (line 100). After my mutation
  experiments a later run without `informal` copied the stale failing logs
  into three tracked `run.out` files. Skipped examples should leave
  `run.out` alone.
