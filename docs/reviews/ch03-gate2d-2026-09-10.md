# Chapter 3 gate-2 re-review (sixth pass)

Scope, in the order asked for: (1) make a crossing disappear; (2) make
`shape_recognized: true` false; (3) make the build gate pass on a real
asynchronous crossing; (4) does the chapter describe the code; (5) the residue
`ch03-gate2c` left open; (6) constraints and house rules, plus the new
`scripts/check-citations.sh`.

Method. Every claim about the code was tested by running the code on designs
written for this review. `tools/dvh/tests/rtl/` was read but nothing here rests
on it. Every design is reproduced in full so it can be re-run. Tools: Yosys
0.68+post, the `dvbook` conda environment, `PYTHONPATH=tools`.

Baseline, verified before anything else: `pytest tools/dvh/tests/test_ch03.py`
passes, 27 tests. `scripts/check-citations.sh` prints "citations: no swallowed
references".

**Verdict: blocking findings remain.**

Yes, a crossing still disappears, by a sixth mechanism (§1.1): the data walk
passes through a latch on its `D` port only, so a crossing that arrives on the
latch's *enable* is invisible. `crossings: 0`, exit 0, on a two-clock design —
and it falsifies the sentence at `:249` that says the data walk passes through a
latch precisely so the crossing behind it is not hidden.

`shape_recognized: true` is also assertable of two structures that are not
two-flop synchronizers carrying one value (§1.2, §1.3), and the build gate still
passes on a clock multiplexer between two asynchronous clocks (§1.4) — the case
`:292` says in print does fail it.

Blockers: §1.1 crossing dropped on a latch enable. §1.2 `known ... two-flop
synchronizer` on a chain whose second stage samples the opposite edge. §1.3
`known` twice on a multi-bit value carried on per-bit synchronizers that
converge outside a register. §1.4 build gate silenced on a clock multiplexer
between two asynchronous clocks. §1.5 four chapter sentences that do not
describe the code.

## 1. Blocking

### 1.1 A crossing is dropped: the data walk enters a latch through `D` only

The sixth mechanism. Domain identity is correct here, both clocks resolve, the
memory passes are irrelevant — the *cone* is incomplete.

```systemverilog
// latchen.sv -- the crossing arrives on a latch's ENABLE, not its data.
// `a` is an aclk register; it opens a latch that a bclk register samples.
module latchen (input logic aclk, bclk, rst_n, input logic d, x,
                output logic q);
  logic a, b, l;
  always_ff @(posedge aclk or negedge rst_n)
    if (!rst_n) a <= 1'b0; else a <= d;
  always_latch if (a) l <= x;
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) b <= 1'b0; else b <= l;
  assign q = b;
endmodule
```

```
clock domains: 2
  aclk: 1 registers
  bclk: 1 registers
registers without reset: 0
crossings: 0, shape not recognized: 0
instances: 0, connections: 0
```

Exit 0. `dvh crossings` returns `{"crossings": [], "unrecognized": []}`. Two
domains are found, both clocks resolve unambiguously, nothing is marked
undecided and nothing is marked `same_clock_source`: the crossing is simply not
there. The elaborated netlist is three cells — two `$adff` and one `$dlatch`
with ports `D`, `EN`, `Q` — so there is nothing exotic for the walk to trip on.

Cause: `tools/dvh/clocks.py:112-121`, the latch branch of `_walk_to_sources`:

```python
    if cell.type in LATCH_TYPES and any_comb:
        out = []
        for b in cell.conns.get("D", []):
```

Only `D` is followed. `$dlatch` has `EN`; `$adlatch` has `EN` and `ARST`;
`$dlatchsr` has `EN`, `SET` and `CLR`; `$sr` has only `SET` and `CLR` and no `D`
at all. Every one of those inputs can carry a foreign-domain register, and none
of them is walked. The asymmetry is visible in the file: `_data_cone_registers`
(`clocks.py:246`) deliberately walks `("D", "EN")` for the *destination*
register — a crossing that lands on a destination flop's enable is found, and
the previous review confirmed it — but an *intermediate* state element loses its
enable.

Why an intermediate flip-flop does not have the same hole: `_walk_to_sources`
stops at a `$dff` and returns it as a source, and the loop in `crossings`
reaches that register in its own turn and walks its `D` and `EN`. Latches are
the only state element the walk passes *through*, and passing through is where
the ports are dropped.

**This falsifies a printed sentence.**
`chapters/ch03-digital-design-for-verifiers.qmd:249`:

> "The two walks also differ at a latch. A latch is a state element, so a path
> through one is never direct and can never be a synchronizer; but stopping
> there would hide the crossing behind it, so the data walk passes through and
> records the latch, while the clock walk stops."

The stated purpose of walking through the latch is that stopping would hide the
crossing behind it. On `latchen.sv` the crossing behind it is hidden anyway,
because "through" means through one port of four. This is the fifth consecutive
review in which a sentence about the tool's latch handling is false; the
previous four were about *where* the walk stops, this one is about what it
carries when it does not stop.

**Fix.** Walk every input port of a latch cell, not `D` alone —
`for port, bits in cell.conns.items() if cell.dirs.get(port) == "input"` — and
keep the existing `through` marking so the path still cannot be counted direct.
Then add a regression fixture for `latchen.sv` and one for a `$dlatchsr` whose
`SET` is foreign. And re-word `:249` to say what the walk actually carries.

For contrast, and to show the hole is specific rather than general: the same
crossing routed through a latch's *data* input (`latchpath.sv`), through a
black-box instance (`bbpath.sv`), over an internal tri-state net (`tribus.sv`),
through a set-reset latch's `SET` where the aclk register is the set condition
(`srlatch.sv`, which Yosys lowers to `$dlatch` + logic on `D`), and through four
module boundaries (`chain.sv`) are all reported, all with exit 1 where they
should be. The memory passes hold up too: a true dual-port RAM written on `aclk`
and read on `bclk` (`tdp.sv`) reports 16 crossings and 17 unreset registers, an
array read combinationally and then through an adder (`memcomb.sv`) reports 16,
and an initialised ROM indexed by a foreign register (`romcross.sv`) reports the
index crossing. §1.1 of `ch03-gate2c` is genuinely closed.

### 1.2 `shape_recognized: true` on a chain whose second stage samples the opposite edge

```systemverilog
// halfperiod.sv -- "two flops", but the second samples on the opposite edge,
// so the first stage gets half a clock period to resolve, not a full one.
module halfperiod (input logic aclk, bclk, rst_n, input logic d,
                   output logic q);
  logic a, s1, s2;
  always_ff @(posedge aclk or negedge rst_n)
    if (!rst_n) a <= 1'b0; else a <= d;
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) s1 <= 1'b0; else s1 <= a;
  always_ff @(negedge bclk or negedge rst_n)     // <-- negedge
    if (!rst_n) s2 <= 1'b0; else s2 <= s1;
  assign q = s2;
endmodule
```

```
crossings: 1, shape not recognized: 0
  known a (aclk) -> s1 (bclk), 1 bit, two-flop synchronizer
```

Exit 0. The JSON says `"shape_recognized": true, "second_stage": ["q"],
"same_clock_source": false`.

The netlist is unambiguous about what this is. The three `$adff` cells are

```
$adff CLK_POLARITY=1 CLK=[2] Q=[8]     (a,  on aclk)
$adff CLK_POLARITY=1 CLK=[3] Q=[7]     (s1, on bclk rising)
$adff CLK_POLARITY=0 CLK=[3] Q=[6]     (s2, on bclk falling)
```

`s1` and `s2` share clock net `[3]` and differ in `CLK_POLARITY`. `CLK_POLARITY`
is read nowhere in `tools/dvh` — `grep -n CLK_POLARITY tools/dvh` returns
nothing — so `_domain_key` (`clocks.py:182-185`) gives both the same key and
`crossings` (`clocks.py:382-384`) accepts `s2` as `s1`'s second stage.

Why this is a false statement rather than a conservative one. The chapter's own
definition, `:89`: "A two-flop synchronizer samples the incoming signal into the
receiving domain and then **waits a full clock period** before sampling the
first stage into a second [@cummings2008cdc]." This structure waits half a
period. The resolution time `S` in the MTBF formula the chapter prints at `:79`
is halved, and `:83` is the passage explaining that the same two-flop structure
gives $4\times10^{29}$ years or about a minute depending on how much of `S` you
have. Halving `S` is a change of the same kind as changing the process corner.
The report calls it `known ... two-flop synchronizer` and the build gate passes.

This is a genuine opposite-edge structure, not a contrived one: designers write
it deliberately to shave a half cycle of latency, and it is one of the shapes a
CDC review exists to catch.

**Fix.** Require the second stage to have the same `CLK_POLARITY` as the first —
the parameter is already in `Cell.params` — and extend the domain key with the
polarity, or record the polarity per register in `clock_tree` and compare it in
`crossings`. Note the choice matters for the report: putting polarity in the
domain key would also make `:262`'s "two domains" count change on any design
with both edges, so comparing it inside `crossings` is the smaller change. Add
`halfperiod.sv` as a fixture.

### 1.3 `shape_recognized: true` twice on a multi-bit value on per-bit synchronizers

The demotion rule at `clocks.py:255-308` fires only when a **register**
downstream reads two chains together. A value that leaves the block through a
port never meets one.

```systemverilog
// portconv2.sv -- a two-bit value, declared as two separate one-bit flops at
// every stage, converging only on the output ports.
module portconv2 (input logic aclk, bclk, rst_n, input logic d0, d1,
                  output logic q0, q1);
  logic a0, a1, s1_0, s1_1, s2_0, s2_1;
  always_ff @(posedge aclk or negedge rst_n)
    if (!rst_n) begin a0 <= 1'b0; a1 <= 1'b0; end
    else begin a0 <= d0; a1 <= d1; end
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) begin s1_0 <= 1'b0; s1_1 <= 1'b0; end
    else begin s1_0 <= a0; s1_1 <= a1; end
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) begin s2_0 <= 1'b0; s2_1 <= 1'b0; end
    else begin s2_0 <= s1_0; s2_1 <= s1_1; end
  assign q0 = s2_0;
  assign q1 = s2_1;
endmodule
```

```
crossings: 2, shape not recognized: 0
  known a0 (aclk) -> s1_0 (bclk), 1 bit, two-flop synchronizer
  known a1 (aclk) -> s1_1 (bclk), 1 bit, two-flop synchronizer
```

Exit 0, both `"shape_recognized": true`. Declared as a two-bit vector instead
(`portconv.sv`, identical but `logic [1:0]`), the same design reports
`CHECK a (aclk) -> s1 (bclk), 2 bits, no synchronizer shape` and exits 1 — so
the width test still catches the vector form, and the per-bit form still walks
past it whenever the consumer is outside the block. That is the same defect
shape as the one `ch03-gate2b` closed (bits declared separately defeat the
check), reappearing on a different axis: not *how the sender declares them*, but
*where they are read*.

This is exactly the structure `:93` quotes Ginosar calling "a complete loss of
data", and the report calls it two two-flop synchronizers.

Three printed sentences overstate what the code does here.
`chapters/ch03-digital-design-for-verifiers.qmd:319`, exercise 6: "The tool
rejects eight parallel one-bit synchronizers on an eight-bit bus, because
someone anticipated that anti-pattern." It rejects them only when a register in
the design reads them together; on a block whose synchronized bits are its
outputs it accepts all eight. `:253` is careful and says "one register
downstream reads *together*", which is true of the code — but `:270` then says
"The tool rejects it only because someone anticipated that anti-pattern ... The
check improved; the lesson did not change", which reads as the check now being
complete for the case it was written for. And `:306`'s summary, "per-bit
synchronizers are a loss of data rather than a partial fix", is the chapter's
teaching, which the tool's own report contradicts on this design.

**Fix.** Two options; the second is better. (a) Treat a top-level output port as
a convergence point, so two recognized chains reaching one port group are
demoted the same way. (b) Cheaper and more honest: demote whenever two or more
recognized chains carry bits *of the same crossing group* — same `from_domain`
and `to_domain`, first stages sharing a clock — regardless of where they are
read, and say so in the note. The chapter can then keep its exercise sentence.
Either way, add `portconv2.sv` as a fixture and correct `:319`.

### 1.4 The build gate still passes on a clock multiplexer between two asynchronous clocks

`:292` states in print:

> "Where the two nets trace back to a single shared source, as a gated clock
> does, the tool says so and the path does not fail the gate. Where they do not,
> **as with a divider or a multiplexer between two clocks**, it does fail"

Here is a multiplexer between two clocks that does not fail.

```systemverilog
// testmux.sv -- the ordinary scan/functional clock multiplexer.  test_clk
// reaches nothing except the multiplexer, which is how a test clock is
// normally wired, so it has no strong evidence anywhere in the design.
module testmux (input logic func_clk, test_clk, test_mode, rst_n,
                input logic [7:0] d, output logic [7:0] q);
  logic clk;
  logic [7:0] stage1, stage2;
  assign clk = test_mode ? test_clk : func_clk;
  always_ff @(posedge func_clk or negedge rst_n)
    if (!rst_n) stage1 <= 8'h0; else stage1 <= d;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) stage2 <= 8'h0; else stage2 <= stage1;
  assign q = stage2;
endmodule
```

```
clock domains: 2
  func_clk#2: 1 registers
  func_clk#22: 1 registers
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK stage1 (func_clk#2) -> q (func_clk#22), 8 bits, no synchronizer shape
```

Exit 0. `"same_clock_source": true`, `"unrecognized": []`.

`test_clk` does not appear anywhere in the printed report. `dvh clock-tree`
shows where it went:

```json
"q": { "clock_sources": ["func_clk"], "gated_or_muxed": true,
       "through": ["$mux", "gated by test_clk", "mux"],
       "clock_ambiguous": false, "domain": "func_clk#22" }
```

The tool has classified a second clock as a gating enable, with
`clock_ambiguous: false` — it is not saying it could not tell; it is saying it
could. An eight-bit unsynchronized crossing between two asynchronous clocks is
printed as "one clock gated differently" and the build passes.

**The boundary is sharp and worth recording.** The bypass needs the second clock
to have no *strong* evidence (`clock_candidates`, `clocks.py:46-75`): it must not
directly drive any register's clock pin anywhere in the design, must not be a
register output used as a clock, and must not come from something opaque. Add
one register on `test_clk` and the same design (`muxboth.sv`) reports three
domains — `clk_a`, `clk_b`, `clk_a+clk_b` — and exits 1. So the tool's verdict on
a crossing depends on whether some *unrelated* register elsewhere happens to be
clocked directly by the second clock. A test clock, a low-power clock used only
behind its multiplexer, or a clock that reaches the block only through a mux are
all wired exactly the way that defeats it, and `muxbypass.sv` (a bare two-clock
mux, no test-mode dressing) behaves identically.

Note that `best == 1 and len(carrying) > 1` at `clocks.py:144-147`, the branch
that records ambiguity, cannot fire here: it requires that *no* input have strong
evidence. Where one clock has strong evidence, every other input is silently
demoted to gating control with no marker. That is the mechanism, and it is not
the same as the "the walk picks the wrong signal as the clock" limit — nothing
picks wrongly; the rule at `clocks.py:138-143` picks the *strongest*, which is
correct as a heuristic and fatal as a domain-identity input.

**Fix, and the recommendation is not to patch this in place.** The chapter's
`same_clock_source` marking exists to keep an ordinary clock gate out of the
gate. Two changes make it sound:

1. A clock net that reaches a multiplexer (`MUX_TYPES`) is never "one clock
   gated differently", whatever the evidence tiers say. Gating propagates or
   stops one source and selection may hand over another — that is `:63`'s own
   distinction, and the code currently does not make it. `Source.through`
   already records `"mux"`; `same_source` at `clocks.py:393-396` can require
   that no source's `through` contains it.
2. A demoted input that is itself a plausible clock — an input port never used
   as anything but a clock-tree input — should set `clock_ambiguous` rather than
   be silently recorded as `gated by`. Then the crossing reports as undecided,
   which is loud, which is the design principle `:242` and `:264` both state.

Until one of those lands, `:292` must not claim a multiplexer between two clocks
fails the gate, and the limit STATUS records as needing to be in the prose is
still not in the prose — see §1.5.

### 1.5 Sentences that do not describe the code

Two are already argued above and are listed here only so the count is in one
place: `:249` (the latch walk, §1.1) and `:292` (a multiplexer between two
clocks fails the gate, §1.4). Three more.

**(a) `:251` describes `_feeds_directly` without the term this pass added.**

> "`_feeds_directly` answers half of the shape question: is this register fed by
> the foreign register with nothing in between."

That is no longer what the function answers. `clocks.py:333-334`:

```python
    if any(b not in (0, "0") for b in cell.conns.get("EN", [])):
        return False
```

An enabled register is fed by the foreign register with nothing in between and
is nevertheless not direct. Verified on `enabled.sv` — an aclk register straight
onto the `D` of a `$adffe` on `bclk` — which reports `"direct": false`. The
function's own docstring at `clocks.py:323-332` states the extra term ("*and*
this register takes it on every clock") and gives the reason (an enable means
the value is held, not resampled); the chapter, which is where a reader meets
the function, does not. This is one of the five changes the pass was made for
and it is invisible in the prose.

**Fix.** One clause: "... with nothing in between, and taken on every clock: an
enable means the value is held rather than resampled, so an enabled register is
not a synchronizer stage."

**(b) The same sentence is a false description in the published schema.**
`tools/dvh/schema/crossings.schema.json`, field `direct`:

> "True if the sender reaches D with no logic between."

False on `enabled.sv`, for the same reason. This one matters more than the prose
because the schema is the contract Appendix I publishes to callers who are not
this book, and `test_every_field_carries_a_description` checks that a description
*exists*, never that it is true. Two neighbours are worth a look at the same
time: `unrecognized` is described as "The subset to review", but a
`same_clock_source` crossing is excluded from it and `:292` says explicitly that
such a pair still needs a person; and `same_clock_source` is described as "True
if both clocks resolve to the same source" without saying that it is the flag
that keeps a crossing out of the build gate, which is the only reason a consumer
would care.

**(c) `:287` enumerates the regression fixtures and is missing the last three.**

The sentence reads as a closed list — nine items joined by "and". There are
thirteen fixtures under `tools/dvh/tests/rtl/`, and the listing at `:282`
splices the test file that uses all thirteen, so a reader can count them:

| `gated_clock.sv` | yes |
| `mux_select.sv` | yes |
| `crossing_via_latch.sv` | yes |
| `per_bit_sync.sv` | yes (twice: per-bit, and bit-blasting) |
| `split_source_sync.sv` | yes |
| `three_flop_per_bit.sv` | yes |

The three unnamed ones are the three most recent, and `ram_crossing.sv` is the

**Fix.** Add the three, or stop enumerating and describe the classes instead.
The second is better: this list has now had to grow in three consecutive passes.

### 2.8 New non-blocking observations

* **A crossing that arrives on an asynchronous reset pin is not reported, and
  `:131` gives the wrong reason for it.** `rstxing.sv` — an `aclk` register
  driving the `negedge` asynchronous reset of a `bclk` register — reports
  `crossings: 0`, exit 0. `_data_cone_registers` (`clocks.py:246`) walks `D` and
  `EN` and no reset pin. `:131` explains the tool's blindness to reset-domain
  crossings with "with one clock on both ends there is no clock crossing to
  find", which implies that two clocks would be enough to make it visible. They
  are not: the cone does not reach the reset pin whatever the clocks are. One
  clause fixes the sentence; extending the cone to reset pins is the larger fix
  and would want its own note in the report, because a reset path is not a data
  path.
* **A synchronizer whose first stage also fans out is still `known`.**
  `tapped.sv` — `s1` feeds `s2` *and* a datapath register in the same domain —
  reports `known a (aclk) -> s1 (bclk), two-flop synchronizer`, exit 0. Two
  flops in series really are there, so this is within the letter of
  `shape_recognized`, and it is a classic review finding a shape recognizer
  cannot see. It belongs in exercise 6's answer rather than in the code.
* **Registers created by the memory passes carry no source location.** In every
  memory design above, `mem[0]`…`mem[15]` print with no `[file:line]`, because
  Yosys attaches no `src` to the cells `memory_map` creates. The chapter does
  not claim otherwise, but `test_every_finding_carries_a_real_source_location`
  runs only on the two-clock design, so the claim "a finding names the RTL that
  produced it" is untested for exactly the category where it fails. Worth a
  known-limitation line in the test's docstring.
* **`scripts/check-citations.sh` check 2 is testing the wrong field for 76 of
  182 bibliography entries.** `scripts/check-citations.sh:39-42` takes whichever
  of `author` or `title` appears *first* in the entry and then greps the
  rendered text for that string's last word. For an entry that puts `title`
  first it therefore greps for a title fragment. Run against
  `pdftotext _book/Design-Verification-draft.pdf`, it reports:

  ```
  cited but not found in the rendered text: goering2004seventy yu2026sweabs
  ```

  Both are false positives: "Goering" appears twice in the rendered text, and
  the script was searching for `percent?` and `Benchmarks` respectively. The
  same field-order assumption can hide a real miss, which is the failure mode
  this script was written to close. **Fix.** Anchor the extraction to the
  `author` field specifically (`/author[ \t]*=/`), take the first author's
  surname, and skip the entry only when there genuinely is no author. Check 1,
  the swallowing-construction pattern, is sound and clean on this chapter.

  With that correction applied by hand, **all 34 keys cited in Chapter 3 appear
  in the rendered bibliography.** Check 1 finds nothing in the chapter.

## 5. Answers to the three questions asked

**Did a crossing disappear?** Yes, once, by a mechanism none of the five
previous rounds used: `latchen.sv`, a crossing arriving on a latch's enable.
`crossings: 0`, exit 0. §1.1. Nine other routes were tried and all nine are
reported correctly — the memory passes in particular hold up well past their
fixture.

**Could `shape_recognized: true` be made false?** Yes, twice. A second stage on
the opposite clock edge (§1.2) and a multi-bit value on per-bit synchronizers
converging outside a register (§1.3). Both exit 0.

**Could the build gate be made to pass on a real asynchronous crossing?** Yes,
and outside the limit the drafter had in mind: an ordinary clock multiplexer
where the second clock is not used as a clock anywhere else (§1.4). The boundary
is that the second clock must have no *strong* evidence, and `:292` currently
claims in print that this case fails the gate.

**The most serious thing in this review** is §1.4, not §1.1. §1.1 is a missing
port in a walk, a ten-line fix with an obvious test. §1.4 is the third
consecutive pass in which the mechanism that keeps ordinary clock gating out of
the build gate turns out to also excuse a real crossing — by shared name tokens,
then by equal source sets, now by a demotion rule that silently reclassifies a
clock as an enable whenever some other clock nearby looks more like a clock. The
first two were fixed by tightening the comparison. This one is not a comparison
bug: the comparison is fine and its *input* is a heuristic that cannot be right
in general. The chapter already knows this — `:240` and `:242` are about exactly
this — but the code applies the "I do not know" branch only when it knows
nothing, and applies a silent guess whenever it knows something. Making the
demotion of a plausible clock set `clock_ambiguous` instead is the change that
matches what the chapter says the tool does.

**Verdict: blocking findings remain.**
