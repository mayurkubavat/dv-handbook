## D3 detail — "two regions of nine", against the documentation and against the chapter

`chapters/ch04-simulation-fundamentals.qmd:182`:

> The other decides its scheduling at compile time rather than maintaining a
> queue, and implements the Active and non-blocking regions of the model rather
> than the full set, iterating them to convergence at run time
> [@verilator-internals].

`:187`, inside the Pitfall that closes the section:

> A tool implementing two regions of nine agrees with the model on any code that
> does not depend on the other seven, and that is most correct code.

**What the cited document says.** `docs/internals.rst`, fetched from
`raw.githubusercontent.com/verilator/verilator/master/docs/internals.rst`
(the entry's own URL, `master` branch). The chapter's sentence is the document's
own headline, at line 223:

> Verilator implements the Active and NBA regions of the SystemVerilog scheduling
> model as described in IEEE 1800-2023 chapter 4, and in particular sections 4.5
> and Figure 4.1.

But the same file, at lines 558–563, describes the rest:

> The remaining regions ('inact', 'obs' and 'react') nest around these in the same
> manner, each iterating the loops of all regions that precede it in the
> SystemVerilog scheduling order. The runtime event loop calls every region
> unconditionally, so scheduling emits an entry point for each one even when the
> design has no logic in it.

So the document names five scheduling regions in its runtime loop — `ico`, `act`,
`nba`, `inact`, `obs`, `react` (six, counting `ico`, which the document introduces
at line 495 as Input Combinational logic) — and the chapter counts two.

**What the tool does.** Written for this review, not adapted from the chapter's
examples — one testbench touching Postponed (`$strobe`), Inactive (`#0`), NBA and
Active in one timestep:

```systemverilog
// t2_regions.sv
module t2;
  logic clk = 1'b0, b = 1'b0;
  initial forever #5 clk = ~clk;
  always @(posedge clk) begin
    b <= 1'b1;
    $display("  [active]    b reads %0b right after b<=1", b);
  end
  always @(posedge clk) $strobe("  [postponed] $strobe sees b=%0b", b);
  always @(posedge clk) begin #0 $display("  [inactive]  a #0 print ran"); end
  assert property (@(posedge clk) b |-> 1'b1) else $error("assertion fired");
  initial begin @(posedge clk); #1; $display("  [next step] b=%0b", b); $finish; end
endmodule
```

```
$ verilator --binary --timing --timescale 1ns/1ps -Wno-DECLFILENAME \
      -Wno-BLKSEQ --assert --top-module t2 -Mdir bt2 t2_regions.sv && ./bt2/Vt2
  [inactive]  a #0 print ran
  [active]    b reads 0 right after b<=1
  [postponed] $strobe sees b=1
  [next step] b=1
- Verilator: $finish at 10ns
```

The `#0` statement ran; `$strobe` reported the post-NBA value and reported it
after the Active-region `$display`; the concurrent assertion compiled and ran.
Those are Inactive, Postponed and Observed behaviors on a tool the chapter says
implements neither. (The same source file does not even parse under the
event-driven simulator: `iverilog -g2012` returns "Error in property_spec of
concurrent assertion item" — which is an interesting fact about the *other* tool
and is nowhere in the chapter.)

**Why this is blocking rather than a nit.** Three reasons.

1. It is the load-bearing sentence of a section (`@sec-ch04-real`) whose entire
   thesis is that you must read the documentation rather than reason from a
   category — and it is a misreading of the documentation, taking one summary
   sentence and treating the arithmetic it implies as a result.
2. The chapter contradicts itself with it. `:70` says of the regions example,
   whose testbench prints from `$strobe`: "the same testbench on a two-state tool
   prints a zero in that position and the ordering point is unchanged." That is
   true — round C verified it and so did this review — and it is only true because
   the tool implements Postponed. Two sections later the reader is told it does
   not.
3. The inference built on the number ("agrees with the model on any code that does
   not depend on the other seven") is what a reader will carry away, and it
   understates the tool in a way that would lead someone to distrust a correct
   result.

*Fix.* Keep the point — which is right and is the best idea in the section — and
drop the count. For instance:

> The other decides its scheduling at compile time rather than maintaining a
> queue. Its documentation describes the design in terms of the model's regions:
> the Active and non-blocking regions are where the work is placed and iterated to
> convergence, and the later regions nest around them [@verilator-internals]. …
> The interesting question is not *which kind* of simulator you have but *how much
> of the model* it implements, and the answer is in the tool's own documentation
> rather than in its category.

If the chapter wants to keep a contrast in the Pitfall, the honest one is that one
tool maintains a run-time queue and the other decides most of the order before the
run starts, which is exactly what `:182` already says in its first clause.

## D4 detail — a timescale cause that is not the cause

`chapters/ch04-simulation-fundamentals.qmd:174`:

> Delays are scaled to the smallest precision used anywhere in the design, so one
> module's declaration changes another module's behavior [@sutherland2007gotchas].

**The first clause is the source's, verbatim in substance.** `g2007.txt:1807–1808`,
§8.1: "The precision is relative to the time unit. Within simulation, all delays
are scaled to the smallest precision used by the design."

**The second clause is the chapter's own inference, and it is wrong.** A module's
delays are rounded to *that module's* declared precision. The design-wide smallest
precision sets the resolution of the shared time wheel and the units `%t` formats
in — it does not change what a coarser module's delays mean.

Built and run both ways for this review. A coarse module, unchanged between runs:

```systemverilog
// ts_a.sv
`timescale 1ns/1ns
module a_mod;
  initial begin
    #1.4 $display("a_mod: after #1.4  $time=%0d  $realtime=%0f", $time, $realtime);
    #1.6 $display("a_mod: after #1.6  $time=%0d  $realtime=%0f", $time, $realtime);
  end
endmodule
```

and a second module, present in one build and absent from the other:

```systemverilog
// ts_b.sv
`timescale 1ns/1ps
module b_mod;
  initial #1.4 $display("b_mod: after #1.4  $realtime=%0t", $realtime);
endmodule
```

```
$ iverilog -g2012 -o ts.vvp ts_a.sv ts_b.sv ts_top.sv && vvp ts.vvp
a_mod: after #1.4  $time=1  $realtime=1.000000
b_mod: after #1.4  $realtime=1400
a_mod: after #1.6  $time=3  $realtime=3.000000
ts_top.sv:4: $finish called at 20000 (1ps)

$ iverilog -g2012 -o ts2.vvp ts_a.sv ts_top2.sv && vvp ts2.vvp     # b_mod removed
a_mod: after #1.4  $time=1  $realtime=1.000000
a_mod: after #1.6  $time=3  $realtime=3.000000
ts_top2.sv:3: $finish called at 20 (1ns)
```

`a_mod`'s `#1.4` rounded to 1 ns in both builds and its `#1.6` landed at 3 ns in
both. `$time` and `$realtime` are identical. The only thing that changed is the
global precision the `$finish` banner and `%t` report in — which is why the first
attempt at this experiment, using `%0t`, appeared to show a difference (1000 and
3000 rather than 1 and 3) and did not. **The finer module changed nothing about
the coarser module's behavior.**

**The source's actual cross-module gotcha, which the chapter does not name, is a
different mechanism and a better story.** `g2007.txt`, §8.1, two paragraphs below
the sentence the chapter quotes:

> The `timescale directive is not bound to modules or files. Once specified, the
> directive affects all modules and files that follow the directive, until a new
> `timescale is encountered by the compiler. This means if some design and/or test
> files contain time scale directives, and other files do not, then changing the
> order in which files are compiled will change the what a delay represents in
> the files that do not have a time scale directive. This can cause radically
> different simulation results, even with the same simulator. Gotcha!

That is the mechanism by which one file's declaration silently changes another
file's behavior, and it produces exactly the failure mode the chapter's next
sentences describe: "a waveform with the right shapes at the wrong times". It also
lands perfectly on the chapter's own closing example at `:176`, where none of the
four examples declares a timescale in its source and the two tools therefore
disagree about what time it is.

*Fix (replaces one clause, and the paragraph gets stronger).*

> A mismatched timescale does not produce an obviously broken result. It produces
> a plausible one: a waveform with the right shapes at the wrong times, or a delay
> that quietly rounds away to nothing. The directive is not bound to a module: it
> applies to every file compiled after it until another one replaces it, so a file
> that declares no timescale takes whatever the file compiled before it declared,
> and changing the compile order changes what that file's delays mean
> [@sutherland2007gotchas]. Delays across the whole design are then scaled to the
> smallest precision any module declared. Simulators round delays finer than the
> declared precision, and this book does not state the rounding rule…

The second half of the paragraph, `:174`'s refusal to state a rounding rule and
`:176`'s account of the chapter's own examples, is unaffected and is correct: the
"at 6 (1s)" claim was re-verified against `regions/run.out:6` and the
`--timescale 1ns/1ps` flags against all six build-file invocations
(`fourstate/run.sh:18,24`, `fourstate/Makefile:7`, `regions/Makefile:13`,
`sampling/Makefile:9`, `race/run_both.sh:16`, `race/lint_both.sh:13`), and no
`.sv` file under `examples/ch04-simulation/` contains a `timescale directive.

### 2.3 Two blocking writers, one variable (`:63`, `:91`) — holds, and the two tools disagree

This is the strongest independent confirmation in the review, because the two
simulators give opposite answers on code written here rather than on the
chapter's own example:

```systemverilog
// t4_blocking.sv
always @(posedge clk) v = 8'd1;

```

```

$ ./b_t4_blocking/Vt4             # statically scheduled
after both writers ran, v=2
```

`:63` ("which runs first is the simulator's choice"), `:91` ("the order is
arbitrary, and the last writer wins") and the whole of the Pitfall at `:62–71`
are confirmed by construction.

### 2.4 The zero-time loop (`:77`) — holds, and the blocking control case confirms the mechanism

The chapter says a non-blocking assignment inside a combinational block
retriggers the block's own sensitivity list and time stops advancing. Written
here from the described mechanism, with a blocking control:

```systemverilog
// t6_loop.sv          // t7_blockingloop.sv is identical but for the operator
always @(m or n) m <= m + 8'd1;   // t7: m = m + 8'd1;
initial begin #1 n = 8'd1; #9 $display("reached time %0t -- NO lock-up", $time); $finish; end
```

```
$ vvp t6.vvp &   # non-blocking
  STILL RUNNING after 6 s -> locked up, time never advanced   (no output at all)
$ vvp t7.vvp     # blocking
reached time 10 -- NO lock-up
```

The non-blocking version never printed and never reached time 10; the blocking
version completed. That is exactly the chapter's claim and exactly Cummings'
argument (2000 §7) that a blocking assignment completes before the trigger event
could be scheduled and therefore cannot retrigger itself. One caveat for anyone
reproducing this: the block must be woken at least once, since SystemVerilog
initializes declaration-initialized variables before time 0 and causes no time-0
event — a first attempt without the `#1 n = 1` poke terminated normally.

### 2.5 Can Icarus even parse a concurrent assertion?

Worth recording because `@sec-ch04-boundary` rests on assertions and no example
in the chapter contains one. `assert property (@(posedge clk) b |-> 1'b1);`
compiles and runs under Verilator with `--assert`; under `iverilog -g2012` it is
a syntax error ("Error in property_spec of concurrent assertion item"). Nothing
in the chapter is wrong because of this, but it is the sharpest available
instance of the chapter's own thesis at `:180` and is not used.
