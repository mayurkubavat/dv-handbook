# 2. Blocking

## B-1. `appendices/appI-agent-tool-layer.qmd:47` and `:209` — the memory passes create registers with no source location, and the appendix's grounding claim and its test claim are both false on a design in this repository

`:47`, the sentence the whole *Grounding* argument rests on:

> The book's own tools carry the source location the netlist records into
> every report: each register in the clock and reset trees, each crossing, and
> each instance in the connection graph names the file and line of the RTL
> that produced it.

`:209`, the sentence that says a test holds it:

> The other runs the tools and fails if a reported source location is blank,
> absolute, or does not name a line in a file that exists.

Both are falsified by `tools/dvh/tests/rtl/ram_crossing.sv`, a fixture this
repository ships, added with the memory passes:

```
$ python3 -m dvh clock-tree ram_crossing tools/dvh/tests/rtl/ram_crossing.sv --validate
schema: registers/mem[0]/src: '' does not match '^[^:]+:\d+'
schema: registers/mem[10]/src: '' does not match '^[^:]+:\d+'
   ... 16 registers ...
exit=2

$ python3 -m dvh reset-tree ram_crossing tools/dvh/tests/rtl/ram_crossing.sv --validate
schema: no_reset/0/src: '' does not match '^[^:]+:\d+'
   ... 16 registers ...
exit=2
```

and the human report prints the sixteen findings with no location at all,
directly above one that has one:

```
registers without reset: 17
  mem[0]
  mem[1]
   ... fourteen more ...
  rd  [tools/dvh/tests/rtl/ram_crossing.sv:14]
```

**Cause.** `design.py:_run_yosys` now runs `memory_collect; memory_map;`
(`design.py:96`, and the comment above it explains why). `memory_map`
synthesizes the storage as `$dff` cells named `$memory\mem[0]$25`, and it
attaches **no attributes to them at all** — no `src`. Verified directly in the
Yosys JSON: of the 172 cells in the mapped `ram_crossing`, 16 `$dff` cells and
143 `$mux` cells carry no `src` attribute; only the one `$dff` that came from
`always_ff @(posedge bclk) rd <= mem[ra]` does. `Cell.src` (`design.py:47`)
defaults to `""`, `_relative("")` returns `""` (`design.py:114-115`), and the
empty string travels into `clock_tree` (`clocks.py:207`), `reset_tree`
(`clocks.py:243`, `:249`) and the `read` report unchanged.

**It is not the fixture.** Any array that survives to `memory_map` does this. A
minimal asynchronous-read RAM behaves identically:

```
$ python3 -m dvh reset-tree asyncram asyncram.sv --validate ; echo $?
2
```

The Chapter 1 FIFO is the exception, not the rule, and that is what has hidden
this: its array sits inside an `always_ff` that also holds the reset logic, so
Yosys converts it to `$adffe`/`$dffe` slices that keep `fifo.sv:34.3-53.6`.
That is the one memory design the tests exercise.

**Why no test caught it.** `test_every_finding_carries_a_real_source_location`
(`tools/dvh/tests/test_ch03.py:305-330`) and
`test_every_command_matches_its_published_schema` (`:244-256`) both run on
`TWO_CLOCK` only, which has no array.
`test_a_crossing_through_a_ram_is_reported` (`:444-455`) is the fixture's own
test and asserts only the domain count and that the crossing is unrecognized —
it never validates the payload and never looks at a location. So the suite is
27 green with the tool emitting output its own published schema rejects.

**Consequences for the printed page.** Three sentences are affected:

1. `:47` "each register in the clock and reset trees ... names the file and
   line of the RTL that produced it" — false for every register that comes
   from an array.
2. `:209` "The other runs the tools and fails if a reported source location is
   blank" — the test does not run the tools on any design where a location is
   blank, so the sentence describes a guarantee the suite does not provide.
   This is the third pass on this sentence.
3. `:207`, the paragraph over the printed `crossings.schema.json`, says the
   schemas are the contract and `:209` says "an output that drifts from its
   schema fails in continuous integration rather than in somebody else's
   parser". Here the output drifts and continuous integration is green.

**Proposed fix**, and the order matters — fix the code, then the sentence, not
the other way round:

- In `design.py`, fall back to the source location of the memory the register
  came from. `memory_collect` keeps the `$mem_v2` cell's `src`; capture it
  before `memory_map` runs, or recover it from the `netnames` entry for
  `\mem`, which does carry `src`. Either gives every `mem[n]` the array's own
  declaration line, which is the right answer for a reader.
- Extend `test_every_finding_carries_a_real_source_location` and
  `test_every_command_matches_its_published_schema` to run over **every**
  fixture in `tools/dvh/tests/rtl/` plus the two book designs, not
  `TWO_CLOCK` alone. A guarantee stated in the book about all reports needs a
  test over more than one design; the sweep that found this took twenty lines.
- Only then is `:47` true as written. If the code is not changed, `:47` and
  `:209` have to say what is true instead, and `:209` must not claim a test
  that does not run.

## S-5. `:97`-`:110` — the message-signature grammar never names its delimiter, and four of its nine stage values contain one

@tbl-appI-signature specifies:

| Field | Content | Where it goes |
|---|---|---|
| Role | `SEQ`, `DRV`, ... | first token of the message ID |
| Stage | `CREATE`, `SEND`, `DRIVE_BEGIN`, `DRIVE_END`, `OBSERVE`, `EXPECT`, `COMPARE_OK`, `COMPARE_FAIL`, `DROP` | **second token of the ID** |

The worked example two paragraphs later is `[DRV_DRIVE_END]`. Nothing in the
appendix says what a token is separated by; the example says it is `_`. Under
that reading `DRV_DRIVE_END` has three tokens and the **second token is
`DRIVE`, not `DRIVE_END`** — and the same is true of `DRIVE_BEGIN`,
`COMPARE_OK` and `COMPARE_FAIL`, four of the nine stages, including
`[SB_COMPARE_FAIL]`, the one the whole triage argument at `:117`-`:127` turns
on.

This is not a typographical nit. `log.uvm_parse` (`:186`) is specified to
return "role ... stage" as separate fields, `log.classify_failure` (`:189`)
consumes them, and step 3 of @sec-appI-building asks a team to build the
emitter and parser in "days of work". The first person to write the parser has
to guess, and the two obvious guesses — split on `_`, or split once on the
first `_` — disagree on four stages out of nine.

The last pass read this table and recorded that "the message-signature grammar
is internally consistent" (`appI-gate2c` §8). It is consistent only under a
reading the table does not state, and no earlier review raised the delimiter at
all.

**Fix.** One clause in the table or the paragraph above it: "Role and stage are

- **`scripts/check-citations.sh` check 2 has two false-positive modes**, both hit
  by this book. It derives a grep target from the last word of the `author`
  field, or of `title` when no `author` line is reached first, so a title-cased
  bibliography entry misses (`goering2004seventy` → it greps "percent?"), and it
