## Verdict

**Needs another pass. Three blocking findings.**

The chapter's measurements hold: all eight examples lint and run, every
`run.out` and `matrix.md` is byte-identical to a fresh
`scripts/check-examples.sh ch06` and to a `make clean run` of the
support matrix (67 s), the caption's counts match the rows, and every
behavior the prose asserts about the two simulators reproduced with
SystemVerilog written for this review — one object answering three ways
on Icarus, the template method running the base step through the
derived handle, `new src` through a base handle building a base object
on Verilator 5.030, a virtual call from a base constructor running the
base body on both, Icarus refusing a call through a handle-typed
property, `$cast` returning zero and leaving the target untouched, and
a whole-language parser elaborating all 33 probes with no diagnostic.
The Icarus and Verilator tracker quotations are exact, and the UVM,
OpenTitan, lowRISC, Liskov and Google passages say what the chapter
says they say — with three exceptions, and those are the blocking
findings.

Two of the three are sentences attributed to the UVM 1.2 Class
Reference that the Class Reference does not contain (one is in the
User's Guide, one is true only of the later 1800.2 library). The third
is a claim about the book's own two compilers — that both state the
three constructor-chaining rules in their diagnostics — that neither
compiler bears out for one of the three rules: Verilator 5.030 does not
parse the `extends base(args)` form at all, and Icarus 13.0 accepts it
together with an explicit `super.new` and runs. All three are one- or
two-sentence fixes, but each is exactly the kind of error the previous
chapter's three rounds were about, and the third is a claim about a
tool the chapter's own probe suite could have measured.

Ten serious findings follow. Four are about the chapter's own table and
worked example: the prose calls the composition row "wrong" where the
table says "no build"; the clone row's Icarus cell measures `$cast` and
handle comparison rather than `clone` (isolated, Icarus *runs* it and
prints the wrong type, which is a stronger result than the one
printed); the row "virtual method called from the base constructor" is
scored *wrong* on both tools against an expectation the chapter itself
says it never verified; and the worked example is said to build all
five patterns when it builds three, with the hole it calls the
"strategy" being, by the chapter's own definition four sections
earlier, the template method. One is about the evidence chain: the
two-tool runner prints its verdict whether or not both tools ran, and
the checker does not consult `EXPECT_OUTPUT` for a passing example, so
the Makefile's claim that "a missing tool fails the run" is false —
measured with Icarus hidden from `PATH`. The others are citation
over-reach (the callback attributed to Gamma et al.; OpenTitan's
reason for not being abstract replaced by a language rule that does
not exist; the config-db pool attributed to the Class Reference) and
an exercise that cannot be done with the shipped code.

## Blocking

**B1 — `:25` says both of the book's compilers state the three
constructor-chaining rules in their diagnostics; for the second rule
neither does, and Verilator 5.030 cannot parse the form the rule is
about.**

`:25`: "The rules are three, and both of this book's compilers state
them in their diagnostics: a `super.new` call must be the first
statement of the derived constructor; when the `extends` clause itself
carries constructor arguments, an explicit `super.new` is an error; and
when the derived constructor says nothing, an implicit `super.new()`
with no arguments is called — which is itself an error if the base
constructor needs one [@ieee1800-2023]." `:173` repeats the second rule
in the summary ("none at all when the `extends` clause carries the
arguments").

Measured (`sv/r1_ctor_not_first.sv`, `r2_ctor_both.sv`,
`r3_ctor_missing.sv`, `r3b_ctor_extends_args.sv`; the Verilator command
is the book's `sv.mk` line):

```
$ iverilog -g2012 r1_ctor_not_first.sv            # super.new after a statement
r1_ctor_not_first.sv:4: error: super.new(...) must be the first statement in a block.
$ verilator --binary --timing ... r1_ctor_not_first.sv
%Error: r1_ctor_not_first.sv:4:32: 'super.new' not first statement in new function (IEEE 1800-2023 8.15)

$ iverilog -g2012 r3_ctor_missing.sv && vvp ...   # no super.new, base needs an argument
r3_ctor_missing.sv:3: error: Missing 1 arguments to constructor $unit.base.new.
$ verilator ... r3_ctor_missing.sv
%Error: r3_ctor_missing.sv:4:12: Missing argument on non-defaulted argument 'i' in function call to FUNC 'new'

$ iverilog -g2012 r2_ctor_both.sv && vvp r2.vvp   # extends base(3) AND super.new(4)
id=4 e=1                                           # accepted, no diagnostic
$ verilator ... r2_ctor_both.sv
%Error: r2_ctor_both.sv:3:27: syntax error, unexpected '(', expecting ';'
$ verilator ... r3b_ctor_extends_args.sv           # extends base(3), no super.new
%Error: r3b_ctor_extends_args.sv:3:27: syntax error, unexpected '(', expecting ';'
$ iverilog -g2012 r3b_ctor_extends_args.sv && vvp r3b.vvp
id=3 e=1
```

Rules one and three are diagnosed by both tools as the sentence says.
Rule two is diagnosed by neither: Verilator 5.030 rejects
`class derived extends base(3)` as a syntax error before it can judge a
`super.new`, and Icarus 13.0 runs the combination the rule forbids and
prints `id=4`. The diagnostic the research note quotes for this rule
("Explicit super.new not allowed with class extends arguments") is in
Verilator's current source, not in the 5.030 the book runs and measures.
The rule itself is very likely the standard's — but the chapter's
authority for it, as written, is the two compilers, and the two
compilers do not supply it; and the summary teaches a form the book's
own simulator cannot compile without saying so.

Fix: "The rules are three. Two of them both of this book's compilers
state in their diagnostics: a `super.new` call must be the first
statement of the derived constructor, and when the derived constructor
says nothing an implicit `super.new()` with no arguments is called,
which is itself an error if the base constructor needs one. The third
is the standard's alone here: the `extends` clause may carry the
constructor arguments instead, and then an explicit `super.new` is an
error [@ieee1800-2023] — a form the Verilator this book runs does not
yet parse, so the listings use `super.new`." Adjust `:173` to match. If
the form is kept in the summary, add a probe for it to `probes.txt`
so the table records the "no build".

**B2 — `:110` attributes copy policies to the UVM 1.2 Class Reference;
in that document `copy` takes no policy.**

`:110`: "UVM's comparison, copy and print policies are strategies passed
as arguments [@accellera2015uvmref]."

The Class Reference at the entry's URL (`src/cr.txt:1288–1296`, the
`uvm_object` "Copying" group):

```
  copy
     function void copy (
        uvm_object rhs
     )
  The copy makes this object a copy of the specified object.
  The copy method is not virtual and should not be overloaded in derived classes.
```

`compare` there does take `uvm_comparer comparer = null` (`cr.txt:1331–1333`)
and `print` takes a `uvm_printer`; `copy` takes only `rhs`. A copier
policy (`uvm_copier`, `copy(uvm_object rhs, uvm_copier copier=null)`)
exists in the IEEE 1800.2 library the chapter cites elsewhere as
`uvm-core-object` (`src/uvm_object.svh:464`), not in the 1.2 Class
Reference. As written, a reader who opens the cited document to see
the copy policy finds a `copy` with no policy argument.

Fix: either "UVM's comparison, printing and packing policies are
strategies passed as arguments [@accellera2015uvmref]" or keep "copy"
and cite `[@uvm-core-object]` for it, saying the copier arrived with
the 1800.2 library.

**B3 — `:123` attributes "polymorphically compatible" to the Class
Reference; the phrase is in the User's Guide and not in the Class
Reference.**

`:123`: "UVM's requirement is that the override be polymorphically
compatible with the original, which is a statement about types, not
about contracts [@accellera2015uvmref]".

```
$ grep -n -i polymorphically src/cr.txt
16704:  get_type_handle   An interface to polymorphically retrieve a handle
16706:  get_type_handle_name   An interface to polymorphically retrieve the name
(and the same two lines repeated at 16725, 16733)
$ grep -n -i polymorphically src/ug.txt
7952: ... Any components which are to be swapped shall be polymorphically compatible.
```

The sentence is the User's Guide's §6.2.1 (`ug.txt:7949–7953`), and the
User's Guide is in `refs.bib` as `accellera2015uvmug` and is cited one
section earlier. The Class Reference's `set_type_override_by_type`
text says nothing of the kind.

Fix: `[@accellera2015uvmug]`. The characterization ("a statement about
types, not about contracts") is fair to the passage, which goes on to
gloss compatibility as "having all the same TLM interface handles".

**S2 — The clone row's Icarus cell measures `$cast` and handle
comparison, not `clone`; isolated, Icarus runs the construct and prints
the wrong type.**

`probes/o17_clone_convention.sv` calls `$cast(r, rhs)` inside `copy`,
`$cast(dc, c)` in the module, and compares `c != b`. Icarus refuses the
handle comparison first (`matrix.md:24`: "no build — SORRY: Compare
class handles not implemented"), so the row records a refusal of a
construct its label does not name. With the same shape — a virtual
`clone()` whose derived override constructs its own class — and neither
`$cast` nor a handle comparison (`sv/r8_clone_plain.sv`):

```
$ iverilog -g2012 -o r8.vvp r8_clone_plain.sv && vvp r8.vvp
clone tag=base n=3
$ verilator --binary --timing --timescale 1ns/1ps -Wall -Wno-DECLFILENAME \
    -Wno-UNUSEDSIGNAL -Wno-fatal --top-module top -Mdir v_r8 r8_clone_plain.sv && ./v_r8/Vtop
clone tag=derived n=3
```

Icarus builds it, runs it, and returns a base object from a derived
one, because the virtual `clone()` binds to the handle's declared type
— the same mechanism as every other *wrong* cell, and the one the
chapter's copying section is about. That is the cell the row should
show: *wrong* / *runs*. It also makes the Pitfall at `:86` bite on both
tools rather than one. Fix: rewrite `o17` to check the clone through
its own virtual methods (a `tag()` returning the class name, and the
copied field) with no `$cast` and no `!=`; the table regenerates and
the counts in the caption and at `:135` follow.

**S3 — `matrix.md:17` scores "virtual method called from the base
constructor" *wrong* on both tools against an expectation the chapter
says it has not verified.**

`probes/o26_virtual_from_ctor.sv` passes only if `seen == 100`: that the
derived override runs from the base constructor *and* that the derived
property initializer `k = 5` has not yet run when it does. Both tools
print `seen=1` (`PROBE o26 FAIL` on each, re-run today). `:54` says of
this shape: "the standard's text on the point was not consulted for
this book". A row that says *wrong* under a caption that reads

Icarus both violate the standard here; the chapter has no source for
that, and the runner's four verdicts have no way to say "differs from
the book's reading". Under AGENTS.md's "every claim about a tool has a
source" this row is an unsourced claim about two named tools. Fix:
take the probe out of `probes.txt` (keep the file), so the table
carries only cells the book can stand behind; the Pitfall at `:54`
already states the measured fact ("Both of this book's simulators run
the base body") without scoring it. The caption then regenerates to
"1 on neither" and `:135` drops "and the constructor-time call".

**S4 — `:115` says the worked example "builds all of them"; it builds
three of the five.**

`:115`: "The worked example below builds all of them on one FIFO."
`env.sv`/`tests.sv`/`tb_fifo_env.sv` contain a factory (`packet_maker`),
a template method with a virtual step (`driver::run`/`before_send`) and
a callback (`packet_cb`). There is no configuration object and no
singleton — the two remaining items in the list at `:111`–`:113` — and
the Worked Example callout at `:144` correctly lists three holes. Fix:
"The worked example below builds three of them on one FIFO: the
factory, the template method and the callback."

**S5 — The worked example's "strategy" hole is a template-method
override by the chapter's own definition.**

`:110` defines the two: "the *template method* above, and its cousin
the *strategy*, where the step is a separate object handed in rather
than a method overridden." In the example, `inverting_driver` *extends*
`driver` and *overrides* the virtual `before_send` (`tests.sv:28–32`);
no object is handed in. That is the template method as `:43` and
`tb_template.sv` teach it. Yet `env.sv:11–12` calls `before_send` "the
strategy hook a test overrides", the callout at `:144` says "a driver
whose `run` is a template method with a strategy hook", `:152`, `:165`
and `run.out` call test 2 "strategy", and exercise 5 asks the reader to
"turn the strategy test into a callback" — which, under the chapter's
definition, is turning a strategy into a strategy. A first-year reader
who has just learned the distinction at `:110` meets its opposite in
the one example meant to fix it. Fix: rename the hole to what it is —
"`before_send` is the virtual step a test overrides" in `env.sv:11–12`
and `tests.sv:27`, "override" in place of "strategy" at `:144`, `:152`,
`:165`, in `tb_fifo_env.sv:45,49` and in exercise 5 — or make the hook
a `send_policy` object with a virtual method that the test hands in,
which is then a strategy and distinct from the callback only by who
calls it, a distinction worth a sentence.

**S6 — Exercise 2 cannot be done with the shipped code, and the
scoreboard's contract check can never fire in any shipped test.**

`:187`: "Write a second derived packet whose `legal` is *looser* than
the base's." `env.sv:24–26`: `virtual function bit legal(); return 1;`.
Nothing is looser than always-true, and the scoreboard's
`|| !p.legal()` (`env.sv:83`) is dead in all three tests: the base
returns 1, and `even_packet::legal()` is always 1 for an object its own
constructor built (`tests.sv:11,14`). The "substitution contract" the
file header advertises (`env.sv:4–5`) is therefore never exercised.
Fix: give `packet::legal` a real invariant — for example, `kind` 3 is
reserved and illegal — have `packet_maker::create` never produce it,
and let exercise 2 ask for a derived packet whose constructor or
`legal` admits it; the factory then substitutes an illegal transaction
and the scoreboard's check has a job. Re-run and re-splice `run.out`.

**S7 — `:107` attributes the callback's name to Gamma et al.**

`:107`: "The patterns a testbench is built from have names — factory,
strategy, template method, singleton, callback [@gamma1994patterns]".
The catalog's twenty-three patterns include Factory Method, Abstract
Factory, Strategy, Template Method and Singleton; no pattern in it is
named "callback" (nor "configuration object", which the list at `:111`
adds). Fix: "four of them have names from Gamma and colleagues' catalog
— factory, strategy, template method, singleton [@gamma1994patterns] —
and the fifth, the callback, is the same idea with the hook made an
object".

**S8 — `:102` replaces OpenTitan's stated reason with a language rule
that does not exist.**

`:102`: "its own source says it would make more sense as an abstract
class but cannot be one: a type parameter's default must be a concrete
class the compiler can instantiate [@opentitan-dv-lib]". The source
(`src/dv_base_driver.sv:8–12`, fetched today):

```
// NOTE: This class would make more sense as an abstract base class (with a pure virtual
//       implementation of get_and_drive). Unfortunately, this isn't possible at the moment because
//       dv_base_agent ends up needing to instantiate a uvm_driver instance unless parameters are
//       overridden. This would be reasonable except that uvm_driver::create is not implemented in
//       UVM 1.2 (the version that OpenTitan currently depends on).
```

The reason given is that the *agent* constructs the default `DRIVER_T`
through the factory unless a test overrides the parameter, and that
UVM 1.2's `uvm_driver` has no `create`. Nothing in the language
requires a type parameter's default to be concrete; an abstract default
is legal until something calls `new` on it, which is what the comment
says happens. Fix: "its own source says it would make more sense as an
abstract class with a pure virtual get-and-drive, and cannot be one
because the agent that holds it constructs the default driver type
unless a test overrides the parameter [@opentitan-dv-lib]. That is the
cost of the family: a default type is a type something will build."

**S9 — `:99` attributes the per-specialization pool, and lowRISC's
motive, to documents that do not state them.**

`:99`: "A configuration database parameterized by type keeps one pool
per specialization, which is why a value set through
`uvm_config_db #(int)` is not found by a read through
`uvm_config_db #(bit [31:0])`, and why lowRISC's guide restricts what
may pass through it [@accellera2015uvmref; @lowrisc-dv-style]." The
Class Reference's `uvm_config_db` text (`src/cr.txt:11309–11316`) says
the functions are static and that "The parameter value 'int' identifies
the configuration type as an int property"; it says nothing about a
pool per specialization — that is a fact of the library's source
(`uvm_config_db.svh`, which the `uvm-core` entry lists). And the lowRISC
rule's stated reason (`src/DVCodingStyle.md:719–723`) is "it is much
easier for namespace collisions to occur when using lower level types",
not the typed lookup. Fix: cite `[@uvm-core]` for the pool, and either
drop the "and why lowRISC…" clause or state its reason: "and lowRISC's
guide, for the related reason that basic types collide in a shared
namespace, allows only configuration objects through it
[@lowrisc-dv-style]".

**S10 — The two-tool runner's verdict line is printed whether or not
both tools ran; the Makefile says the opposite.**

`three-handles/Makefile:1–2`: "the verdict line is pinned so a missing
tool fails the run". `run_both.sh` is `set -uo pipefail` (no `-e`) and
ends with an unconditional `echo "verdict: …"`; `check-examples.sh:77–85`
consults `EXPECT_OUTPUT` only in the `expect == fail` branch, and these
examples are `EXPECT := pass`. Measured with `iverilog` removed from

--- event-driven simulator
run_both.sh: line 7: iverilog: command not found
--- statically scheduled simulator
sides via a=3 b=3 c=3  (one object, three handles)

The checker would record `run=pass`, and the spliced `run.out` would
carry "command not found" in place of the Icarus line the chapter's
opening argument rests on. The same pattern is in Chapter 5's
`lifetime` and `twostate-reset` examples. Fix (one line): `set -euo
pipefail` and chain the two runs and the verdict with `&&`, so a
missing tool exits non-zero before the verdict; or teach
`check-examples.sh` to honor `EXPECT_OUTPUT` for `EXPECT := pass` as
well, which is what the Makefile comment believes it already does.
Escalate the Chapter 5 instances to the author.

## 3. The worked example

`env.sv` is not edited by any test: `tests.sv` declares three derived
classes and `tb_fifo_env.sv` chooses which maker, driver and callback

under the names S5 asks to correct.

The even packet: every object it builds has an even `seq`
(`tests.sv:11`), its `legal` is `super.legal() && !word.seq[0]`, so it
is stricter and never false for its own objects. It is a subtype under
the chapter's stricter-invariant criterion; M9 is about the stronger
sentence at `:152`.

The strategy test's zero errors: `driver::run` calls `before_send(p)`
before `sent.push_back(p)` and before driving `p.word` (`env.sv:51–58`),
so the object the scoreboard pops is the one the hook already changed
and the word on the wire is the changed word. The prose at `:165` says
exactly this, and it is what the code does; no variant was run, since
the sequence of statements settles it. What the prose does not say is
that `legal()` is never consulted in earnest (S6).
