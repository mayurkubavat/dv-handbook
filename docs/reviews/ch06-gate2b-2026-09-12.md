## Blocking

**B1 — `:86` says Icarus "gets that line right" for `new base`; the
table at `:133` says *no run*, and the tool aborts.**

`:86`, in the Pitfall: "`new base` printed `packet` for an object that
is an `error_packet`. Nothing warned. The other tool gets that line
right and the next one wrong: its `clone`, being virtual, binds to the
handle's declared type and returns a base object too, which the table
below records."

"That line" is `copy_by_new = new base` with `base` holding an
`error_packet` (`tb_cast_clone.sv:43`). The table's row for exactly that
shape (`matrix.md:22`):

```
| `new src` through a base handle holding a derived object | no run | wrong |
```

Measured today with the same shape and nothing else
(`sv/r7_new_src_base_handle.sv`):

```
$ iverilog -g2012 -o r7_new_src_base_handle.vvp r7_new_src_base_handle.sv && vvp r7_new_src_base_handle.vvp
Assertion failed: (defn_ == that->defn_), function shallow_copy, file vvp_cobject.cc, line 83.
$ verilator --binary --timing --timescale 1ns/1ps -Wall -Wno-DECLFILENAME -Wno-UNUSEDSIGNAL -Wno-fatal --top-module top -Mdir v_r7_new_src_base_handle r7_new_src_base_handle.sv && ./v_r7_new_src_base_handle/Vtop
src=derived copy=base
```

Icarus does not get the line right; it compiles it and then aborts the
simulation. The second half of the sentence (its `clone` returns a base
object, "which the table below records") is correct and measured
(`sv/r8_clone_plain.sv`: Icarus `clone tag=base n=3`, Verilator
`clone tag=derived n=3`; `matrix.md:23` *wrong* / *runs*). The
chapter's research note records the same abort for this probe, so the
sentence contradicts the chapter's evidence as well as its table.

Why blocking rather than serious: it is a positive statement that a
named tool produces the correct result for a construct, it sits in a
Pitfall box the reader is meant to rely on, and the book's own table
and runner say the opposite. The previous round's B1 was the same kind
of claim (a rule "both compilers state in their diagnostics") and was
blocking for the same reason.

Fix (one clause): "The other tool cannot run that line at all — its
simulator aborts on a copy across a hierarchy, which the table below
records as *no run* — and gets the next one wrong: its `clone`, being
virtual, binds to the handle's declared type and returns a base object
too." No code changes, no re-splicing; `run.out` and `matrix.md` are
already correct.

## Serious (not blocking)

**S1 — `:109` attributes "by type and by name" to the User's Guide,
which describes overrides by instance or by type only.**

`:109`: "UVM's factory does this by type and by name, with overrides
that a test installs before the environment builds
[@accellera2015uvmug]."

The User's Guide's factory section (`src/ug.txt:7949–7953`, §6.2.1):
"The mechanism used is referred to as an override and the override can
be by instance or type." The "installed before the environment builds"
half is there (`ug.txt:8014`: "All type-override code should be
executed in a parent prior to building the child(ren)"). The name-based
half is not: `grep -n -i by_name src/ug.txt` finds two lines, one
about `uvm_resource_db::read_by_name` (`ug.txt:3759`) and one about a
callback's `add_by_name` (`ug.txt:8400`), neither about factory
overrides, and every override call the
guide prints is `set_type_override_by_type` or
`set_inst_override_by_type` (`ug.txt:2584, 3117, 3120, 4045, 4061`).
The name-based interface is the Class Reference's
(`src/cr.txt:6468–6480`: `set_inst_override_by_name`,
`set_type_override_by_name`, `create_object_by_name`).

The claim is true of UVM; the cited document does not make it. Fix:
either "by type and by instance [@accellera2015uvmug]" or keep "by
name" and add `[@accellera2015uvmref]` for it: "…does this by type and
by name [@accellera2015uvmref], with overrides that a test installs
before the environment builds [@accellera2015uvmug]".

## Minor

**M1 — `:19` "it runs the base class's code everywhere."** The listing
just above prints `b=99`: through the middle handle Icarus ran the
*middle* class's body, not the base's. The accurate statement is the
one `:51` makes ("binds every call to the class whose code makes it")
and `o08` measures (`via_a=1 via_b=2 via_c=3`). Fix: "it runs the code
of each handle's declared class and reports that everything passed".

**M2 — `:99` "A factory that creates by type must create the base
specialization and `$cast` the result."** "The base specialization" is
not a thing the reader has met. What `dv_base_test.sv:64–70` does is
create through a wrapper, receive a `uvm_object`, and `$cast` it to
`CFG_T`. Fix: "A factory that creates by type hands back a base handle,
and the caller `$cast`s it to the specialization it asked for, which is
the idiom in OpenTitan's base test".

**M3 — `:165` "it inverted every packet's kind", and the class name
`inverting_driver`.** `tests.sv:30` is `p.word.kind = 2'(p.word.kind +
1) % 3`, which maps 0→1, 1→2, 2→0: a rotation, not an inversion, and
with three kinds "invert" has no meaning. Fix: "it changed every
packet's kind before sending" and, if the name is to match, `rotating_driver`
(re-splice `tests.sv`, `tb_fifo_env.sv`).

**M4 — Exercise 2 (`:187`) "a derived packet whose constructor admits
the reserved kind that `packet::legal` rejects."** `packet::new`
already admits kind 3 (`env.sv:21–23` stores whatever it is given);
what never produces it is `packet_maker::create` (`env.sv:34`). The
exercise as worded asks for something the base already does. Fix: "a
derived packet whose constructor *forces* the reserved kind, and a
maker that returns it". Done that way (`sv/ex2_tests.sv`,
`sv/ex2_tb.sv`, built with the shipped `env.sv`), the factory
substitutes it and the scoreboard says what the exercise promises:

```
  MISMATCH got kind=3 seq=0 expected kind=3 seq=0 legal=0
  … (six lines)
wild      6 packets, 6 errors
```

**M5 — `:25` "The rules are three. Two of them both of this book's
compilers state in their diagnostics:"** — "Two of them both of" reads
as a typo on first pass. Fix: "The rules are three. Both of this
book's compilers state two of them in their diagnostics:".

**M6 — `refs.bib`.** Seven entries added for this chapter are still
cited nowhere in the book (`icarus-pr-469`, `icarus-pr-1416`,
`opentitan-tl-seq-item`, `ieee1800.2-2020`, `cummings2012factory`,
`cocotb-bus`, `pyuvm`; `grep -rl` over `chapters/ appendices/
index.qmd` finds none). Harmless, as the previous round said; noted
so the count in `STATUS.md:45` ("22 new `refs.bib` entries") is read
as entries added, not entries used. Everything else in the file
checked out today: `accellera2015uvmref` now `year = {2014}` against
the title page's "June 2014" (`src/cr.txt:7`); `gamma1994patterns`
has one `note`; every key the chapter cites exists.
