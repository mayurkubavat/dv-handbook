# Chapter 3 gate-2 re-review (seventh pass)

Scope, in the order asked for: (1) make a crossing disappear; (2) make the
build gate pass on a real asynchronous crossing; (3) make `shape_recognized:
true` false; (4) does the chapter describe the code; (5) house rules and the
research note's constraints.

Method. Every claim about the code here was produced by running the code on
designs written for this review, under `/private/tmp/.../scratchpad/rtl`.
`tools/dvh/tests/rtl/` was read but nothing here rests on it. Tools: Yosys
0.68+post, the `dvbook` conda environment, `PYTHONPATH=tools`.

Baseline, verified before anything else: `pytest tools/dvh/tests/test_ch03.py`
passes, 31 tests.

**Verdict: blocking findings remain.**

The headline, and the answer to both of the first two questions at once:

**A seventh mechanism.** Two asynchronous clocks arriving on one *vector* input
port — `input logic [1:0] lane_clk`, which is how a multi-lane block normally
receives its per-lane clocks and what a `generate` loop over a clock array
produces — are recorded as one clock source, because `Module.finish` maps a bit
to its **port name**, not to the bit. `same_clock_source` is then true, the
crossing is removed from `unrecognized`, and `dvh read` exits **0** on an
eight-bit unsynchronized crossing between two unrelated clocks while printing
"1 of them one clock gated differently" about a design containing no clock
gate at all. §1.1.

**An eighth.** A crossing that arrives on a synchronous *clear* — the
`if (flag) q <= 0; else q <= d;` that `opt_dff` lowers to `$sdff`'s `SRST` pin
— is not reported at all. `_data_cone_registers` walks `D` and `EN` and no
other input. §1.2.

Sections follow. Each was appended after it was run.

## 1. Blocking

### 1.1 A vector clock port is one clock source, so the gate passes on a real asynchronous crossing

`Module.finish` (`tools/dvh/design.py:71-75`) maps every bit of an input port
to the **port name**:

```python
        for pname, p in self.ports.items():
            if p["direction"] == "input":
                for b in p["bits"]:
                    if isinstance(b, int):
                        self.port_of_bit[b] = pname
```

`_walk_to_sources` (`clocks.py:101-102`) returns `Source(mod.port_of_bit[bit],
"port")`, so two *different bits* of one vector port produce one source name.
`_domain_key` keeps them apart, because identity is the net — that fix holds —
but `same_source` in `crossings` (`clocks.py:418-421`) compares *source name
sets*, and those are equal. The crossing is therefore excluded from
`unrecognized` (`clocks.py:442-443`) and `dvh read` returns 0.

```systemverilog
// veccclk.sv -- two unrelated lane clocks arriving on one vector port.
// lane_clk[0] and lane_clk[1] are separate asynchronous clocks; the bus is
// how a multi-lane block normally receives them.
module veccclk (input logic [1:0] lane_clk,
                input logic rst_n,
                input logic [7:0] d,
                output logic [7:0] q);
  logic [7:0] a, b;
  always_ff @(posedge lane_clk[0] or negedge rst_n)
    if (!rst_n) a <= 8'h0; else a <= d;
  always_ff @(posedge lane_clk[1] or negedge rst_n)
    if (!rst_n) b <= 8'h0; else b <= a;
  assign q = b;
endmodule
```

```
clock domains: 2
  lane_clk#2: 1 registers
  lane_clk#3: 1 registers
registers without reset: 0
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (lane_clk#2) -> b (lane_clk#3), 8 bits, no synchronizer shape
instances: 0, connections: 0
```

**Exit 0.** An eight-bit unsynchronized crossing between two asynchronous
clocks, and the build passes. The JSON is explicit about the mechanism:

```json
{"to": "b", "to_domain": "lane_clk#3", "from": "a",
 "from_domain": "lane_clk#2", "width": 8, "direct": true,
 "second_stage": [], "shape_recognized": false,
 "same_clock_source": true, "note": "no synchronizer shape"}
```

and `dvh clock-tree` shows there is no gating anywhere: both registers report
`"gated_or_muxed": false, "through": [], "clock_ambiguous": false`. So the
printed line *"1 of them one clock gated differently"* is a false statement
about a design that contains no clock gate, no multiplexer and no shared
source. This is not the recorded limit ("the walk picked the wrong signal as
the clock"): nothing was mis-identified, both clocks resolved, and the report
still asserts a relationship between them that does not exist.

The idiomatic form is worse, because nobody writes `lane_clk[0]` by hand — they
write a `generate` loop:

```systemverilog
// genclk.sv -- a clock tree built in a generate loop over a clock array.
module genclk #(parameter int N = 2)
               (input logic [N-1:0] clk, input logic rst_n,
                input logic [7:0] d, output logic [7:0] q);
  logic [7:0] stage [N];
  genvar i;
  generate
    for (i = 0; i < N; i++) begin : g_lane
      always_ff @(posedge clk[i] or negedge rst_n)
        if (!rst_n) stage[i] <= 8'h0;
        else        stage[i] <= (i == 0) ? d : stage[i-1];
    end
  endgenerate
  assign q = stage[N-1];
endmodule
```

```
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK stage[0] (clk#2) -> q (clk#3), 8 bits, no synchronizer shape
```

Exit 0 again. `input logic [NLANES-1:0] lane_clk` with a per-lane pipeline is
an ordinary multi-lane PHY, and it is the shape the chapter's own tool is least
able to see.

**This falsifies a printed sentence.**
`chapters/ch03-digital-design-for-verifiers.qmd:294`:

> "Where the two nets trace back to a single shared source, as a gated clock
> does, the tool says so and the path does not fail the gate. Where they do
> not, as with a divider or a multiplexer between two clocks, it does fail"

Here the two nets do *not* trace back to a single shared source — they are two
independent clocks — and the tool says they do.

**Fix.** `same_clock_source` must be a statement about *nets*, not names. Two
candidate changes, in order of preference:

1. Make a port source carry the bit, not just the port: in `_walk_to_sources`,
   return the port name for a one-bit port and `f"{port}[{index}]"` for a bit
   of a vector, using the index of the bit within the port's `bits` list. The
   printed label improves too — `lane_clk[0]` is what a reader wants to see.
2. Or compute `same_source` from the clock *bits* the two registers' walks
   reached rather than from `clock_sources`, and record those bits in
   `clock_tree` so `crossings` can compare them.

Either way, add `veccclk.sv` (or `genclk.sv`) as a regression fixture, and the
schema's description of `same_clock_source` should say what the flag does —
see §3.2.

Note that the same name-collapse affects `clock-tree`'s `clock_sources` field,
which reports `["lane_clk"]` for both registers. A consumer of that JSON, which
Appendix I invites, cannot tell the two clocks apart at all.

### 1.2 A crossing that arrives on a synchronous clear is not reported

`_data_cone_registers` (`clocks.py:264-272`) walks two ports:

```python
    for port in ("D", "EN"):
```

`opt_dff` — the pass the chapter at `:231` says was added precisely so a
synchronous reset is not missed — folds `if (flag) q <= 0; else q <= d;` onto
`$sdff`'s `SRST` pin. `flag` then leaves the data cone entirely.

```systemverilog
// srst2.sv -- the crossing arrives on a synchronous clear that opt_dff
// folds onto $sdff's SRST pin.  `a` is an aclk register.
module srst2 (input logic aclk, bclk, input logic d,
              input logic [7:0] x, output logic [7:0] q);
  logic a;
  logic [7:0] b;
  always_ff @(posedge aclk) a <= d;
  always_ff @(posedge bclk)
    if (a) b <= 8'h0;
    else   b <= x;
  assign q = b;
endmodule
```

```
clock domains: 2
  aclk: 1 registers
  bclk: 1 registers
registers without reset: 1
  a  [srst2.sv:7]
crossings: 0, shape not recognized: 0
instances: 0, connections: 0
```

Exit 0. `dvh crossings` returns `{"crossings": [], "unrecognized": []}`. The
netlist is two cells:

```
$sdff CLK=[3] D=[5..12] Q=[13..20] SRST=[21]
$dff  CLK=[2] D=[4]     Q=[21]
```

`[21]` is the aclk register's `Q` driving the bclk register's `SRST`, and
nothing walks `SRST`. This is not a reset-domain crossing that a reader might
argue belongs in another report: it is an ordinary functional control bit
crossing a clock boundary unsynchronized — the textbook single-bit control
crossing the chapter says at `:249` the tool exists to catch — that happens to
have been *lowered* onto a reset pin by the very optimization pass the chapter
added. Write the same RTL with an asynchronous reset present as well
(`srstx.sv`) and Yosys leaves it as a `$mux` on `D`, and the crossing *is*
reported, `CHECK a (aclk) -> b (bclk), 8 bits`, exit 1. So whether the tool
sees a real crossing depends on whether the destination register happens to
have an asynchronous reset.

The same hole swallows `$dffsr`'s asynchronous `SET`:

```systemverilog
// dffsrx.sv -- the crossing arrives on $dffsr's asynchronous SET.
module dffsrx (input logic aclk, bclk, input logic d, x,
               output logic q);
  logic a, b;
  always_ff @(posedge aclk) a <= d;
  always_ff @(posedge bclk or posedge a)
    if (a) b <= 1'b1; else b <= x;
  assign q = b;
endmodule
```

`crossings: 0`, exit 0 — while `dvh reset-tree` on the *same* design reports
`"b": {"kind": "asynchronous", "active": "high", "sources": ["a"]}`. The tool
already knows that a register in `aclk` asynchronously drives a register in
`bclk`; the crossing report simply does not ask the reset tree.

**Fix.** Extend `_data_cone_registers` to every input port of the destination
cell that is not `CLK` — `SRST`, `ARST`, `CLR`, `SET`, `ALOAD`, `AD` — and
carry the port name into the crossing record so the report can distinguish
"arrives on the data" from "arrives on the clear". A crossing onto a reset pin
is a different review question from one onto `D`, and the schema should say
which it is. Fixtures: `srst2.sv` and `dffsrx.sv`.

### 1.3 `dvh read` and `dvh reset-tree` crash on `$aldff`

`design.py:29` puts `$aldff` and `$aldffe` in `ASYNC_RESET_TYPES`.
`reset_tree` (`clocks.py:238-241`) then does

```python
            pin = "ARST" if "ARST" in cell.conns else "CLR"
```

`$aldff` has neither. Its asynchronous ports are `ALOAD` and `AD`. Every
command that builds a reset tree dies:

```systemverilog
// aldffx.sv -- an asynchronously loaded register.
module aldffx (input logic aclk, bclk, ld, input logic [7:0] d,
               output logic [7:0] q);
  logic [7:0] a, b;
  always_ff @(posedge aclk) a <= d;
  always_ff @(posedge bclk or posedge ld)
    if (ld) b <= a; else b <= d;
  assign q = b;
endmodule
```

```
Traceback (most recent call last):
  ...
  File ".../tools/dvh/clocks.py", line 253, in reset_tree
    for b in cell.conns[pin]:      # $dffsr's set/reset are per-bit vectors
             ~~~~~~~~~~^^^^^
KeyError: 'CLR'
```

Confirmed on `dvh read` and `dvh reset-tree`; `yosys` emits
`$aldff ['AD', 'ALOAD', 'CLK', 'D', 'Q']` for that design. `dvh crossings` and
`dvh clock-tree` survive because they do not build a reset tree.

This is legal, ordinary SystemVerilog — an asynchronous load or an
asynchronous preset to a non-constant value — and the tool aborts on it with a
Python traceback and exit 1, the same exit code a *finding* uses. A project
that has gated its build on `dvh read`, which is what the Future
Directions callout at `:291`-`:299` proposes, cannot tell a crash from a crossing.

**Fix.** Either handle `$aldff`/`$aldffe` properly — the asynchronous behavior
is a load, so report `kind: "asynchronous load"` with `ALOAD` as the control
and `AD` as the value — or remove them from `ASYNC_RESET_TYPES` and let them
fall through to `no_reset`, which is at least true. The `AD` input is also a
data path (`b <= a` above), so §1.2's fix must cover it. Separately,
`cli.main` should catch and report rather than traceback, and should not reuse
exit 1 for an internal error; `gate2c` §2.3 raised the same point about a
missing file and it is still open.

### 1.4 `shape_recognized: true` eight times on an eight-bit bus — `gate2d` §1.3, unfixed

`_flag_converging_synchronizers` (`clocks.py:275-328`) still fires only when a
**register** downstream reads two chains together, so a bus that leaves the
block through its ports never meets one. `gate2d` §1.3 reported this with a
two-bit design and it is unchanged; here it is in the exact shape the chapter
names in print.

```systemverilog
// perbit8.sv -- eight parallel one-bit synchronizers on an eight-bit bus,
// each bit declared separately, output only through the module's ports.
module perbit8 (input logic aclk, bclk, rst_n, input logic [7:0] d,
                output logic [7:0] q);
  logic a0,a1,a2,a3,a4,a5,a6,a7;
  logic p0,p1,p2,p3,p4,p5,p6,p7;
  logic r0,r1,r2,r3,r4,r5,r6,r7;
  always_ff @(posedge aclk or negedge rst_n)
    if (!rst_n) {a7,a6,a5,a4,a3,a2,a1,a0} <= 8'h0;
    else begin a0<=d[0]; a1<=d[1]; a2<=d[2]; a3<=d[3];
               a4<=d[4]; a5<=d[5]; a6<=d[6]; a7<=d[7]; end
  always_ff @(posedge bclk or negedge rst_n)          // first stages
    ...
  always_ff @(posedge bclk or negedge rst_n)          // second stages
    ...
  assign q = {r7,r6,r5,r4,r3,r2,r1,r0};
endmodule
```

```
crossings: 8, shape not recognized: 0
  known a0 (aclk) -> p0 (bclk), 1 bit, two-flop synchronizer
  known a1 (aclk) -> p1 (bclk), 1 bit, two-flop synchronizer
  ... (all eight)
```

`dvh read` exits **0**; `dvh crossings --validate` exits 0 with
`"unrecognized": []` and `"shape_recognized": true` on all eight.

The boundary is one register wide. `perbit8r.sv` is the identical design with
one extra `always_ff` in `bclk` that latches the eight bits before they leave,
and every one of the eight is then rejected:

```
crossings: 8, shape not recognized: 8
  CHECK a0 (aclk) -> p0 (bclk), 1 bit, 8 one-bit synchronizers are read
        together by q; their bits can resolve in different cycles
```

**This falsifies three printed sentences.**

`chapters/ch03-digital-design-for-verifiers.qmd:321`, exercise 6:

> "The tool rejects eight parallel one-bit synchronizers on an eight-bit bus,
> because someone anticipated that anti-pattern. Find a structure it would
> wrongly accept, and write the check that would catch it."

`perbit8.sv` *is* eight parallel one-bit synchronizers on an eight-bit bus, and
the tool accepts all eight. The exercise asks the reader to find a structure
the tool wrongly accepts while standing on an example it also wrongly accepts.

`:270`:

> "The tool rejects it only because someone anticipated that anti-pattern and
> wrote a check for it, and the first version of that check looked for bits
> sharing a declared name, which a design that declares its eight flops
> separately walks straight past. The check improved; the lesson did not
> change."

`perbit8.sv` declares its eight flops separately and walks straight past the
*improved* check too, on the axis the improvement did not cover: not how the
sender declares the bits, but where they are read.

`:308`, the summary bullet: "per-bit synchronizers are a loss of data rather
than a partial fix" — which the tool's own report contradicts on this design,
printing `known ... two-flop synchronizer` eight times.

`:253` is the one sentence in the chapter that is accurate here, because it
says "one register downstream reads *together*". That accuracy is what makes
`:270`, `:308` and `:321` wrong: the chapter states the limitation once and
then three times writes as though it were not there.

**Fix.** `gate2d` offered two and the second is still the better one: demote
whenever two or more recognized chains belong to the same crossing group — same
`from_domain`, same `to_domain`, first stages on the same clock — regardless of
where they are read, and say so in the note. Treating a top-level output port
group as a convergence point also works and is narrower. Either way `:321`
needs an example the tool actually rejects, and `perbit8.sv` becomes a fixture.

### 1.5 §1.1 again by a second, independent route: a black box with a multi-bit clock output

The name-collapse of §1.1 is not confined to ports. `_walk_to_sources`
(`clocks.py:181`) names an unknown driver `f"{mod.net(bit)} (driven by
{cell.type})"`, and `Module.net` (`design.py:77-80`) returns the *net* name, so
every bit of one vector gets one name. A phase-locked loop emitting two clocks
on one bus is therefore one source:

```systemverilog
// pllbb.sv -- two clocks out of one black box, on one output vector.
(* blackbox *)
module clkgen (input logic ref_clk, output logic [1:0] clk_out);
endmodule

module pllbb (input logic ref_clk, rst_n, input logic [7:0] d,
              output logic [7:0] q);
  logic [1:0] c;
  logic [7:0] a, b;
  clkgen u_pll (.ref_clk(ref_clk), .clk_out(c));
  always_ff @(posedge c[0] or negedge rst_n)
    if (!rst_n) a <= 8'h0; else a <= d;
  always_ff @(posedge c[1] or negedge rst_n)
    if (!rst_n) b <= 8'h0; else b <= a;
  assign q = b;
endmodule
```

```
crossings: 1, shape not recognized: 1, 1 of them one clock gated differently
  CHECK a (c (driven by clkgen)#20) -> b (c (driven by clkgen)#29), 8 bits,
        no synchronizer shape
```

**Exit 0.** This is the chapter's own canonical clock source: `:56` defines a
primary clock as "a primary input of the design or the output of an analog
block such as a phase-locked loop treated as a black box". Both of the two
forms the definition names defeat the gate when the block emits more than one
clock on one bus. Whichever fix §1.1 takes has to cover the `unknown` source
name as well as the `port` one.

For contrast, and to show these are specific rather than general: the same
crossing carried over an internal tri-state net (`tribus.sv`), over a
bidirectional top-level `inout` pad (`inoutx.sv`), through a one-hot `$pmux`
select (`pmuxsel.sv`), through two module boundaries with the clocks arriving
only inside the submodules (`hierclk.sv`), through an initialised ROM indexed
by a foreign register (`romcross.sv`) and through a dual-clock simple
dual-port RAM (`sdpram.sv`, 16 crossings and 17 unreset registers) are all
reported, all with exit 1. The memory passes and the hierarchy flattening hold
up.

### 1.6 `:287` undercounts the repository's own history, and calls a class closed that is not

`chapters/ch03-digital-design-for-verifiers.qmd:287`:

> "Crossings vanished from the report six separate ways: a domain identified
> by the names of its clock sources rather than by the net, three different
> rules that suppressed a finding in the name of removing a false alarm, a
> walk that stopped at a latch, and an array that never became registers at
> all. Structures were recognized as synchronizers that were not: chains
> behind an enable, chains sampling opposite clock edges, and eight parallel
> one-bit chains carrying one value."

Replacing `gate2d`'s enumeration of fixtures with a taxonomy was the right
move, and the taxonomy is one round behind the repository in two places.

**(a) The count is six and the fixtures record eight.** Two of the sixteen
designs under `tools/dvh/tests/rtl/` record ways a crossing vanished that no
clause of that sentence covers:

* `latch_enable_crossing.sv` — its own header says it plainly: "The walk was
  changed once already to pass through a latch rather than stop at one ... It
  passed through the data input only, so a register in one domain driving the
  *enable* ... reported nothing." That is not "a walk that stopped at a latch";
  the walk did not stop, and `crossing_via_latch.sv` is the separate fixture
  for the case that did. `clocks.py:117-120` describes the two as distinct
  defects.
* `scan_clock_mux.sv` — `test_a_scan_clock_mux_does_not_escape_the_build_gate`
  says "it was classified as a gating enable and the crossing was excused as
  'one clock, gated differently', exit 0." The sentence's first list is about
  vanishing "from the report" and its second about false recognition; a
  crossing that is printed and then excused from the gate is in neither, and
  it is the mechanism §1.1 of this review reaches by a different route.

These are the two most recent entries, which is the pattern the paragraph
immediately goes on to name: "Every one of those was a claim this chapter made
about its own code before anyone ran the code on a design that tested the
claim."

**(b) "eight parallel one-bit chains carrying one value" is listed as a class
the tool no longer mis-recognizes.** §1.4 above is eight parallel one-bit
chains carrying one value, reported as eight two-flop synchronizers, exit 0.

**Fix.** Either state the count as the repository holds it — and it will need
raising again after §1.1–§1.4 — or drop the numeral and the closed list, and
say that the directory grows at every review, which is the sentence's actual
argument and does not depend on a count. Whichever is chosen, the per-bit
clause must not claim more than `:253` does.

## 2. Non-blocking findings

### 2.1 The published schema's `direct` description is still false

`tools/dvh/schema/crossings.schema.json`, field `direct`:

```json
"direct": {
  "description": "True if the sender reaches D with no logic between.",
  "type": "boolean",
  "$comment": "And on every clock: an enable holds, not resamples."
}
```

`gate2d` §1.5(b) reported this and the fix put the missing term in `$comment`.
`test_every_field_carries_a_description` says in its own docstring why that is
not enough: "`description` is the consumer-facing keyword; `$comment` is a note
between schema authors and does not count." So a caller reading the contract
still reads a false sentence. Verified on `enabled.sv` (an `aclk` register
straight onto the `D` of a `$dffe` on `bclk`): `"direct": false`, while the
sender does reach `D` with no logic between.

Two neighbours in the same file are worse after §1.1:

* `unrecognized` — "The subset to review." A `same_clock_source` crossing is
  excluded from it, and §1.1 shows that set now includes genuinely
  asynchronous crossings. `:294` says in the chapter that such a pair still
  needs a person.
* `same_clock_source` — "True if both clocks resolve to the same source."
  False on `veccclk.sv` and `pllbb.sv`: they resolve to the same *name*. The
  description also does not say that this is the flag that keeps a crossing
  out of the build gate, which is the only reason a consumer would care.

**Fix.** Move the second term of `direct` into `description`; restate
`unrecognized` as "the crossings this run fails on"; and once §1.1 is fixed,
`same_clock_source` should say "same clock net" and name its effect on the
exit code.

### 2.2 A recognized shape whose first stage fans out into functional logic

Inside the chapter's stated contract, but worth knowing, and a better exercise
than the one `:321` currently sets:

```systemverilog
// metafan.sv -- the first stage's output escapes into functional logic as
// well as feeding the second stage: a metastable node used directly.
module metafan (input logic aclk, bclk, rst_n, input logic d, x,
                output logic q, qq);
  logic a, s1, s2, use_raw;
  always_ff @(posedge aclk or negedge rst_n)
    if (!rst_n) a <= 1'b0; else a <= d;
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) s1 <= 1'b0; else s1 <= a;
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) s2 <= 1'b0; else s2 <= s1;
  always_ff @(posedge bclk or negedge rst_n)
    if (!rst_n) use_raw <= 1'b0; else use_raw <= s1 & x;
  assign q = s2; assign qq = use_raw;
endmodule
```

```
crossings: 1, shape not recognized: 0
  known a (aclk) -> s1 (bclk), 1 bit, two-flop synchronizer
```

Exit 0. The receiving path *is* a two-flop synchronizer, so this is the
ceiling `:270`–`:272` describes honestly rather than a false statement — the
chapter is not wrong here. It is listed because exercise 6 at `:321` asks the
reader to "find a structure it would wrongly accept", and this one is a real
CDC bug class (a metastable node consumed directly), unlike the example the
exercise itself offers.

### 2.3 An internal error and a finding still share exit 1, and the exit code now carries less

`gate2c` §2.3, unchanged, and more consequential now. `design._run_yosys` runs
Yosys with `capture_output=True` and `check=True`; a `CalledProcessError`
escapes `cli.main` as a raw traceback with Yosys's own diagnostics discarded,
and the process exits 1 — the code a *finding* uses. Reproduced by handing the
tool RTL Yosys rejects, and by `dvh read nosuchtop f.sv`.

With §1.1, §1.2 and §1.4 in place, a project that has gated its build on
`dvh read` — which is exactly what the Future Directions callout at `:291`-`:299` proposes
— can get exit 0 on a real asynchronous crossing and exit 1 on a typo in a
file name. `cli.main` should catch `CalledProcessError`, print `e.stderr`, and

### 2.4 The undecided-clock note says "enable" where the cause was selection

`clocks.py:431-434` prints one note for every ambiguous pair: "clock and enable

roots*, and there is no enable involved:

```
CHECK stage1 (func_clk) -> q (undecided clock of q), 8 bits,
      clock and enable not distinguishable here; declare the clocks
```

The verdict is right and loud, which is what matters, but the reason given is

### 2.5 `width` is the receiving register's width, not the crossing's

"Width of the receiving register, in bits" — and the chapter's `:253` ties the
width test to the shape rather than to the printed line, so nothing is false.
It does read as the width of the value that crossed, which it is not.

## 3. Answers to the five questions asked

**1. Can a crossing still disappear? Yes, by a mechanism not on the list.**
`srst2.sv` (§1.2): an eight-bit register in `bclk` synchronously cleared by an
`aclk` register. `crossings: 0`, `unrecognized: []`, exit 0. Cause:
`_data_cone_registers` walks `D` and `EN` and nothing else, so `opt_dff` —
added by this chapter to stop a synchronous reset being missed — moves the
crossing out of the cone onto `$sdff`'s `SRST`. `dffsrx.sv` is the same hole on
`$dffsr`'s asynchronous `SET`, and `dvh reset-tree` reports the very
relationship `dvh crossings` misses.

**2. Can the build gate pass on a real asynchronous crossing? Yes, twice
over.** `veccclk.sv` and `genclk.sv` (§1.1): two asynchronous clocks on one
vector input port. `pllbb.sv` (§1.5): two asynchronous clocks on one black
box's output vector. All three exit 0 on an eight-bit unsynchronized crossing,
via `same_clock_source`, and all three print "1 of them one clock gated
differently" about designs with no gate. This is not the recorded limit of a
mis-identified clock: both clocks resolve, `clock_ambiguous` is false, and the
walk reaches the right nets. The fault is that `same_clock_source` compares
source *names* and `Module` names a bit by its port or net rather than by its
bit.

**3. Can `shape_recognized: true` be made false? Yes, unchanged from the last
round.** `perbit8.sv` (§1.4): eight parallel one-bit synchronizers on an
eight-bit bus, all eight `known`, exit 0, because the bus leaves through the
module's ports and `_flag_converging_synchronizers` needs a downstream
register. `gate2d` §1.3 reported this and it is not fixed. The two shapes
`gate2d` reported alongside it, the opposite-edge second stage and the scan
multiplexer, both **are** fixed: `halfperiod.sv` now exits 1, and `testmux.sv`
reports `undecided clock of q` and exits 1.

**4. Does the chapter describe the code?** Four sentences do not: `:294`
(a multiplexer between two clocks fails the gate — §1.1), `:270`, `:308` and
`:321` (the tool rejects eight per-bit synchronizers — §1.4), plus `:287`'s
count and its per-bit clause (§1.6). Three sentences that were wrong last
round are now right: `:251` carries the enable term, `:249`'s latch sentence
matches a walk that now follows every latch input, and `:287` no longer
enumerates a fixture list that had gone stale.

**5. House rules and constraints.** No violation in the chapter. All three
house-rule items `gate2d` marked blocking are fixed. Both modes of
`scripts/check-citations.sh` pass. The research note's seven prohibitions are
all respected. Details in §2.6–§2.8.

## Verdict

Five blocking findings:

| § | finding | one-line fix |
|---|---|---|
| 1.1 | two clocks on one vector port are one source; gate passes on a real asynchronous crossing, exit 0 | name a port source by its bit, or compare clock *nets* in `same_source` |
| 1.2 | a crossing onto `$sdff`'s `SRST` or `$dffsr`'s `SET` is not reported at all | walk every non-`CLK` input of the destination cell in `_data_cone_registers` |
| 1.3 | `dvh read`/`dvh reset-tree` crash with `KeyError: 'CLR'` on `$aldff` | handle `ALOAD`/`AD`, or drop `$aldff` from `ASYNC_RESET_TYPES` |
| 1.4 | eight per-bit synchronizers on an eight-bit bus report `known` when the bus leaves through ports | demote by crossing group, not by downstream register; correct `:321` |
| 1.5/1.6 | four chapter sentences do not describe the code (`:270`, `:287`, `:294`, `:308`, `:321`) | rewrite with the code in front of you, after the above land |

`STATUS.md`'s stopping rule applies and should be read before the next patch.
It says: "another defect of the same class in `clocks.py` means the design
change failed — escalate rather than patch a fifth time." §1.1 and §1.2 are
that class. The shape of the recurrence is worth naming precisely, because it
is not that the fixes were wrong — every fix this repository has made has held,
and I re-ran all of them — but that each was made against the *instance* the
last review constructed:

* **Identity by name, not by net.** `_domain_key` was fixed to key on the net
  after three reviews. `same_clock_source` was never given the same treatment,
  so the identical defect survives one function away, and §1.1 is that defect
  reaching the build gate through the two clock sources the chapter's own
  Definition callout names.
* **A walk that covers some ports of a cell.** `_data_cone_registers` was given
  `EN` alongside `D`; the latch branch of `_walk_to_sources` was given
  `EN`, `ARST`, `SET` and `CLR` alongside `D` this round. The destination
  register's own `SRST`, `SET`, `CLR`, `ALOAD` and `AD` were not, and §1.2 is
  that.

Both suggest the same remedy, which is cheaper than another round of
instances: replace each hard-coded port list and each name comparison with an
enumeration the netlist supplies — every input port that is not `CLK`, and the
bit rather than the name — and let the tests assert the enumeration rather than
the instance. §1.3 is evidence for the same point from a third direction:
`$aldff` was put in a type set without anyone asking what ports that type has.

**blocking findings remain**
